# WingMan · 聊天僚机 — 项目全流程报告

> 把聊天记录交给大模型记忆，通话时实时听懂对方，然后告诉你**该怎么回**。
>
> 本报告分三轮：**第一轮**搭出可运行脚手架并上线 GitHub（一~四节）；  
> **第二轮**把它做成「双击就能用、且坏了能自己看出哪坏了」的桌面软件（第五节）；  
> **第三轮**把打包版真正跑一遍，挖出三个只有实战才暴露的问题（第六节）。  
> 第五节是形态上的收口，第六节是「承诺的功能到底能不能用」的收口。

---

## 一、原始需求

做一个 GitHub 项目，三个能力：

1. **接入大模型语音通话识别**
2. **记忆微信 / QQ 聊天记录并分析**
3. **接入大模型，通过识别回复进行指导回复** —— 它给选项、人来选；也可自动回复

期望效果：选中和某个人的全部 QQ 聊天记录 → 让大模型记忆 → 给出聊天规划 →  
对方回复后点击启动 → 识别后给出对此时对方的分析、几个可选回复、并实时推测聊天走向。

### 澄清后确定的四个岔路口

| 问题     | 选择                         |
| ------ | -------------------------- |
| 聊天记录来源 | QQ + 微信**都要**，做成插件式适配器     |
| 语音场景   | **实时监听 + 事后转写都要**          |
| 大模型接入  | 云端 API 与本地 Ollama **可切换**  |
| 交付程度   | 完整方案文档 + **可运行脚手架**，便于持续迭代 |

### 第二轮的三个岔路口（做软件，不是做脚手架）

第一轮交付的是「能跑通」；但**能让别人也用上**是另一回事。第二轮开头重新问了三个问题：

| 问题     | 选择               | 备注                  |
| ------ | ---------------- | ------------------- |
| 先动哪一块  | **直接打包 .exe**    | 我当时不确定 .exe 适不适合，先试 |
| 最终整合形态 | **独立 .exe 桌面软件** | 双击打开，像个正经软件         |
| 语音走哪条路 | **两条都留，向导里让我选**  | 云端省事 / 本地隐私，场景不同    |

关于「.exe 适不适合」我当时的判断是：**可行，但它是「问题放大器」**。  
核心依赖都是纯 Python + numpy，打包技术上没问题；但打包之后  
错误会从「控制台红字」变成「双击没反应」，每次改代码还要重新构建。  
所以这次打包**顺带把三件必须一起做的事做掉了**（数据目录、错误可见性、自检），  
没有只交一个壳。详见第五节。

## 三、六个关键设计决策

这部分是整份报告里最值钱的内容 —— 都是**有代价的取舍**，不是教科书结论。

### 1. 双通道采集 = 天然的说话人分离

语音通话时：

- **系统回环（loopback）捕获到的是对方的声音**
- **麦克风捕获到的是自己的声音**

所以只要同时开两路采集，就白得了说话人分离的结果，  
不需要跑声纹识别或说话人聚类模型。

这是整个语音方案能成立的地基。代价是需要 `soundcard` 这类能抓回环的库，  
且必须正确识别系统的默认播放设备。

### 2. 不让模型给自己打分

最初的想法是让模型给每条候选回复打 0~10 分。实测不可行：  
**模型对自产内容的自评普遍偏高，且方差极小**，四条回复经常都是 8.5、8.7、8.6、8.4，  
排序毫无意义。

改用本地可解释启发式，四个维度：

| 维度   | 判据                                  |
| ---- | ----------------------------------- |
| 自然度  | 长度合理性（3~25 字最佳）、语气词、AI 腔词表命中、书面语    |
| 共情温度 | 是否呼应对方提到的话题、是否含情绪回应词、对方情绪强度高时未接住则扣分 |
| 目标推进 | 行动动词、提问引导、与用户长期目标是否一致               |
| 风险   | 雷区命中、感叹号过多、绝对化表达、与对方原话重合度过高（复读）     |

`total = 1 + 9 × clamp(0.30·自然 + 0.25·共情 + 0.30·推进 − 0.35·风险)`

**关键在于输出 `score_notes`**：不只给分，还要说明"− 命中雷区「宝贝」"。  
用户看得懂分数是怎么来的，这比一个孤零零的 7.2 有用得多。

### 3. 推演概率不让模型直接编

让模型输出 `58%`、`27%`、`15%` 这种数字是不可信的 ——  
它对概率的标定能力远不如对"大概率/有可能/不太可能"的定性判断。

做法：提示词里只允许填 `likely / possible / unlikely`，  
代码映射为 `0.62 / 0.26 / 0.12` 再按实际分支数归一化。

**并且推演结果必须带免责声明，前端要显眼展示。**  
把一个语言模型的情景模拟包装成预言，是在骗用户，  
而用户会据此做出真实的、可能有代价的决策。这条线不能越。

### 4. 观测与推测必须分开

分析结果里：

- `signals` = **观测**（消息长度、标点、表情数、有无提问、回复节奏）
- `subtext` = **推测**（她其实在想什么）

前端用不同颜色分开展示，观测项可以点开看到原文。

这么做的目的不是好看，是**降低用户对模型的盲目信任** ——  
而盲目信任一个会幻觉的模型，在人际关系这个场景里代价很高。

### 5. 事实层全量注入，检索层动态召回

记忆分三层：

| 层     | 存量  | 进 Prompt 的方式     | 理由                        |
| ----- | --- | ---------------- | ------------------------- |
| L1 事实 | 几十条 | **全量**           | 几百 token，但漏掉"她讨厌被叫宝贝"代价极大 |
| L2 摘要 | 若干  | 最近 3~5 条         | 长期脉络                      |
| L3 检索 | 上万条 | 按当前消息动态召回 top-30 | 细节与当时语境                   |

L1 全量是关键判断：**漏掉的代价和多余的成本完全不对称**。

### 6. 三个工厂都保证"降级可跑"

`build_llm` / `build_embedder` / `build_asr` 的契约是**永远返回可用实例**：

- 配了云模型 → 用云端
- 配了 Ollama → 用本地
- 都没配 → Mock Provider，`import` 后立刻能跑完整链路
- Embedding 没配 → 本地字符 n-gram 哈希向量（不是玩具，中文里字面重合和语义相关高度相关）

这么设计是因为：**第一次跑起来时看不到东西的项目，很难被继续做下去。**  
Mock 的价值在于让人先看清楚交互流程对不对，再决定要不要投入配置真实模型。

## 四、关于"自动回复"的立场

需求里提到了自动回复。项目**没有实现无人值守的代聊**，只有「建议 + 一键复制」。

理由写在 `docs/COMPLIANCE.md`，核心是三条：

1. **对方以为在和你交流。** 这是欺骗，不是效率工具。
2. **关系的价值来自真实。** 用模型代聊得到的"好感"是假的，你也没从中成长。
3. **一旦暴露，信任崩塌。** 这是不可逆的损失。

所以 API 层面的形态是：

```
模型出候选 → 你选择 → 落到你的输入框 → 你确认后发送
```

决策权和责任都留在人手里。  
`engine/prompts.py` 里的红线段落也写死了：禁止操纵/PUA、禁止谎报身份、禁止纠缠。

## 五、从脚手架到桌面软件（第二轮）

这一节是全部工作的收口。核心命题只有一个：

> **源码能跑 ≠ 别人能用。** 中间的差距不是「打个包」，而是三类问题：  
> 数据写哪、出错怎么让人看见、配置状态怎么让人自己查明白。

### 5.1 打包的真实代价：它是「问题放大器」

先说结论：**.exe 可行，但它会把所有原本「看得见」的问题变成「看不见」。**

|       | 源码运行                 | 打包成 exe                    |
| ----- | -------------------- | -------------------------- |
| 报错    | 控制台红字 + traceback    | **双击没反应**                  |
| 数据    | `backend/data/`，随手能看 | 写哪？程序目录可能只读                |
| 改一行代码 | 保存即生效                | 重新构建 40 秒                  |
| 缺依赖   | `pip install` 一行     | 要么内置，要么用户永远修不好             |
| 启动    | 秒级                   | onefile 要解压十几秒，**用户会以为卡死** |

所以这次打包**没有只交一个壳**，而是连带把三件必须一起做的事做掉了（5.2~5.4）。  
如果只打包不改这三处，用户拿到的会是一个「点了没反应、数据找不到、也不知道缺什么」的黑盒。

一个具体的取舍：**用 onedir 而不是 onefile**。  
onefile 每次启动解压到**随机临时目录**、退出即删 —— 用户第二次打开会发现  
「我导入的聊天记录全没了」。onedir 启动是秒级的，东西都看得见，排错也直观。  
代价是分发的是一个文件夹而不是单文件，这在说明里写清楚就行。

### 5.2 数据目录：为什么必须挪出程序目录

冻结态（`sys.frozen`）下把可写数据全部迁到 `%LOCALAPPDATA%\WingMan`：

```
%LOCALAPPDATA%\WingMan\
├── data\wingman.db      聊天记录、画像、设置
├── logs\wingman.log     滚动日志（2MB × 3）
├── logs\selfcheck.txt   最近一次自检报告
├── logs\asr_test.txt    最近一次语音自检报告
├── models\              本地语音模型权重（下过才有）
└── .env                 可选的手工配置
```

资源（前端页面、文档）仍从包内 `_MEIPASS` 读，**只有可写的才搬走**。  
判断集中在 `config.py` 的 `_resource_dir()` / `_writable_root()` 两个函数里，  
其他模块不感知「自己是不是在 exe 里」。

顺带做了一件容易漏的事：老名字的库文件（改名前的 `chatwing.db`）会自动改名过来，  
连 `-wal` / `-shm` / `-journal` 这些边车文件一起搬，**用户数据不丢**。

### 5.3 错误可见性：`--noconsole` 是打包最大的坑

打包后没有控制台，**所有异常都变成「双击没反应」**，这是最糟的失败方式 ——  
用户连「发生了什么」都不知道，更没法反馈。

对策是给每条错误路径都留一个出口：

| 出口                       | 面向谁    | 内容                                    |
| ------------------------ | ------ | ------------------------------------- |
| `logs/wingman.log`       | 排查者    | 滚动日志，UTF-8                            |
| 原生弹窗（`MessageBoxW`）      | 普通用户   | 人话 + 日志文件路径                           |
| `WingMan.exe --check`    | 反馈问题时  | 自检报告 → `logs/selfcheck.txt`，可直接发给别人   |
| `WingMan.exe --asr-test` | 语音出问题时 | 设备/电平/引擎/文本逐步输出 → `logs/asr_test.txt` |
| 界面「自检」页                  | 全部用户   | 三档结论 + 每项一个跳转按钮                       |

还有一个小但致命的细节：**冻结后 stdout 会掉回 Windows 本地代码页（GBK）**，  
日志里的中文全变乱码。`_setup_logging()` 里显式  
`sys.stdout.reconfigure(encoding="utf-8", errors="replace")`。

### 5.4 自检：状态只有三档，每条非「已完成」都要带一个「点哪里能修好」

`selfcheck.py` 的硬规则：

```
ok   可用，不用管
warn 能用但会打折，或者非必需项缺失
fail 这项功能现在是坏的，会给用户错误结果
```

**不许只报「失败」** —— 每条非 ok 必须带一句人话说明 + 一个可执行的下一步。  
界面上还要有个按钮直接跳到能把这项修好的那个设置页。

这条规则的价值在「语音」这一项上体现得最明显。用户面对的是**两条二选一的路**：  
云 ASR（填地址就能用，代价是音频传第三方）还是本地模型（音频不出本机，要下模型）。  
选了一条但没配全时，工厂会**静默退化成 Mock** —— 界面上看不出区别，  
只是识别结果是假的。所以自检反过来读「用户本来想走哪条路」，再指出那条路上缺的那一环：

| 用户的选择       | 实际状态             | 自检说什么                                  |
| ----------- | ---------------- | -------------------------------------- |
| 本地模型        | 包里没有语音库          | 「选了本地模型，但当前程序没内置语音库，实际走的是 Mock」+ 两条替代路 |
| 本地模型        | 库在，模型没下          | 「你要用的模型 large-v3 还没下载（已下载：tiny、small）」 |
| 本地模型        | 库和模型都在，引擎却是 mock | 「配置没能生效，保存一次设置即可」                      |
| 云 ASR       | 没填接口地址           | 「选了云 ASR 但没填地址，实际走的是 Mock」             |
| 云 ASR       | 地址填了             | ok                                     |
| 没选（还是 mock） | —                | 「语音还是 Mock，文字链路完全可用」+ 二选一引导            |

再往前一步是**语音链路实测**：录一段并转写，把设备列表、电平、引擎、耗时、  
识别文本逐步摊开。因为语音故障的现象永远是同一&#x53E5;**「没反应」**，  
但原因可能是没装采集库 / 找不到麦克风 / 麦克风被静音 / 环境太吵 /  
模型没下载 / 引擎还是 Mock —— **六种原因现象完全一样，解法完全不同**。  
这一屏就是用来把「没反应」拆成「第几步不行」的实测样本：

```
[OK  ] 设备: 找到 4 个设备（含 2 个回环）
[FAIL] 录音: 电平 RMS=0.0009，几乎是静音。设备选对了但没收到声音
       —— 检查麦克风是否被静音、音量是否为 0。
[OK  ] 引擎: local · 本地 faster-whisper · tiny · cpu/int8
[WARN] 转写: 没识别出任何文字
```

### 5.5 踩到的三个「不报错、只给错结果」的坑

这三个坑在 `docs/DESKTOP.md` 里各占一节（第 7~9 节）。  
它们的共同点：**不抛异常、不打印警告，只是安静地给你错误的结果** —— 所以最难发现。

#### 坑一：`available` 不等于 `ready`（自己造出来的 bug）


`ASREngine.available` 的语义是「这个引擎对象构造得出来」。对本地 whisper 来说，  
只要 `faster-whisper` 库在它就是 `True` —— **哪怕模型权重一个字节都没下载**。  
自检面板当初就用它判断，于是：

```
用户：选「本地模型 large-v3」→ 没下载权重
      → 自检显示绿色「已完成」
      → 用户以为配好了 → 录音后什么都没发生 → 不知道卡在哪
```

这**正是自检模块本身要消灭的那类问题**，结果它自己犯了。  
修法是把两个概念分开：

|             | 含义                | 用途        |
| ----------- | ----------------- | --------- |
| `available` | 引擎对象构造得出来         | 工厂选择实现类   |
| `ready`     | **现在拿一段音频进来就能出字** | 自检面板、界面状态 |

`LocalWhisperASR.ready` = 库在 **且** 权重已下载；再补一个 `not_ready_reason`  
说明差在哪。自检改用 `ready` 后，上面那条路径变成 `[warn]` +  
「模型 large-v3 还没下载（已下载：tiny、small）」+ 跳到语音设置页。

> 教训：**状态判断要问「能不能真的干活」，而不是「对象有没有造出来」。**  
> 这两者的差集，正是「看着配好了、用起来没反应」的全部来源。

#### 坑二：「int16 量级的 float32」——最阴的一个

测试脚本里写了：

```python
pcm = np.frombuffer(raw, np.int16).astype(np.float32)   # 忘了 / 32768
```

`dtype` 变成 `float32` 了，但**数值还在 ±32768**。而当时的 `transcribe()`  
只按 `dtype` 判断要不要归一化：

```python
if pcm.dtype == np.int16:
    pcm = pcm / 32768.0      # float32 直接跳过这一步
```

于是送进 Whisper 的波形被放大了 3 万倍：

```
实际说的：今天加班到十点，好累啊，你周末有空吗
识别出来：玩玩玩玩玩玩!
```

**不报错、不警告，只是给你错结果。**

排查过程里差点走错方向 —— 一度怀疑是 `tiny` 模型太弱。关键在于做了一次  
**英文对照实验**：英文同样乱，才确认是管线问题而不是模型能力问题。  
（如果只测中文，很容易得出「中文就是不行」的错误结论。）

修法是 `asr/base.py` 的 `to_float_mono()`：不只看 `dtype`，还用**峰值兜底** ——  
`float32` 但峰值 > 1.5 的，一律按 int16 量级处理（> 256 除以 32768，否则除以 127，  
兼容 int8 量级的输入）。修完后三种输入形式输出**逐字一致**（见 5.7 实测表）。

> 教训：跨模块传数组时，「**dtype 对**」不等于「**量纲对**」。  
> 接口契约要写清值域，并且用**数值特征做兜底校验**，而不是只信类型标签。

#### 坑三：`soundcard` 是两条语音路线的公共依赖

写打包配置时的第一反应是「录音库只有本地转写才需要，放进 `WITH_ASR` 分支吧」。**这是错的** ——  
走云 ASR 时同样要先用 `soundcard` 抓系统回环/麦克风，再把音频 POST 给云端。  
少了它，**标准版的语音会整条废掉**。两类包都必须带。

另外它的出现位置是**函数内延迟导入**（为了「没装也能跑」）：

```python
def _soundcard():
    try:
        import soundcard as sc   # 函数内 import
    except ImportError:
        return None
```

PyInstaller 的字节码分析**确实**能扫到函数内的 import，所以它「碰巧」被打进去了。  
但这是运气 —— 哪天把导入挪进 `try/except` 或换成 `importlib` 就会静默丢包，  
而症状是「打包版能启动，但一录音就报没装库」。所以 spec 里显式声明了隐藏导入。

> 教训：**「碰巧能工作」和「保证能工作」之间要留一道显式声明。**  
> 靠工具的实现细节生效的东西，写下来当注释，别当契约。

### 5.6 与另一个 agent 的工作合并

推送时发现远程多了 9 个提交 —— 是另一个 agent 从同一个基点分头做的一整套工作：

- `wingman.cmd` + `scripts/bootstrap.ps1`：**源码侧**零配置启动器（自动建 venv、  
  按锁定版本装依赖、调 preflight、起服务、开浏览器）
- `scripts/preflight.py` + `--doctor`：启动前自检
- `GET /api/health/details`：配置来源溯源（每个键的值到底来自 runtime/env/dotenv/default）
- `requirements.lock.txt`：25 个精确版本
- 4 份文档（QUICKSTART / MODELS / TROUBLESHOOTING / CHANGELOG）、38 项测试
- 代理绕过（`_trust_env_for`）与中文 Windows 编码处理

**两边目标相同、路径不同**：他要的是「源码装起来不费劲」，我要的是「连 Python 都不用装」。  
所以合并的重点不是「谁覆盖谁」，而是**把两条路讲清楚、让它们共存**。

冲突只有 3 个文件（`.github/workflows/ci.yml`、`api/__init__.py`、`README.md`）。  
前两个是机械合并，第三个是真问题 —— 两边都重写了「快速开始」，语义重叠但不冲突。  
最后的处理是：

- 保留他的「快速开始（3 步）」作为 TL;DR
- 新&#x589E;**「三种跑法：怎么选」**，把 `wingman.cmd` / `WingMan.exe` / 手动源码  
  摆在一张表里，并指出**唯一的分水岭是「这台机器愿不愿意装 Python」**
- 新增「排错从哪下手」，明确两个自检入口各自的命令与产物路径

**顺带决定了两套自检不合并。** 检查项本来就不一样：  
`--doctor` 查 Python 版本 / 位数 / venv / 依赖锁一致性（这些在 exe 里根本不存在）；  
`--check` 查资源路径 / 可写目录 / WebView2 / 模型权重（这些在源码模式下不成为问题）。  
强行合一会让两边都要塞一堆「如果是另一种形态则跳过」的分支，反而更难维护。  
所以保持两个入口 + 在文档、前端、`--check` 输出里互相指路。

> 可复用的经验：两个 agent 并行做同一件事时，**价值最高的产出往往不是代码，是「怎么让用户不被两条路搞晕」**。  
> 合并时先问「用户面对几个入口、他知不知道该选哪个」，比先 diff 代码更有效。

## 六、第三轮：把打包版真正跑一遍

前两轮的验证停在「装上能开、数据不丢、接口通」。这一轮补的是更硬的一条：  
**核心功能在冻结环境里到底能不能跑通。**

结论是能跑通，但先跑出了三个问题 —— 而且三个都属于「只做功能测试永远看不见」的那类。

### 6.1 这轮为什么能挖出问题：上一轮的清单漏了一整条路径

上一轮对打包版的语音验证，验的是 `--asr-test` 能加载模型并出字。但  
**加载已有模型**和**按需下载模型**是两条完全不同的代码路径：

| 步骤       | 实际走的东西                              | 上一轮验了吗   |
| -------- | ----------------------------------- | -------- |
| 加载已下载的模型 | `faster_whisper` 读本地目录              | ✅ 验了     |
| 从网上下载模型  | `huggingface_hub` + 镜像 + 写磁盘 + 校验落盘 | ❌ **漏了** |

而「模型按需下载、带真实进度与剩余时间、可切国内镜像」是写在 CHANGELOG 和  
界面上对用户的承诺。**承诺了却没验，等于没做。** 所以这轮第一件事就是补这条：  
在打包版里真的下载一个当前没装的模型。

（顺带一个方法论：验证清单要按**代码路径**列，不能按**用户功能**列。  
按功能列会写出「语音能用」这种条目，它掩盖了内部其实有三条路径、  
你只走通了其中一条。）

### 6.2 三个问题的全景

| # | 问题               | 只做功能测试能发现吗  | 现象                         | 处理                   |
| - | ---------------- | ----------- | -------------------------- | -------------------- |
| 1 | 中文转写偶尔出繁体        | 只有跑真实模型才看得到 | `base` 把「10点…吗?」写成「10點…嗎?」 | 加简体 `initial_prompt` |
| 2 | 下载失败时的提示把人带偏     | 只在真出错时才看得到  | 「缺组件」被翻译成「重试 / 勾国内镜像」      | 新增「缺组件」判断分支          |
| 3 | `hf_xet` 白占 9 MB | **不能**      | 只有量了体积、并追问「它为什么在这儿」才会发现    | spec 里加 `excludes`   |

第 3 个最典型：它对功能零影响，所以**任何功能测试都不会报警**。  
这类问题只有两个入口能发现 —— 量体积，或者读构建配置时多问一句。

### 6.3 一次「差点改错」的排查：把「静态分析看不见」的范围搞错了

这段值得单独记，因为**我差点基于一个错误的推断去改构建配置**。

起因是查体积时注意到：标准版里根本没有 `huggingface_hub` 这个目录，  
却单独躺着一个 `hf_xet`（9.06 MB）。而本地转写的「按需下载模型」正是靠  
`huggingface_hub` 实现的 —— 顺着想下去就是：**打包版的下载功能是坏的**。

证据看起来也很足：`backend/app/asr/models.py` 里那行  
`from huggingface_hub import snapshot_download` 写在函数**内部**，  
而项目文档里早就有一条「uvicorn 的实现类是运行时按字符串挑的，静态分析看不见」。  
两件事一叠加，我很自然地得出了「函数内的 import 也看不见 → 这个模块没被打进包」，  
并准备去 spec 里补一个 `hiddenimports`。

改之前我决定先核对一下。方法是拿 PyInstaller 自己的归档读取器，  
把 exe 里真正的模块清单列出来：

```python
from PyInstaller.archive.readers import CArchiveReader, ZlibArchiveReader
r = CArchiveReader("dist/WingMan-full/WingMan.exe")
open("pyz.pyz", "wb").write(r.extract("PYZ.pyz"))   # 模块归档在里层
names = sorted(ZlibArchiveReader("pyz.pyz").toc)    # 权威清单
```

结果是：`huggingface_hub` 有 **147 个子模块，本来就在包里**。

结论：**推断错了，而且错在一个很值得记的地方。**

> **「静态分析看不见」只对「模块名是运行时拼出来的」成立，  
> 不要推广到函数内写的 `from X import Y`。**  
> PyInstaller 用的是字节码分析，函数内的 import 照样能追到。  
> 唯一追不到的是 `importlib.import_module(name)` 这种 —— 也就是 uvicorn 那一类。

这次排查还顺带踩了另外两个坑，都是「工具本身在骗你」：

- **不能用 `grep` 二进制里的字符串来判断模块在不在包里。** 我一开始就是  
  这么干的，而且在 exe 里 grep 到了 `huggingface_hub`（3 次），差点当成  
  「本来就在」的证据。可那几次命中来自 `models.py` 里讲解 Xet 的  
  **文档字符串** —— 字符串会被打进去，模块不一定。反过来，模块真被打进去时  
  PYZ 内容是压缩的，grep 又可能什么也搜不到。**两个方向都会给假结论。**
- **我的第一次核对脚本自己写错了。** 我写的是  
  `txt in acc`（`acc` 是字符串**列表**），这是精确成员判断，不是子串匹配。  
  于是三个修复全部报 `False`，看起来像「重建没生效」，实际是探针错了。  
  改用子串匹配后三项全为 `True`。

三个坑叠在一起，教训是同一句：**核对「东西在不在」时，要用权威接口，  
并且先拿一个已知为正的样本校验你的探针。**

### 6.4 一个把我自己坑到的验证陷阱：连到了旧进程

看清 6.3 之后，下载到底能不能用还没验证。我起了打包版服务，`curl` 了  
`/api/health`，结果看到一组自相矛盾的东西：

```
"db": "...\wingman\backend\data\wingman.db"      ← 这是**仓库里**的源码数据目录
providers: asr -> mock                              ← 而我起的是**完整版**，ASR 应该是 local
```

同时后台任务显示进程**已经退出**。查下来原因是：

- 机器上还留着**三个早前会话遗留的源码模式服务**（端口 8791 / 8793 / 8797）；
- 打包版为了做单实例，启动时会探测目标端口，发现已有 WingMan 就**直接复用、不起新服务**；
- 于是我新起的 exe 静默退出，而我的 `curl` 打到的是**那个旧进程**。

这不是产品的 bug（日常使用里「已经开着就别再起一个」是对的），  
而是**验证方法**的 bug。记下两条以后照做：

> 1. 手工验证时**换一个没人用的端口**，别用默认端口。
> 2. 核对响应里的**数据目录是不是你预期的那一个** —— 这是确认  
>    「你连的是自己刚起的那个进程」最省事的判据。

顺手也修了一句会加重这个陷阱的日志：原来无论什么模式都印  
「检测到已有 WingMan 在运行，**直接打开界面**」，但 `--no-window` 下其实不会打开任何界面。  
现在会说实话。**日志不准确与日志缺失同样有害 —— 它会让你在错误的方向上多绕一圈。**

### 6.5 修复一：中文转写不再吐繁体（用户可见）

在打包版里下载 `base` 并转写同一段中文，得到：

```
[文本] 今天加班到10點,好累呀,你周末有空嗎?      ← 繁体
```

内容是对的、字形是错的。用户不会认为「模型倾向繁体」，  
只会认为**这软件认错字了** —— 对一个中文优先的产品，这是硬伤。

处理方式是给中文转写加一段简体 `initial_prompt`。实测对比：

| 规格   | 无提示词                         | 带简体提示词                       |
| ---- | ---------------------------- | ---------------------------- |
| tiny | 今天加班到10点好累呀你周末有空吗            | 今天加班到十点,好累呀,你周末有空吗?          |
| base | 今天加班到10**點**,好累呀,你周末有空**嗎**? | 今天加班到10**点**,好累呀。你周末有空**吗**? |

`base` 的置信度也从 0.735 升到 0.787。

副作用要说清：加了提示词会改变 beam search 的路径，个别用词会有出入  
（`tiny` 会把「10点」写成「十点」—— 同样正确）。这个代价可以接受。

**为什么不用繁简转换库？** 转一个字形而已，引个库不是更省事吗？  
因为转换库只是**事后补救**，而提示词是**从源头不让模型往繁体跑**，  
还能顺手把语气定在普通话上。而且少一个依赖就少一份体积和许可问题。

另外一个细节：只在**明确是中文**时加。`auto` 模式本来就是在做语种识别，  
此时塞一段中文进去会把语种判断本身带偏 —— **宁可偶尔出繁体，也不要认错语种。**

### 6.6 修复二：错误话术不能把人带进死胡同

这一个是 6.3 那次排查的副产品，但价值不低。

模型下载失败时，代码会调 `_explain_error()` 把底层报错翻译成人话。  
它有网络超时、401、磁盘满等分支，最后有一句兜底：  
「可以先重试一次；一直失败的话，勾上「使用国内镜像」或换个小一号的模型。」

问题在于它**没有「缺组件」这一类**。也就是说，如果哪天真有模块没打进包，  
用户会看到 `ModuleNotFoundError` 被翻译成「重试 / 换镜像」——  
**而镜像补不上一个没打进包的模块，这是个永远修不好的方向。**  
更糟的是用户不会想到来反馈，只会放弃。

现在新增了这类判断。关键细节是**它必须排在所有网络关键词之前**：  
模块名有可能碰巧命中下面的关键词（比如名字里带 `connection`），  
排在后面就会被误判成网络故障、又绕回那条死胡同。

> 这是这个项目反复出现的一个模式：**「没有建议」不可怕，  
> 「看起来合理但方向错误的建议」才可怕。** 前者用户会来问，后者会让用户默默流失。

### CI 设计

`.github/workflows/ci.yml`，matrix 覆盖 **Python 3.11 / 3.13**。第一轮是四步，  
第二轮合并后扩到六步（加粗的是新增的）：

2. 后端 `compileall` 语法检查
3. **单元测试 `pytest tests/ -q`（53 项）**
4. 端到端冒烟测试（Mock Provider，**不需要任何 API Key**）

> 第 5 步是个很值得抄的做法：GBK 控制台只能在中文 Windows 本机验，  
> Linux 的 CI 抓不到；那就退一步，守住能在 CI 里守住的两件事 ——  
> 调用方不设任何编码变量时能跑通、输出流连中文都表示不了时必须可读降级。  
> **测不了全部，就把能测的那部分固化下来，别因为「测不全」而一条都不测。**

### 它第一次运行就抓到了一个本地漏掉的 bug

现象：`test_smoke.py` 里「抽到含『猫』的事实」这条断言在 CI 上失败，**本地一直是绿的**。

第一反应是「Linux 和 Windows 有差异」，实测**与平台无关**：

- 用不同 `PYTHONHASHSEED`（0 / 7 / 13）连跑三次，结果完全一致 → 排除哈希随机化
- 真因是流程问题：改完 `mock.py` 后只跑了 `e2e_check.py`（它不检查事实抽取），  
  **没有重跑冒烟测试**，本地结果还停留在改坏之前

### 根因：三层叠加，每层单独看都「合理」

| 层       | 问题                                                                                                           | 修复                                                                           |
| ------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| `store` | facts 唯一键 `(chat_id, subject, key)` 把「喜欢」这类一对多关系建模成字典。配合 `INSERT OR REPLACE`，「喜欢猫」被后来抽到的「喜欢火锅」**静默覆盖**，不报任何错 | 唯一键改为 `(chat_id, subject, key, value)`                                       |
| `store` | SQLite 不支持修改约束，老库需要迁移                                                                                        | 新增 `_migrate_facts_unique()`：读 `sqlite_master` 原始 DDL 判断版本 → 重建表。数据保留、重复执行幂等 |
| `mock`  | 同一 key 只保留置信度最高的 1 条（且用**严格大于**比较），丢掉同类不同内容的事实                                                               | 按 key 分组保留前 4 条；单字过滤从「长度 < 2」一刀切改为按键白名单                                      |

修复效果（真实数据）：

```text
[peer] 喜欢   = '吃火锅'   conf=0.75  ev=12
[peer] 喜欢   = '猫'      conf=0.75  ev=27   ← 之前被整条覆盖
```

### 三条可复用经验

1. **静默覆盖比报错危险得多**。数据模型错了，上游改多少都没用 ——  
   而且这类错误不抛异常，只安静地给你一个缺了一半的画像。  
   改 schema 唯一键时必须同时写迁移，且迁移必须幂等。
2. **「本地全绿」≠「CI 绿」，但原因常常不是平台**，  
   而是改了公共代码却只跑了部分测试。CI 的价值不是「更严格」，而是「不会忘记跑」。
3. **定位跨环境不确定性的手法**：固定 `PYTHONHASHSEED` 多跑几次。  
   结果一致即可排除随机性，问题必然在确定的代码路径上。

## 九、下一步建议

完整路线见 `docs/ROADMAP.md`（三阶段，每项标注要改哪个文件）。

### 第一优先：Prompt 调优（没变）

> 其他所有功能都建立在"模型给出的分析够准、建议够好"这个前提上。  
> 如果分析是废话、建议是套话，再漂亮的前端和再快的语音都没有意义。

方法：从真实记录里挑 20 个已经回复过的片段，  
把"对方那句话说出口之前"的状态喂给引擎，  
看它给的选项里有没有你当时真选的那条。

**命中率超过 50%，就说明它真的在理解，而不是在说场面话。**

第二轮打包没有改变这条建议的优先级 —— 桌面化解决的是「能不能用上」，  
Prompt 质量解决的是「值不值得用」。前者做完了，后者还没开始。

第三轮也没有改变它。第三轮修的三件事（繁体、错误话术、体积）都属于  
「让已有的东西不出错」，**没有一件让建议本身变得更聪明**。  
现在的分析仍然是 Mock 规则引擎产出的 —— 流程完整，内容空洞。  
**这是当前项目最大的缺口，也是唯一一个「不填 API Key 就无法推进」的缺口。**

### 第二优先：把这次没验到的地方补上

诚实记一下**累计没有验证**的东西，免得日后误以为验过了：

| 没验的                                         | 为什么                             | 怎么补                                  |
| ------------------------------------------- | ------------------------------- | ------------------------------------ |
| 云 ASR 实际效果                                  | 手里没有可用的 ASR API Key             | 填一家 OpenAI 兼容的 ASR 服务，用「语音链路实测」跑 5 秒 |
| 真实通话采集                                      | 需要真的在通话中双通道采                    | 打微信语音，两路都开，看字幕是否分离正确                 |
| `small` / `medium` / `large-v3` 在**打包版**里转写 | 第二轮只验过下载与文件结构；第三轮补了 `base` 的全链路 | 换显卡机器，或直接跑 `scripts/asr_bench.py` 对比 |
| 另一台没装 Python 的机器                            | 本机就是开发机                         | 把 `dist/WingMan` 拷过去双击               |
| macOS / Linux 桌面                            | 打包只做了 Windows                   | 无计划；源码路线本身是跨平台的                      |
| 打包版的 `--no-webview` 等非默认组合                  | 只验了标准版和 `--with-asr`            | —                                    |

第三轮补上的（原先在这张表里）：**模型按需下载**、**`base` 规格在冻结环境里的  
加载与转写**、**打包版整体跑 `e2e_check.py`**。补它们的方法都是同一句：  
**按代码路径列清单，而不是按用户功能列。**

另外有两个**结构性问题**值得在下一轮解决：

1. **两条自检路径的信息不同步**：`--doctor`（源码侧）和 `--check`（打包版）  
   各有一份检查逻辑和文案。现在靠文档和前端指路，长期看会漂移。  
   彻底的做法是抽一个**平台无关的「环境事实采集层」**，  
   两个入口共用它、只各自决定「怎么呈现」。这次没做，因为改动面太大。
2. **前端仍是 1600+ 行的单文件**，加了自检页和语音面板之后更臃肿了。  
   见 ROADMAP 阶段 2。
3. **（第三轮新增）构建产物体积没有自动化门禁**。`hf_xet` 那 9 MB 是靠人  
   盯出来的 —— 说明「体积回归」目前完全靠自觉。低成本做法是在 CI 里加一条：  
   构建后体积超过阈值就报警（而不是失败，避免噪声）。

本地则要先下模型（**音频一帧都不出本机**）。  
先跑 `scripts/asr_bench.py` 看看该选哪一档模型。

## 十一、第五轮：界面重做，以及两个「不是看起来那样」的真 bug

用户测试后的反馈有四条：前端太 AI 味、云大模型获取不到（要求先搞定 DeepSeek 最新模型）、
字体排版挤在一起很乱、新手友好不够。按「先调研同类项目再动手」的要求，
看了 chatgpt-on-wechat、wechat-bot、ChatBox、Cherry Studio 的做法，
再回到自己的代码里找根因。

结论是：四条里，**有两条的根因和症状描述完全不在一个地方**。

### 11.1 「云大模型获取不到」= 预设里的模型名过期了

界面上「DeepSeek」那个一键预设，填的模型名是 `deepseek-chat`。

查 DeepSeek 官方文档后确认：**`deepseek-chat` 和 `deepseek-reasoner` 已于
2026-07-24 被永久下线**，调用直接返回错误，没有宽限期、没有软跳转。
当前可用的模型名是：

| 模型名 | 对应 | 定位 |
|---|---|---|
| `deepseek-flash` | DeepSeek-V4.1-Flash | 快、便宜，日常聊天够用 |
| `deepseek-v4-pro` | DeepSeek-V4-Pro | 推理更强，单价约 4 倍 |

Base URL 仍是 `https://api.deepseek.com/v1`（这个没问题）。

也就是说，用户照着界面上的预设点一下，**必然连不上** —— 而界面上完全看不出
「这个预设已经过期了」。这是典型的静默失效：服务商下线模型不会通知你，
界面上也没有任何东西会过期。

修了三处：

1. 预设改成当前可用的 `deepseek-flash` / `deepseek-v4-pro`，点一下可在两者间切换；
2. 新增**退役模型名检测** —— 读到（或存着）已下线的名字，当场弹提示并给一键替换按钮。
   这同时也帮到了「以前配过、现在突然连不上」的老用户；
3. 其他服务商（通义、Kimi、硅基流动）补上「模型名时有更新，点『拉取模型列表』更准」
   的说明 —— 这类名字的保质期都不长。

另外，**「测试连通」失败时不再只丢一句 HTTP 错误**。新手拿到 `HTTP 404` 是没法
自己往下走的，现在会按状态码分别给出「可能是什么原因 + 下一步点哪」：

| 现象 | 提示 |
|---|---|
| 401 | API Key 不对，去后台重新复制（注意别漏字符、别填到 Base URL 那格） |
| 404 | Base URL 写错：应以 `/v1` 结尾，且不要带 `/chat/completions` |
| 提到模型 | 模型名不对或账户没开通；用「拉取模型列表」挑 |
| 429 | 额度用尽或太频繁 |
| 超时 / 网络 | 检查代理是否拦了本机请求；或先切 Ollama 本地模型绕过网络 |

### 11.2 「字体排版挤在一起很乱」= 同名 CSS 类互相覆盖

这一条最值得记。第一反应是字号太小、行距太紧，但改字号解决不了 ——
因为**根因根本不是字号**。

真正的问题：`.sub` 这个类名被两个模块占了 ——

- 各页标题下的**副标题段落**用它；
- 通话页的**字幕行**也用它，并且定义了
  `display: grid; grid-template-columns: 66px 1fr`。

CSS 后定义者胜。于是**每个页面的副标题都被压成了 66px 宽的一列**，一个词一行，
看起来就是「字全挤在一起」。

两处单独看都是对的，也不报任何错 —— 只有把页面真的渲染出来才看得见。
这也是为什么这次必须做截图验证，而不是读完代码就下结论。

修法：字幕行改名 `.cap`。并加了两条守卫测试
（`backend/tests/test_frontend_assets.py`）：

- 禁止同一份 CSS 里出现两个顶层同名类规则（要复用就用逗号合并选择器）；
- 禁止预设里出现已下线的模型名。

### 11.3 去 AI 味：把「AI 生成的后台面板」改成「正常的桌面工具」

「AI 味」在视觉上其实有很具体的特征，这一版全踩了：深色底 + 紫蓝渐变、
装饰性符号堆砌（`◎ ◈ ↧ ◉ ✚ ⚙`）、密集的小字号、术语化的英文标签。

重做的方向参考了 ChatBox —— 它的定位是「UI 偏向传统即时通讯软件，
符合大众使用习惯」，这正是要的效果：

- **配色**：深色 + 渐变 → 浅色中性灰阶 + **单一强调色**（靛蓝 `#2f6fed`）。
  强调色只有一个，不再到处发光。
- **字号**：原来混用了 11 / 11.5 / 12 / 12.5 / 13 / 13.5 / 14 / 15 / 17 / 19 共十档，
  现在收成 **12 / 13 / 14.5 / 15.5 / 21** 五档，正文行高统一 1.7。
- **间距**：走 8 / 12 / 16 / 24 / 32 的节奏，卡片内边距给足。
- **图标**：混用的符号字符换成统一线性 SVG，颜色跟随状态。
- **语义色**：统一为「浅底 + 中色字 + 同色描边」，不再是深色发光。

### 11.4 新手友好

借鉴同类项目的共同点：**新手第一屏需要的不是功能入口，而是「我现在缺什么、下一步点哪」**。

- 指挥台顶部加「三步上手卡」：接上大模型 → 导入聊天记录 → 开始分析。
  每个未完成项直接给按钮跳到对应页面；两步都齐之后**整块自动收起**，不打扰已配好的人。
- 空状态、错误提示统一成「为什么 + 怎么办」的结构。
- 记忆页的事实归属标记由 `peer` / `me` 显示为「对方」/「我」——
  不该让用户去猜 `peer` 是谁。

### 11.5 怎么验证的（方法本身也值得记）

本机没有 `agent-browser`（要下 500MB Chromium），改用**系统 Chrome 无头截图**。
两个坑，缺一个就挂：

1. **页面里的 SSE 长连接会让截图挂死。** `EventSource` 是持久连接，
   而 `--virtual-time-budget` 要等网络空闲 —— 结果永远等不到，进程卡死 2 分钟以上。
   为此加了一个 `?nostream=1` 开关（正常访问不带这个参数，行为完全不变）。
2. **`--force-device-scale-factor=1` 不能省。** 否则系统 DPI 缩放会让
   `--window-size` 与实际 CSS 视口对不上（设 1500，实际视口只有 1080）。

顺带加了 `?view=<页面名>` 深链接，可以直接跳到某一页。

### 11.6 本轮之后

- 测试 **61 → 66 通过**（新增 5 条前端守卫）。
- 文档同步：README（加了界面截图）、CHANGELOG、`docs/MODELS.md`、`docs/DESKTOP.md` 第 14 条。
- 截图配图放在 `docs/images/`。

**没有重新打包 exe、也没有更新 Release** —— 线上 v0.2.0 里仍是旧界面。
重发版受限于本机 `github.com` 约 13KB/s（上一轮实测 91MB 传了 22 分钟只到 16%），
需要先确认再动。

> **该事项已于第十二节完成。** 而且这次网络完全不同：走本地代理（7897），
> 91.5MB 的完整版附件 **46 秒**传完。同一个「网络慢」的结论，隔一天就不成立了 ——
> 值得记一笔：把一次实测的速率当成环境的固有属性，是很容易犯的错。

## 十二、第六轮：推上 GitHub，并重新发版（v0.2.1）

上一节结尾留了一件事没做：**线上 Release 里的 exe 还是旧界面**。
这一轮的指令只有一句 ——「你推到 github」—— 做完正好把这件事结了。

### 12.1 先推代码，再把 exe 一起发了

`git push` 推上去的是 `6868b23`（界面重做那个提交）。
但如果只推代码，从 Release 下载到的新手拿到的仍是旧界面 ——
界面重做等于只对源码读者可见。所以接着把 exe 也重发了一版。

**没有覆盖 v0.2.0，而是发了 v0.2.1。** 已发布的 Release 刻意不覆盖：
它的附件已经被下载过，校验和也印在说明书里，覆盖会让校验和失效、
也会让「我下的是哪个包」说不清。`make_release.py` 里就是这么写死的 ——
遇到已存在的 tag 直接拒绝，而不是「顺手更新一下」。

### 12.2 版本号又漂移了，这次是发布脚本自己

升版本号要同步四处（`__version__` / CHANGELOG / README / 发行说明），
`test_version.py` 已经在盯了。但这轮核对时发现**第五处**：

```
scripts/make_release.py:  ap.add_argument("--version", default="0.2.0")
```

这个脚本存在的全部意义就是「别让版本号漂移」，它自己的默认值却会第一个过期，
而且**过期得静默** —— 不加 `--version` 就会打出一个版本号与代码不符的包，
正是它当初要防的那件事。

改成从 `backend/app/__init__.py` 里正则读取。**默认值不该是同一个事实的另一份副本。**

### 12.3 第三个静默 bug：说明书把一个路径写错了

打包前逐条核对文档时发现：自检报告实际写在**数据目录**
`%LOCALAPPDATA%\WingMan\logs\selfcheck.txt`，但 zip 里的使用说明、README、
发行说明三处都说它写在「程序目录」—— 而程序目录下压根没有 `logs\` 这个文件夹。

后果不是崩溃，而是**用户按说明去找，找不到那个文件**，然后得出
「自检根本没跑 / 这软件坏了」的结论。功能是好的，说明书把人带沟里了。
**一个指错位置的文件名，和功能坏了给人的感觉是一样的。**

修的过程本身有个小插曲：加完守卫测试（文档里提到 `selfcheck.txt` 时，
该文件名之前不能出现「程序目录」），第一次跑就被自己的记录绊倒 ——
我在踩坑记录里**引述**了错误原文，而测试分不清「引述」和「真的指错」。
最后改成转述。这条测试确实在干活。

### 12.4 重新打包的理由：产物必须对得上确切的源码

第一次打包完成后，我又改了 `desktop.py` 的一段文档字符串 —— 它在包里。
按「只差一段注释，无所谓」放过，就等于发布的产物与源码有一次说不清的偏差。

于是重新打了一遍。**这个项目的卖点之一就是「产物可追溯」，为省 10 分钟留下
一次说不清的偏差，不划算。** 更好的做法本来应该是：所有代码改完再打包。

### 12.6 本轮的三条教训

1. **「网络慢」是一次实测，不是环境属性。** 上一轮同样的上传卡在 13KB/s，
   这一轮走代理 46 秒传完 91.5MB。不要把自己的单次观测当成世界的常量。
2. **守卫测试写下来就会开始抓人，包括抓写它的你。** 引述错误文本同样会触发
   针对该文本的守卫 —— 这不是误报，而是提醒：文档里的每一处文本都会被当真的读。
3. **顺序也是工程的一部分。** 「先打包、后改代码」这件事没有任何一个测试能拦住，
   只能靠流程自觉：**改完了再打包，不然就重打。**
