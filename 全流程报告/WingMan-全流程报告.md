## 一、原始需求与四个岔路口

做一个 GitHub 项目，三个能力：

1. **接入大模型语音通话识别**
2. **记忆微信 / QQ 聊天记录并分析**
3. **通过识别回复进行指导回复** —— 它给选项、人来选

期望效果：选中和某个人的全部 QQ 聊天记录 → 让大模型记忆 → 给出聊天规划 →
对方回复后点击启动 → 识别后给出对此时对方的分析、几个可选回复、并实时推测聊天走向。

### 澄清后确定的四个岔路口

| 问题 | 选择 |
|---|---|
| 聊天记录来源 | QQ + 微信**都要**，做成插件式适配器 |
| 语音场景 | **实时监听 + 事后转写都要** |
| 大模型接入 | 云端 API 与本地 Ollama **可切换** |
| 交付程度 | 完整方案文档 + **可运行脚手架**，便于持续迭代 |

### 第二轮的三个岔路口（做软件，不是做脚手架）

第一轮交付的是「能跑通」；但**能让别人也用上**是另一回事。

| 问题 | 选择 | 备注 |
|---|---|---|
| 先动哪一块 | **直接打包 .exe** | 当时不确定 .exe 适不适合，先试 |
| 最终整合形态 | **独立 .exe 桌面软件** | 双击打开，像个正经软件 |
| 语音走哪条路 | **两条都留，向导里让我选** | 云端省事 / 本地隐私，场景不同 |

关于「.exe 适不适合」的判断是：**可行，但它是「问题放大器」**。详见第六节。

### 后续轮的岔路口（都是「不可逆操作，先问清再动」）

| 轮次 | 问题 | 答复 |
|---|---|---|
| 第四轮 | 「对象」是否允许多人合并成一个？ | 允许，但**只在确定无歧义时自动接住**，否则让用户显式合并 |
| 第五轮 | 用户手写的人物设定，AI 整理时能不能覆盖？ | **默认只填空，不动手写稿** |
| 第七轮 | 0.2.0 要不要保留安装包？ | 保留，只是换个名字 |
| 第七轮 | commit 邮箱要不要重写历史？ | **要，彻底清** |

### 必须记住的不变量（踩了会静默出错）

1. **chat 必须有人**：`upsert_chat` 末尾强制 `ensure_person_for_chat`。新写入路径漏了这条，人物列表就是空的。
2. **chat_id 生成规则有两套**：导入 `{platform}-{slug}-{md5[:6]}`、采集 `{client}:{account}:{peer_key}`。**不要新造第三套。**
3. **改 platform 时不要跟着改 chat_id** —— chat_id 是幂等键与游标的依据。

## 三、六个关键设计决策

这部分是整份报告里最值钱的内容 —— 都是**有代价的取舍**，不是教科书结论。

### 1. 双通道采集 = 天然的说话人分离

语音通话时：

- **系统回环（loopback）捕获到的是对方的声音**
- **麦克风捕获到的是自己的声音**

所以只要同时开两路采集，就白得了说话人分离的结果，**不需要跑声纹识别或说话人聚类模型**。

这是整个语音方案能成立的地基。代价是需要 `soundcard` 这类能抓回环的库，
且必须正确识别系统的默认播放设备。

> ⚠️ **这个方案在 v0.1.1 被整体撤下了**（原因见第八节「语音为什么撤下」）。
> 保留在这里是因为它是本报告里唯一一个「技术成立但产品上放弃」的完整案例。

### 2. 不让模型给自己打分

最初的想法是让模型给每条候选回复打 0~10 分。实测不可行：
**模型对自产内容的自评普遍偏高，且方差极小**，四条回复经常都是 8.5、8.7、8.6、8.4，排序毫无意义。

改用本地可解释启发式，四个维度：

| 维度 | 判据 |
|---|---|
| 自然度 | 长度合理性（3~25 字最佳）、语气词、AI 腔词表命中、书面语 |
| 共情温度 | 是否呼应对方提到的话题、是否含情绪回应词、对方情绪强度高时未接住则扣分 |
| 目标推进 | 行动动词、提问引导、与用户长期目标是否一致 |
| 风险 | 雷区命中、感叹号过多、绝对化表达、与对方原话重合度过高（复读） |

```
total = 1 + 9 × clamp(0.30·自然 + 0.25·共情 + 0.30·推进 − 0.35·风险)
```

**关键在于输出 `score_notes`**：不只给分，还要说明「− 命中雷区「宝贝」」。
用户看得懂分数是怎么来的，这比一个孤零零的 7.2 有用得多。

### 3. 推演概率不让模型直接编

让模型输出 `58%`、`27%`、`15%` 这种数字是不可信的 ——
它对概率的标定能力远不如对「大概率/有可能/不太可能」的定性判断。

做法：提示词里只允许填 `likely / possible / unlikely`，
代码映射为 `0.62 / 0.26 / 0.12` 再按实际分支数归一化。

**并且推演结果必须带免责声明，前端要显眼展示。**
把一个语言模型的情景模拟包装成预言，是在骗用户，
而用户会据此做出真实的、可能有代价的决策。**这条线不能越。**

### 4. 观测与推测必须分开

分析结果里：

- `signals` = **观测**（消息长度、标点、表情数、有无提问、回复节奏）
- `subtext` = **推测**（她其实在想什么）

前端用不同颜色分开展示，观测项可以点开看到原文。

这么做的目的不是好看，是**降低用户对模型的盲目信任** ——
而盲目信任一个会幻觉的模型，在人际关系这个场景里代价很高。

### 5. 事实层全量注入，检索层动态召回

记忆分三层：

| 层 | 存量 | 进 Prompt 的方式 | 理由 |
|---|---|---|---|
| L1 事实 | 几十条 | **全量** | 几百 token，但漏掉「她讨厌被叫宝贝」代价极大 |
| L2 摘要 | 若干 | 最近 3~5 条 | 长期脉络 |
| L3 检索 | 上万条 | 按当前消息动态召回 top-30 | 细节与当时语境 |

L1 全量是关键判断：**漏掉的代价和多余的成本完全不对称。**

### 6. 三个工厂都保证「降级可跑」

`build_llm` / `build_embedder` / `build_asr` 的契约是**永远返回可用实例**：

- 配了云模型 → 用云端
- 配了 Ollama → 用本地
- 都没配 → Mock Provider，`import` 后立刻能跑完整链路
- Embedding 没配 → 本地字符 n-gram 哈希向量（不是玩具，中文里字面重合和语义相关高度相关）

这么设计是因为：**第一次跑起来时看不到东西的项目，很难被继续做下去。**
Mock 的价值在于让人先看清楚交互流程对不对，再决定要不要投入配置真实模型。

> 但这条契约也埋了一个雷：**静默退化成 Mock**（见第七轮「坑一：available 不等于 ready」）。

## 四、关于「自动回复」的立场

需求里提到了自动回复。项目**没有实现无人值守的代聊**，只有「建议 + 一键复制」。

理由写在 `docs/COMPLIANCE.md`，核心是三条：

1. **对方以为在和你交流。** 这是欺骗，不是效率工具。
2. **关系的价值来自真实。** 用模型代聊得到的「好感」是假的，你也没从中成长。
3. **一旦暴露，信任崩塌。** 这是不可逆的损失。

所以 API 层面的形态是：

```
模型出候选 → 你选择 → 落到你的输入框 → 你确认后发送
```

决策权和责任都留在人手里。
`engine/prompts.py` 里的红线段落也写死了：禁止操纵/PUA、禁止谎报身份、禁止纠缠。

### 5.2 CI 设计

`.github/workflows/ci.yml`，matrix 覆盖 **Python 3.11 / 3.13**。六步（加粗的是第二轮新增）：

1. 安装依赖：`requirements.lock.txt`（25 个精确版本，与本地启动器同一份）+ `requirements-dev.txt`
2. 后端 `compileall` 语法检查
3. **单元测试 `pytest tests/ -q`**
4. 端到端冒烟测试（Mock Provider，**不需要任何 API Key**）
5. **编码防护：无编码环境变量 + 强制 ASCII 输出流两种场景下都不得崩溃、不得产生乱码字节**
6. 前端 `index.html` 内联 JS 语法检查（node `vm.Script` 编译）

> 第 5 步是个很值得抄的做法：GBK 控制台只能在中文 Windows 本机验，Linux 的 CI 抓不到；
> 那就退一步，守住能在 CI 里守住的两件事 —— 调用方不设任何编码变量时能跑通、
> 输出流连中文都表示不了时必须可读降级。
> **测不了全部，就把能测的那部分固化下来，别因为「测不全」而一条都不测。**

### 5.3 复查中修掉的 6 个真实 bug

1. `clean_sender("")` 返回「未知用户」，污染 `clean_sender(x) or 默认值` 的写法 → 空输入改为返回空串，兜底交给调用方。
2. httpx 的 `base_url` 不带尾斜杠时，把 `/api/x` 当相对路径处理，拼出畸形请求目标 → 服务端 404。
3. 环境里设了 `http_proxy`，httpx 默认走代理，本地请求被改成绝对地址形式 → 404。本机检查脚本需 `trust_env=False`。
4. Mock 关键词抽取切出「哈哈哈今」这类垃圾 → 加连续重复字收敛 + 停用字首尾过滤。
5. Mock 事实抽取把「我是认真的」抽成职业、把「猫的」连语气词一起抽出 → 收紧正则 + 值清洗 + 泛化词黑名单。
6. **事实抽取静默丢数据**（最严重的一个）：见下节。

### 5.4 CI 第一次运行就抓到一个本地漏掉的 bug

现象：`test_smoke.py` 里「抽到含『猫』的事实」这条断言在 CI 上失败，**本地一直是绿的**。

第一反应是「Linux 和 Windows 有差异」，实测**与平台无关**：

- 用不同 `PYTHONHASHSEED`（0 / 7 / 13）连跑三次，结果完全一致 → 排除哈希随机化
- 真因是流程问题：改完 `mock.py` 后只跑了 `e2e_check.py`（它不检查事实抽取），
  **没有重跑冒烟测试**，本地结果还停留在改坏之前

#### 根因：三层叠加，每层单独看都「合理」

| 层 | 问题 | 修复 |
|---|---|---|
| `store` | facts 唯一键 `(chat_id, subject, key)` 把「喜欢」这类一对多关系建模成字典。配合 `INSERT OR REPLACE`，「喜欢猫」被后来抽到的「喜欢火锅」**静默覆盖**，不报任何错 | 唯一键改为 `(chat_id, subject, key, value)` |
| `store` | SQLite 不支持修改约束，老库需要迁移 | 新增 `_migrate_facts_unique()`：读 `sqlite_master` 原始 DDL 判断版本 → 重建表。数据保留、重复执行幂等 |
| `mock` | 同一 key 只保留置信度最高的 1 条（且用**严格大于**比较），丢掉同类不同内容的事实 | 按 key 分组保留前 4 条；单字过滤从「长度 < 2」一刀切改为按键白名单 |

修复效果（真实数据）：

```text
[peer] 喜欢 = '吃火锅'  conf=0.75  ev=12
[peer] 喜欢 = '猫'      conf=0.75  ev=27   ← 之前被整条覆盖
```

#### 三条可复用经验

1. **静默覆盖比报错危险得多**。数据模型错了，上游改多少都没用 ——
   而且这类错误不抛异常，只安静地给你一个缺了一半的画像。
   改 schema 唯一键时必须同时写迁移，且迁移必须幂等。
2. **「本地全绿」≠「CI 绿」，但原因常常不是平台**，
   而是改了公共代码却只跑了部分测试。CI 的价值不是「更严格」，而是「不会忘记跑」。
3. **定位跨环境不确定性的手法**：固定 `PYTHONHASHSEED` 多跑几次。
   结果一致即可排除随机性，问题必然在确定的代码路径上。

## 六、第二轮：从脚手架到桌面软件

这一节是形态上的收口。核心命题只有一个：

> **源码能跑 ≠ 别人能用。** 中间的差距不是「打个包」，而是三类问题：
> 数据写哪、出错怎么让人看见、配置状态怎么让人自己查明白。

### 6.1 打包的真实代价：它是「问题放大器」

先说结论：**.exe 可行，但它会把所有原本「看得见」的问题变成「看不见」。**

| | 源码运行 | 打包成 exe |
|---|---|---|
| 报错 | 控制台红字 + traceback | **双击没反应** |
| 数据 | `backend/data/`，随手能看 | 写哪？程序目录可能只读 |
| 改一行代码 | 保存即生效 | 重新构建 40 秒 |
| 缺依赖 | `pip install` 一行 | 要么内置，要么用户永远修不好 |
| 启动 | 秒级 | onefile 要解压十几秒，**用户会以为卡死** |

所以这次打包**没有只交一个壳**，而是连带把三件必须一起做的事做掉了（6.2~6.4）。

一个具体的取舍：**用 onedir 而不是 onefile**。
onefile 每次启动解压到**随机临时目录**、退出即删 —— 用户第二次打开会发现
「我导入的聊天记录全没了」。onedir 启动是秒级的，东西都看得见，排错也直观。
代价是分发的是一个文件夹而不是单文件，这在说明里写清楚就行。

### 6.2 数据目录：为什么必须挪出程序目录

冻结态（`sys.frozen`）下把可写数据全部迁到 `%LOCALAPPDATA%\WingMan`：

```
%LOCALAPPDATA%\WingMan\
├── data\wingman.db      聊天记录、画像、设置
├── logs\wingman.log     滚动日志（2MB × 3）
├── logs\selfcheck.txt   最近一次自检报告
├── models\              本地语音模型权重（下过才有）
└── .env                 可选的手工配置
```

资源（前端页面、文档）仍从包内 `_MEIPASS` 读，**只有可写的才搬走**。
判断集中在 `config.py` 的 `_resource_dir()` / `_writable_root()` 两个函数里，
其他模块不感知「自己是不是在 exe 里」。

顺带做了一件容易漏的事：老名字的库文件（改名前的 `chatwing.db`）会自动改名过来，
连 `-wal` / `-shm` / `-journal` 这些边车文件一起搬，**用户数据不丢**。

### 6.3 错误可见性：`--noconsole` 是打包最大的坑

打包后没有控制台，**所有异常都变成「双击没反应」**，这是最糟的失败方式 ——
用户连「发生了什么」都不知道，更没法反馈。

对策是给每条错误路径都留一个出口：

| 出口 | 面向谁 | 内容 |
|---|---|---|
| `logs/wingman.log` | 排查者 | 滚动日志，UTF-8 |
| 原生弹窗（`MessageBoxW`） | 普通用户 | 人话 + 日志文件路径 |
| `WingMan.exe --check` | 反馈问题时 | 自检报告 → `logs/selfcheck.txt`，可直接发给别人 |
| 界面「体检」页 | 全部用户 | 三档结论 + 每项一个跳转按钮 |

还有一个小但致命的细节：**冻结后 stdout 会掉回 Windows 本地代码页（GBK）**，
日志里的中文全变乱码。`_setup_logging()` 里显式
`sys.stdout.reconfigure(encoding="utf-8", errors="replace")`。

### 6.4 自检：状态只有三档，每条非「已完成」都要带一个「点哪里能修好」

`selfcheck.py` 的硬规则：

```
ok   可用，不用管
warn 能用但会打折，或者非必需项缺失
fail 这项功能现在是坏的，会给用户错误结果
```

**不许只报「失败」** —— 每条非 ok 必须带一句人话说明 + 一个可执行的下一步。
界面上还要有个按钮直接跳到能把这项修好的那个设置页。

8 项检查：

| key | label | 可能状态 | 分组 |
|---|---|---|---|
| `runtime` | 运行环境 | ok | 运行环境 |
| `storage` | 数据目录可写 | ok/fail | 运行环境 |
| `log_dir` | 日志目录 | ok | 运行环境 |
| `frontend` | 界面资源 | ok/fail | 运行环境 |
| `docs` | 文档 | ok/warn | 运行环境 |
| `database` | 记忆库 | ok/warn(空库)/fail | 核心能力 |
| `llm` | 大模型 | ok/warn(mock)/fail | 核心能力 |
| `embedder` | 记忆检索 | ok/warn(hash)/fail | 核心能力 |

### 6.5 踩到的三个「不报错、只给错结果」的坑

这三个坑在 `docs/DESKTOP.md` 里各占一节。它们的共同点：
**不抛异常、不打印警告，只是安静地给你错误的结果** —— 所以最难发现。

#### 坑一：`available` 不等于 `ready`（自己造出来的 bug）

`ASREngine.available` 的语义是「这个引擎对象构造得出来」。对本地 whisper 来说，
只要 `faster-whisper` 库在它就是 `True` —— **哪怕模型权重一个字节都没下载**。

```
用户：选「本地模型 large-v3」→ 没下载权重
      → 自检显示绿色「已完成」
      → 用户以为配好了 → 录音后什么都没发生 → 不知道卡在哪
```

这**正是自检模块本身要消灭的那类问题**，结果它自己犯了。修法是把两个概念分开：

| | 含义 | 用途 |
|---|---|---|
| `available` | 引擎对象构造得出来 | 工厂选择实现类 |
| `ready` | **现在拿一段音频进来就能出字** | 自检面板、界面状态 |

> 教训：**状态判断要问「能不能真的干活」，而不是「对象有没有造出来」。**
> 这两者的差集，正是「看着配好了、用起来没反应」的全部来源。

#### 坑二：「int16 量级的 float32」——最阴的一个

```python
pcm = np.frombuffer(raw, np.int16).astype(np.float32)   # 忘了 / 32768
```

`dtype` 变成 `float32` 了，但**数值还在 ±32768**。而当时的 `transcribe()`
只按 `dtype` 判断要不要归一化：

```python
if pcm.dtype == np.int16:
    pcm = pcm / 32768.0      # float32 直接跳过这一步
```

于是送进 Whisper 的波形被放大了 3 万倍：

```
实际说的：今天加班到十点，好累啊，你周末有空吗
识别出来：玩玩玩玩玩玩!
```

**不报错、不警告，只是给你错结果。**

排查过程里差点走错方向 —— 一度怀疑是 `tiny` 模型太弱。关键在于做了一次
**英文对照实验**：英文同样乱，才确认是管线问题而不是模型能力问题。
（如果只测中文，很容易得出「中文就是不行」的错误结论。）

修法是 `asr/base.py` 的 `to_float_mono()`：不只看 `dtype`，还用**峰值兜底** ——
`float32` 但峰值 > 1.5 的，一律按 int16 量级处理（> 256 除以 32768，否则除以 127）。

> 教训：跨模块传数组时，「**dtype 对**」不等于「**量纲对**」。
> 接口契约要写清值域，并且用**数值特征做兜底校验**，而不是只信类型标签。

#### 坑三：`soundcard` 是两条语音路线的公共依赖

写打包配置时的第一反应是「录音库只有本地转写才需要，放进 `WITH_ASR` 分支吧」。**这是错的** ——
走云 ASR 时同样要先用 `soundcard` 抓系统回环/麦克风。

另外它的出现位置是**函数内延迟导入**（为了「没装也能跑」）。
PyInstaller 的字节码分析**确实**能扫到函数内的 import，所以它「碰巧」被打进去了。
但这是运气 —— 哪天把导入挪进 `try/except` 或换成 `importlib` 就会静默丢包，
而症状是「打包版能启动，但一录音就报没装库」。所以 spec 里显式声明了隐藏导入。

> 教训：**「碰巧能工作」和「保证能工作」之间要留一道显式声明。**
> 靠工具的实现细节生效的东西，写下来当注释，别当契约。

### 6.6 与另一个 agent 的工作合并

推送时发现远程多了 9 个提交 —— 是另一个 agent 从同一个基点分头做的一整套工作：

- `wingman.cmd` + `scripts/bootstrap.ps1`：**源码侧**零配置启动器
- `scripts/preflight.py` + `--doctor`：启动前自检
- `GET /api/health/details`：配置来源溯源（每个键的值来自 runtime/env/dotenv/default）
- `requirements.lock.txt`：25 个精确版本
- 代理绕过（`_trust_env_for`）与中文 Windows 编码处理

**两边目标相同、路径不同**：他要的是「源码装起来不费劲」，我要的是「连 Python 都不用装」。
所以合并的重点不是「谁覆盖谁」，而是**把两条路讲清楚、让它们共存**。

冲突只有 3 个文件。最后的处理是：

- 保留他的「快速开始（3 步）」作为 TL;DR
- 新增**「三种跑法：怎么选」**，把 `wingman.cmd` / `WingMan.exe` / 手动源码摆在一张表里，
  并指出**唯一的分水岭是「这台机器愿不愿意装 Python」**
- 新增「排错从哪下手」，明确两个自检入口各自的命令与产物路径

**顺带决定了两套自检不合并。** 检查项本来就不一样：
`--doctor` 查 Python 版本 / 位数 / venv / 依赖锁一致性（这些在 exe 里根本不存在）；
`--check` 查资源路径 / 可写目录 / WebView2 / 模型权重（这些在源码模式下不成为问题）。
强行合一会让两边都要塞一堆「如果是另一种形态则跳过」的分支，反而更难维护。

> 可复用的经验：两个 agent 并行做同一件事时，**价值最高的产出往往不是代码，是「怎么让用户不被两条路搞晕」**。
> 合并时先问「用户面对几个入口、他知不知道该选哪个」，比先 diff 代码更有效。

| 需要 Python | ✅ 3.11+ | ❌ 不用装 | ✅ 3.11+ |

## 七、第三轮：把打包版真正跑一遍

前两轮的验证停在「装上能开、数据不丢、接口通」。这一轮补的是更硬的一条：
**核心功能在冻结环境里到底能不能跑通。**

### 7.1 这轮为什么能挖出问题：上一轮的清单漏了一整条路径

上一轮对打包版的语音验证，验的是 `--asr-test` 能加载模型并出字。但
**加载已有模型**和**按需下载模型**是两条完全不同的代码路径：

| 步骤 | 实际走的东西 | 上一轮验了吗 |
|---|---|---|
| 加载已下载的模型 | `faster_whisper` 读本地目录 | ✅ 验了 |
| 从网上下载模型 | `huggingface_hub` + 镜像 + 写磁盘 + 校验落盘 | ❌ **漏了** |

而「模型按需下载、带真实进度与剩余时间、可切国内镜像」是写在 CHANGELOG 和
界面上对用户的承诺。**承诺了却没验，等于没做。**

> 方法论：验证清单要按**代码路径**列，不能按**用户功能**列。
> 按功能列会写出「语音能用」这种条目，它掩盖了内部其实有三条路径、你只走通了其中一条。

### 7.2 一次「差点改错」的排查：把「静态分析看不见」的范围搞错了

这段值得单独记，因为**我差点基于一个错误的推断去改构建配置**。

起因是查体积时注意到：标准版里根本没有 `huggingface_hub` 这个目录，
却单独躺着一个 `hf_xet`（9.06 MB）。顺着想下去就是：**打包版的下载功能是坏的**。

证据看起来也很足：`models.py` 里那行 `from huggingface_hub import snapshot_download`
写在函数**内部**，而项目文档里早就有一条「uvicorn 的实现类是运行时按字符串挑的，静态分析看不见」。
两件事一叠加，就得出了「函数内的 import 也看不见 → 这个模块没被打进包」的结论，
并准备去 spec 里补一个 `hiddenimports`。

改之前决定先核对。方法是拿 PyInstaller 自己的归档读取器，把 exe 里真正的模块清单列出来：

```python
from PyInstaller.archive.readers import CArchiveReader, ZlibArchiveReader
r = CArchiveReader("dist/WingMan-full/WingMan.exe")
open("pyz.pyz", "wb").write(r.extract("PYZ.pyz"))   # 模块归档在里层
names = sorted(ZlibArchiveReader("pyz.pyz").toc)    # 权威清单
```

结果是：`huggingface_hub` 有 **147 个子模块，本来就在包里**。

> **「静态分析看不见」只对「模块名是运行时拼出来的」成立，
> 不要推广到函数内写的 `from X import Y`。**
> PyInstaller 用的是字节码分析，函数内的 import 照样能追到。
> 唯一追不到的是 `importlib.import_module(name)` 这种 —— 也就是 uvicorn 那一类。

这次排查还顺带踩了另外两个坑，都是「工具本身在骗你」：

- **不能用 `grep` 二进制里的字符串来判断模块在不在包里。** 一开始就是这么干的，
  而且在 exe 里 grep 到了 `huggingface_hub`（3 次），差点当成「本来就在」的证据。
  可那几次命中来自 `models.py` 里讲解 Xet 的**文档字符串** —— 字符串会被打进去，模块不一定。
  反过来，模块真被打进去时 PYZ 内容是压缩的，grep 又可能什么也搜不到。**两个方向都会给假结论。**
- **第一次核对脚本自己写错了。** 写的是 `txt in acc`（`acc` 是字符串**列表**），
  这是精确成员判断，不是子串匹配。于是三个修复全部报 `False`，看起来像「重建没生效」，
  实际是探针错了。改用子串匹配后三项全为 `True`。

> 教训：**核对「东西在不在」时，要用权威接口，并且先拿一个已知为正的样本校验你的探针。**

### 7.3 一个把我自己坑到的验证陷阱：连到了旧进程

起了打包版服务，`curl` 了 `/api/health`，结果看到一组自相矛盾的东西：

```
"db": "...\wingman\backend\data\wingman.db"   ← 这是**仓库里**的源码数据目录
providers: asr -> mock                         ← 而我起的是**完整版**，ASR 应该是 local
```

同时后台任务显示进程**已经退出**。查下来原因是：

- 机器上还留着**三个早前会话遗留的源码模式服务**（端口 8791 / 8793 / 8797）；
- 打包版为了做单实例，启动时会探测目标端口，发现已有 WingMan 就**直接复用、不起新服务**；
- 于是新起的 exe 静默退出，而 `curl` 打到的是**那个旧进程**。

这不是产品的 bug（日常使用里「已经开着就别再起一个」是对的），
而是**验证方法**的 bug。记下两条以后照做：

> 1. 手工验证时**换一个没人用的端口**，别用默认端口。
> 2. 核对响应里的**数据目录是不是你预期的那一个** —— 这是确认
>    「你连的是自己刚起的那个进程」最省事的判据。

顺手也修了一句会加重这个陷阱的日志：原来无论什么模式都印
「检测到已有 WingMan 在运行，**直接打开界面**」，但 `--no-window` 下其实不会打开任何界面。
现在会说实话。**日志不准确与日志缺失同样有害 —— 它会让你在错误的方向上多绕一圈。**

### 7.4 修复一：中文转写不再吐繁体

在打包版里下载 `base` 并转写同一段中文，得到：

```
[文本] 今天加班到10點,好累呀,你周末有空嗎?      ← 繁体
```

内容是对的、字形是错的。用户不会认为「模型倾向繁体」，只会认为**这软件认错字了**。

处理方式是给中文转写加一段简体 `initial_prompt`。实测对比：

| 规格 | 无提示词 | 带简体提示词 |
|---|---|---|
| tiny | 今天加班到10点好累呀你周末有空吗 | 今天加班到十点,好累呀,你周末有空吗? |
| base | 今天加班到10**點**,好累呀,你周末有空**嗎**? | 今天加班到10**点**,好累呀。你周末有空**吗**? |

`base` 的置信度也从 0.735 升到 0.787。

**为什么不用繁简转换库？** 转换库只是**事后补救**，而提示词是**从源头不让模型往繁体跑**，
还能顺手把语气定在普通话上。而且少一个依赖就少一份体积和许可问题。

另一个细节：只在**明确是中文**时加。`auto` 模式本来就是在做语种识别，
此时塞一段中文进去会把语种判断本身带偏 —— **宁可偶尔出繁体，也不要认错语种。**

### 7.5 修复二：错误话术不能把人带进死胡同

模型下载失败时，代码会调 `_explain_error()` 把底层报错翻译成人话。
它有网络超时、401、磁盘满等分支，最后有一句兜底：
「可以先重试一次；一直失败的话，勾上「使用国内镜像」或换个小一号的模型。」

问题在于它**没有「缺组件」这一类**。如果哪天真有模块没打进包，
用户会看到 `ModuleNotFoundError` 被翻译成「重试 / 换镜像」——
**而镜像补不上一个没打进包的模块，这是个永远修不好的方向。**

现在新增了这类判断。关键细节是**它必须排在所有网络关键词之前**：
模块名有可能碰巧命中下面的关键词（比如名字里带 `connection`），
排在后面就会被误判成网络故障、又绕回那条死胡同。

> 这是这个项目反复出现的一个模式：**「没有建议」不可怕，
> 「看起来合理但方向错误的建议」才可怕。** 前者用户会来问，后者会让用户默默流失。

## 八、第四轮：以「对象」为中心的整体改版

### 8.1 这一版在解决什么

旧版的数据模型没问题（`persons` 表早就有），**问题在界面的组织方式**：

一级导航是**按功能的来源**分的，不是按用户的意图分的：

```
指挥台 · 记忆 · 导入 · 采集 · 通话（敬请期待）· 自检 · 设置
```

要「导一段记录」得先自己想清楚「这算导入还是采集」；想「看看对她的了解」得知道那叫「记忆」；
而「通话」占着一个一级位置却什么都不能做。

同时，**同一个人不止一个会话**这件事没有被表达出来。一个人在微信、QQ、换过昵称的老号上
都留下记录时，旧版里它们是三个并列的「会话」，各有一份人物设定、各记各的事实：

- 在微信那个会话里说过「她不喜欢被叫宝贝」，在 QQ 那个会话里又踩一次；
- 想整体看「她最近的状态」，得自己把两个会话的建议来回翻。

**这一版把「对象」提为第一层，会话降为「渠道」（第二层）。**

### 8.2 语音为什么撤下（重要决策记录）

原始需求里有「接入大模型语音通话识别」，技术上也在第三轮跑通了（见 7.7）。
但 **v0.1.1（原 0.2.1）把它整体撤下了**（提交 `6fb9fdd`、`acff853`）：

- 通话页现在只剩占位文案，且明确声明「没有任何按钮、后端入口也一并移除」；
- CSS 里 `.subs/.cap/.meter` 随之清理；
- README 与 `docs/COMPLIANCE.md` 里的相关表述一并核对，不留「通话页还在」的失实描述。

**为什么撤**：它是三个能力里唯一一个「法规与场景都最别扭」的部分 ——
在通话中实时采集对方的声音涉及录音告知、平台条款与两方同意，产品上无法给出干净的边界。
技术可行性不构成保留理由。这个决定被写进了 `docs/COMPLIANCE.md`，
并且原「通话」页里有价值的内容（路线图思路）被压缩进「关于 → 路线图」一节 ——
**不是原样搬运（那是另一种冗余）。**

### 8.4 四个关键设计决策

#### (1) 时间语义：从「抓取时刻」改为「消息自己的时刻」

这是用户明确提出的一点：**复制一段上周的聊天记录，记成今天是没有意义的。**

现在时间来源分 5 类，每条消息都会标注，界面上可点开看解释：

| `ts_source` | 含义 |
|---|---|
| `clipboard` | 复制出来的文本自己带了年月日（最可信） |
| `relative` | 文本里是「昨天 21:03」这类相对时间，按复制那一刻往前推 |
| `inferred` | 完全没带时间，按该会话时间线推定（**新的默认**） |
| `assumed` | 旧的「抓取时刻」，**仅用于兼容已存在的数据** |
| `manual` | 用户手填 |

`inferred` 的算法：锚点取该会话库里**最后一条消息的时刻**，逐秒递增，
且**绝不越过复制时刻**（消息不可能来自未来）。

相对时间解析有两处刻意收紧，都是被真实文本打脸之后加的：

```python
# 1) 裸钟点只在「紧跟称呼之后」才认 —— 否则正文里的比分 3:1 会被当成时间
def _parse_ts(text, *, allow_bare_clock=False, now=None) -> ...

# 2) 算出来的时刻晚于当下就回退一天 —— 「21:03」在上午复制，指的是昨天晚上
```

> **为什么把这件事看得很重**：真时间轴上混进假时间，「她平时几点找我说话」这类结论
> 就是错的。而这个错误**不会报错**，只会安静地给出错误结论。

#### (2) 多渠道上下文合并

`build_context(ctx, chat_ids, ...)` 现在接受一组渠道，`chat_ids[0]` 是**主渠道**：

- **人格 / 昵称 / 检索锚点**取自主渠道，**新消息也写进主渠道**；
- **事实**：对象级 + 该对象名下全部渠道级事实合并成一个视野，各带 `scope` 标注，
  **只合并视野、不做去重**；
- **摘要**：跨渠道按 `period` 排序取前 N；
- **近期消息**：跨渠道合并后**按 `ts` 归并**取尾部 N 条；
- **检索**：**逐渠道**做（`per_chat_k = max(5, top_k // len(ids))`），结果统一按 `score` 排序再截断。

最后一条是刻意的：如果合并成一个池子再检索，
**话多的那个渠道会把话少的整个盖掉** —— 而用户勾上第二个渠道，恰恰是因为那里有独有信息。

**单渠道的旧路径完全保留**，老用法不受影响。

#### (3) 事实的合并展示规则：分组、分别计数、不去重

对象页「记忆」Tab 里，事实按 **对象级** 与 **渠道级** 两组显示、**分别计数**。

理由：同一条事实在两个视野里各出现一次是正常的 ——

- 对象级那条是「跨渠道成立」的判断；
- 渠道级那条是「在这段对话里说过」的记录。

合并掉就丢掉了**来源**，而来源恰恰是用户判断「这条可不可信」的依据。

#### (4) 「检查更新」：查不到就说不知道

```python
except Exception as exc:
    return {
        "ok": False, "current": __version__,
        "hint": "没查到不等于已是最新 —— 可能是断网、代理或 GitHub 访问不了。"
                "可以直接打开项目地址自己看一眼。",
        "repo": REPO_URL,
    }
```

**关键点是查不到时不给 `has_update` 字段。** 把「没查到」和「查到了、没有新版本」
合并成一句「已是最新」，是在替用户做一个他没法复核的结论。
这是 v0.1.3 那个 `Failed to fetch` 留下的教训。

### 8.5 修掉的三个 bug

#### Bug 1（用户报的）：半自动采集第二次选中就崩

```
AttributeError: 'PersonChannel' object has no attribute 'peer_name'
```

**根因**：`schemas.PersonChannel` 少了 `peer_name` / `me_name` 两个字段，
而 `semi._resolve_names` 读了两处。

**为什么看起来是「随机」的**：

`_resolve_person_id` 在库里找不到同名者时返回 `""` →
`_resolve_names` 的守卫 `if store is not None and person_id:` **短路，循环从不执行**。
第一次创建时 person 还不存在（`person_id=""`）→ 不炸；
第一次落库时 `upsert_chat` 的 `ensure_person_for_chat` 已把 person 建好并绑上 chat，
第二次选中时 `person_id` 非空 → 守卫放行 → 遍历 `person_detail().channels` → 崩。

**充要条件**：`person_id` 非空 **且** 该 person 至少绑定一个 chat。

**为什么测试没抓到**：`test_collect_semi.py` 的 `_started()` 直接给 `sc._peer_names` 赋值，
绕过 `_resolve_names`；唯一走真 `start()` 的用例用的 person 由 `create_person` 建、
**没有任何 chat** → `channels == []` → 循环体一次都不进。

**修法**（比「只改调用点」更稳）：字段补进 `PersonChannel`（**只加不删**，前端在用的响应模型
加字段是兼容的），并在 `store.person_detail` 里从 `ChatInfo` 填进去 ——
这样「渠道视图缺字段」这一类坑一次性消掉。

**守卫**：`test_start_works_when_the_person_already_has_a_channel`**真的调 `start()`**，
且**实测在旧代码上会复现原始 AttributeError**。

#### P0（本轮改版自己引入的）：`loadChats` 被调用但已不存在

重构把 `loadChats` 并进了 `loadObjects`，**但漏改了 5 个调用点**。

它本来是个编译期错误，但**单文件 HTML、无构建步骤，没有编译器帮忙**，
于是它一路来到了测试面前 —— 而那一轮全量测试是绿的。

实际后果**比「一个小按钮失效」严重得多**，两条路径表现完全不同：

| 调用点 | 后果 |
|---|---|
| `init()` 里那一次 | 抛 `ReferenceError` → 后面的**读设置、自检、深链接跳转全都不执行** |
| 指挥台分析成功后那一次 | 它在 `try` 里 → 异常被 `catch` 接住 → **刚渲染出的分析结果被覆盖成一句错误提示** |

第二条最坑：用户看到的是「分析坏了」，而真正的问题在刷新列表那一步；
`renderBundle()` 明明成功了，`catch` 却把它的成果擦掉。
**一个 `try` 包得太宽，会把「成功的结果」和「收尾时的失败」搅在一起。**

**修法两层**：① 改掉 5 个调用点；② 补上一条**会失败的测试**：

```python
def test_no_calls_to_undefined_functions(html: str) -> None:
    """脚本里调用的每个名字，最终都要有人定义它。"""
    script = html[html.index("<script>"):]
    called  = _called_function_names(script)     # 抠出所有 `名字(`
    defined = _defined_function_names(script)    # 函数声明 / var-let-const / for-of / 参数与解构
    unknown = sorted(n for n in called
                     if n not in defined and n not in _JS_KEYWORDS
                     and n not in _BROWSER_GLOBALS and n not in _CSS_FUNCS)
    assert not unknown, f"这些函数被调用了但没人定义：{unknown}"
```

减法里那三张表不是偷懒：关键字与浏览器内置对象天然不需要在本文件定义；
`_CSS_FUNCS` 是因为**模板串里的内联样式会长得像 JS 调用** ——
`style="width:min(680px,100%)"` 会带出 `min()`。这条只能显式排除，并写清楚为什么。

**这条守卫经过反证**：把调用点还原成修复前的写法，它会失败。

#### 新功能自己带出来的：「后台运行」变成单向门

给窗口 × 加了「关闭弹窗（后台运行）」之后，问题变成：**怎么把窗口找回来？**

最自然的写法是「再双击一次 `WingMan.exe` 就再开一个窗口」——
代码里本来就有单实例检测，看起来天衣无缝。**但这个窗口是个空壳：**

- 服务在**第一个**进程里，第二个进程只负责渲染那个窗口；
- 页面上的请求全都打到老进程的服务上；
- 于是在新窗口里点「关闭程序」→ 请求发到老进程 → 老进程退出并销毁**它自己的**窗口 →
  新窗口变成一具对着死服务的躯壳，而**第二个进程还挂在那儿**。

用户看到的是「点了关闭程序，窗口还在」。

**修法**：第二次双击走 `POST /api/desktop/show`，由老进程执行 `window.show()`。

```python
def _ask_running_instance_to_show(port: int) -> bool:
    """请**已经在跑的那个实例**把它自己的窗口显示出来。

    为什么不是「在这里再开一个窗口」：服务只在一个进程里。第二个进程开出来的
    窗口只是一个空壳 —— 「关闭程序」关掉的是新壳，老进程连服务带窗口继续活着。
    """
```

`show()` 失败时（浏览器模式、老版本不认识这个接口）**如实返回 `shown=false`**，
调用方再退回「新开一个窗口」。

> 教训：**多进程 + 单服务的组合里，「谁持有状态」比「谁能画出界面」重要得多。**
> 凡是出现「壳与本体分离」的可能，都要先问一句：**这个动作作用到哪个进程上了？**

## 九、第五轮：「先填后补」与「其他聊天」

### 9.1 这一版在解决什么

上一版把记忆的中心从「会话」换成了「对象」，但**顺序是固定的**：
必须先把聊天记录导进来，程序才会替你建出那个对象。

可是人的真实顺序常常是反的 —— 你先听说了一个人、先知道了一些情况
（她叫什么、你们是什么关系、你想走到哪一步），**过一阵子**才拿到聊天记录。
想先把「雷区：别提前任」记下来，却发现**没有地方写**，因为还没有任何一条记录。

这一版做两件事：

1. **把顺序解开** —— 先建对象、随时补、之后再用记录去完善它；
2. **补上「其他聊天」** —— Telegram / 钉钉 / 短信 / 贴吧里说的话，以前无处安放。

另外顺手挖出并修掉了**三个「静默坏了很久」的问题**，其中最严重的一个是
**「导入微信聊天记录」从项目第一个版本起就是崩的**。

### 9.4 「让 AI 帮我整理」——在你的草稿上补，而不是重写

`profiler.py` 新增 `build_person_profile(ctx, person_id, *, overwrite=False)`。
与渠道级 `build_profile` 的三处关键差别：

1. **跨渠道**：输入是这个人所有渠道的消息，每条标着来自哪个渠道；
2. **不吃掉用户手写稿**：默认只填空；
3. **先建索引**：顺手把每个渠道的向量索引补齐，导完就能直接分析。

核心合并策略：

```python
_USER_FIELDS = ("goal", "stage", "taboos", "my_style")   # 用户手写的，默认不动
_MODEL_FIELDS = ("peer_profile",)                        # 模型字段，允许改写

for field in _PERSONA_FIELDS:
    old = str(getattr(cur, field) or "").strip()
    new = str(data.get(field) or "").strip()
    if field in _USER_FIELDS and old and not overwrite:
        kept.append(field)
        continue
    if not new:
        continue
    patch[field] = new
    updated.append(field)
```

**`kept` 的判定刻意不看模型有没有给出新值。** 它是给用户的一句**保证**
（「你手写的这四项，我一项都没动」），不是模型这次的成绩单。
如果只在「模型恰好也想改这一项」时才列出来，用户拿到的就是一份随模型心情浮动的清单 ——
少了一项他就得自己去比对是不是被改掉了，反而更不敢按这个按钮。

两条容易被忽略的实现细节：

- **`before_ids` 必须在抽事实之前取**，否则 `facts_extracted` 永远是 0；
- **抽样按渠道配额**：`per_chat = max(10, PROFILE_SAMPLE // len(channels))`。
  不这么做的话，话多的渠道会把话少的整个盖掉 ——
  而「Ta 在 QQ 上很冷淡」这种结论恰恰只存在于那个话少的渠道里。

一个渠道读失败不拖垮其它渠道（逐渠道 try/except 收进 `warnings`）；
还没导入记录的「提前新建」对象按这个按钮**不报错**，而是返回一句「下一步该做什么」。

### 9.5 「其他聊天」渠道

除 QQ / 微信以外的来源，现在是一个**明确定义的位置**，不是「认不出来的东西」。
它有三个接缝，三处都改了：

```python
# backend/app/store.py —— 渠道映射
_CHANNEL_BY_PLATFORM = {
    "qq": "qq", "wechat": "wechat",
    "other": "other", "generic": "other",      # generic 是导入适配器的名字
    "call": "call", "voice": "call",
    "offline": "offline", "face": "offline",
}

def _channel_from_platform(platform: str) -> str:
    """platform → channel。**兜底是 `other`，不是 `generic`。**"""
    return _CHANNEL_BY_PLATFORM.get((platform or "").strip().lower(), "other")
```

```python
# backend/app/api/routes_collect.py —— 半自动采集白名单
# QQ/微信 之外的东西自动采不了，但半自动（剪贴板）采得了 —— 你复制什么它接什么。
# 若沿用 SUPPORT_MATRIX 当白名单，就等于「其他聊天」被自动采集的短板连坐了。
SEMI_CLIENTS: tuple[str, ...] = ("qq", "wechat", "wechat3", "other")
```

**为什么白名单不能复用 `SUPPORT_MATRIX`**：那张表回答的是「能不能读加密库」，
而「其他聊天」读不了加密库、却完全采得了剪贴板。复用会让这个渠道被连坐。

第三处是「显式传入的渠道名也要过映射」——新增 `_norm_channel(channel, platform)`。
原因是半自动采集靠 `channel == client` 认领已有渠道，库里同时存在 `generic` 与 `other`
两个写法时，它会给同一个对象重复建一个渠道。迁移里也把历史 `generic` 行 UPDATE 成 `other`。

### 9.6 让用户说清「这话是在哪说的」

**文本排布长得像微信，不等于它来自微信。** 所以 `import_file` / `import_text`
都新增了 `platform` 参数，用户声明的来源压过适配器猜测：

```python
plat = (str(platform or "").strip() or adapter.platform) or "other"
chat_id = make_chat_id(plat, name)
store.upsert_chat(chat_id, plat, name, peer_name, me_name)
```

粘错标签是静默的 —— 只会在之后某次分析答得不对时才隐约浮出来，很难回溯到导入这一步。
所以 `ImportResult` 也加了两个字段，让结果**当面回报归宿**：

```python
class ImportResult(BaseModel):
    ...
    platform: str = ""     # 这段记录最后归到了哪个平台
    channel: str = ""      # 以及哪个渠道（从库里读回来，不在这里重算一遍映射）
```

**不认得的平台：渠道兜底 `other`，平台原样保留。** 这是一个刻意的不对称：
渠道名是给人看的归类，只允许有限几个值；平台名是**用户自己打的字**，
认不出来就原样显示（「（保持原样）」），不许悄悄改掉。

### 9.7 空对象接住之后的同名导入

```python
# store.py::ensure_person_for_chat
placeholder = self.find_person_by_alias(name)
if placeholder is not None and self._channel_count(placeholder.id) == 0:
    log.info("「%s」是先前手建的空对象，这次的记录挂到它名下（%s）", name, placeholder.id)
    self.bind_chat(chat_id, placeholder.id)
    return placeholder.id
```

判据是「那个名字下**一段记录都没有**」，这一点是刻意的：

- 空对象里没有任何数据，接住它**不可能把谁的记忆混在一起**，没有猜错的风险；
- 那个名字下**已经有**记录时，退回原来的保守策略（新建，让用户显式合并）——
  因为「QQ 上的张三」和「微信上的张三」是不是同一人，程序无从判断。
  **猜错是静默的，而记忆混在一起比多建一个人严重得多。**

这条同时修掉了一个真实的用户工作流问题：按原来的写法，
「先建对象、后导记录」会得到**两个同名对象**。

### 9.8 三个「静默坏了很久」的问题

这一类问题的共同形状是：**编译不报、导入不报、界面照常打开**，
只有真走到那一条路时才出问题 —— 而那条路恰好没有测试。

| 问题 | 坏在哪 | 为什么没人发现 |

### 9.9 Bug 1 的真根因：「检查更新显示 0.3.1」

**不是文案写错，是一个 0.3.1 时代的旧进程还在 8787 端口答话。**

前端 `index.html` 是 `StaticFiles` **每次从磁盘现读**的（所以是新的），
服务却是一个**一直在跑的进程**（所以是旧的）。

排查过程（可复用）：

```text
端口 8787（旧进程）: version=0.3.1 → 检查更新：有新版本 v0.4.0（当前 v0.3.1）
端口 8801（新进程）: version=0.4.0 → 检查更新：已是最新（v0.4.0）
```

一开始按「文字写错」的方向找（grep `0.3.1`、看 `#about-ver`、查 GitHub Releases 侧的 `latest`），
全部正常。改用 `Get-NetTCPConnection` 列出 87xx–89xx 的监听端口，
发现 8787 上有一个 python 进程；逐个端口打 `/api/health` 比对版本，才确认它就是旧进程。

#### 三层防呆（不只满足于杀进程）

1. **前端自带版本号常量**，与 `/api/health` 报的版本比对：

```js
const BUILD = "0.5.0";
// 前端是**每次从磁盘现读**的，服务却是一个一直在跑的进程，两者可以来自不同版本。
```

不一致时在页面顶部弹红横幅 `#ver-warn`，写明「界面 vX，答话的本机服务 vY」+ 旧进程排查步骤。

2. **桌面壳自述**（`GET /api/desktop/state`）：

```python
{
  "version": __version__,
  "started_at": datetime.fromtimestamp(_STARTED_AT).astimezone().isoformat(timespec="seconds"),
  "uptime_seconds": int(max(0, time.time() - _STARTED_AT)),
  "mode": "exe" if IS_FROZEN else "source",
  "pid": os.getpid(),
}
```

3. **HTML 加 `Cache-Control: no-store`**（`NoStoreHtmlMiddleware`，
   只给 `text/html` 补，不覆盖已有的 cache-control 头）。

4. 另加一条测试盯着「前端 `BUILD` 必须等于后端 `__version__`」——
   否则这道检查会变成天天误报的噪音，用户很快学会无视它，那还不如没有。

> **为什么会有旧进程？** 常见来源是「关闭弹窗（后台运行）」那个选项 ——
> 它刻意不结束服务，方便下次双击直接回来。选过它之后又升级程序，就会撞上这个。

### 9.10 六条关键守卫的脚本化反证

标准是项目既有的那条：**新测试要能在旧代码上失败**。六条全过：

| 改回旧写法 | 如期失败的用例 |
|---|---|
| 删掉 `wechat.py` 的 `iter_blocks` 导入 | `test_bundled_samples_import_through_their_own_adapter` |
| `_resolve_map` 拿候选表当实际列名 | `test_column_names_are_matched_against_the_real_columns` |
| `_pick` 直接取 `probes[0]` | `test_nothing_matches_falls_back_to_the_generic_parser` |
| `_guess_paste_suffix` 一律返回 `.txt` | `test_column_names_are_matched_against_the_real_columns` |
| `import_file` 忽略用户声明的 `platform` | `test_declaring_the_source_beats_the_adapter_guess` |
| `kept` 改成「模型也想改时才列入」 | `test_refine_still_reports_a_draft_field_the_model_said_nothing_about` |

**反证过程本身带来两个收获**：

1. 「`kept` 只在模型也想改时才列出来」这条改动**本来没有任何测试盯着** ——
   旧测试用的是 Mock 引擎，而 Mock 会把全部字段都填满，所以新旧写法都能过。
   为此专门加了一个「没有证据的字段就不写」的模型桩，才把这件事钉住。
2. 第一次写的反证脚本里，「`_resolve_map`」那条改动**不够忠实**
   （改成了另一种坏法，恰好被别的修复兜住了），于是它「通过」了 ——
   说明**反证本身也要被怀疑**。

## 十、第六轮：关窗死锁与内存瘦身

### 10.1 用户报了什么

> 我点击右上角叉的时候，总会卡住，显示「WingMan 未响应」。你给我把程序优化流畅一些。

拆成两件事：

| 诉求 | 性质 |
|---|---|
| 点 × 卡死 | 确定性故障 —— 「总会」说明每次都会中 |
| 程序内存整体优化 | 性能优化 —— 但得先知道内存花在哪 |

### 10.2 死锁：先复现，不猜

这类「窗口卡死」的直觉答案通常是「主线程被某个耗时操作占住了」。
但那个方向会把整件事带偏。先拿数据说话。

**`Process.CloseMainWindow()` 就是发 `WM_CLOSE`**（等价于点 ×）；
**`Process.Responding` 读的就是 Windows 判定「未响应」用的那个状态**（内部即 `IsHungAppWindow`）。

```powershell
$proc = Get-Process | Where-Object { $_.MainWindowTitle -like "*WingMan*" } | Select-Object -First 1
[void]$proc.CloseMainWindow()          # 等价于点了 ×
for ($i = 1; $i -le 8; $i++) {
  Start-Sleep -Seconds 1
  $p = Get-Process -Id $proc.Id -ErrorAction SilentlyContinue
  Write-Output ("第 {0}s：Responding={1} CPU={2}s" -f $i, $p.Responding, $p.CPU)
}
```

> 一开始想用 `Add-Type` 调 P/Invoke 的 `SendMessage` + `IsHungAppWindow`，
> 但 `Add-Type` 在本机被安全策略拦下了。换成这两个 .NET 内置成员后**完全等价**。

结果：

| 时刻 | Responding | CPU |
|---|---|---|
| 发 WM_CLOSE 前 | `True` | 2.0625s |
| 之后 1 秒 | **`False`** | 2.0625s |
| … | … | … |
| 之后 8 秒 | **`False`** | **2.0625s（纹丝不动）** |

**CPU 纹丝不动，是死锁的指纹。**

如果是「算不过来」，CPU 读数会往上走（那就是性能问题，该去优化算法）；
这里它**完全不动** —— 说明进程什么都不干，只是**在等**。

这一条把方向从「找耗时操作」直接扭到了「找互等」。

### 10.3 根因：UI 线程里的同步 `evaluate_js`

顺着「在等」的线索去看关窗那一刻的调用栈：

```
用户点 ×
  → Windows 发 WM_CLOSE
  → pywebview 在 UI 线程上回调 FormClosing
  → 我们的 _on_closing()          ← 就在这个线程里
  → _ask_frontend_to_choose()      ← 想通知页面弹窗
  → _WINDOW.evaluate_js(...)       ← 同步阻塞
  → semaphore.acquire()            ← 死等
```

而 `evaluate_js` 的那一头（pywebview 6.2.1，`platforms/edgechromium.py:136`）：

```python
def evaluate_js(self, script: str, parse_json: bool):
    def _callback(res):
        ...
        semaphore.release()          # ← 只有它能让上面那句返回

    result = None
    semaphore = Semaphore(0)
    try:
        self.webview.Invoke(
            Func[Object](
                lambda: self.webview.ExecuteScriptAsync(script).ContinueWith(
                    Action[Task[String]](lambda task: _callback(json.loads(task.Result))),
                    self.syncContextTaskScheduler,      # ★ 投递到 UI 线程的同步上下文
                )
            )
        )
        semaphore.acquire()          # ← 无限等待，没有超时
    except Exception:
        ...
    return result
```

**关键就在 `syncContextTaskScheduler` 这个参数。**

`ExecuteScriptAsync(...)` 完成之后，回调 `_callback`（负责 `release()`）
被安排到 **UI 线程的同步上下文**上执行。而 UI 线程此刻正卡在
`_on_closing` 里等 `semaphore` —— **没有人在跑那个回调，也就永远没人 release。**

两边互等，`semaphore.acquire()` 没有超时，**永不解开**。

> 这也解释了为什么它是**必然**的而不是偶发的：只要走关窗这条路，
> `evaluate_js` 就一定是在 UI 线程上被调用的。用户说的「总会」，是准确的。

### 10.4 修法：把「通知界面」挪出 UI 线程

关窗钩子只做一件事：**置标志 + 起一个后台线程，然后立刻返回**。

```python
def _on_closing() -> bool:
    """pywebview 的关窗钩子。返回 False = 取消这次关闭。

    ⚠️ 这个函数跑在 UI 线程上（winforms 的 FormClosing 事件回调），
    所以这里绝不允许出现同步的 evaluate_js。
    """
    if _CLOSE["quitting"]:
        return True
    if _CLOSE["pending"]:
        return True                      # 再点一次 × → 直接放行
    _CLOSE["pending"] = True
    threading.Thread(
        target=_ask_frontend_or_close, name="wingman-close-ask", daemon=True
    ).start()
    return False
```

**为什么放到后台线程就好了**：`evaluate_js` 内部的 `self.webview.Invoke(...)`
在非 UI 线程调用时会**投递**到 UI 线程执行；而此刻 UI 线程已经从钩子里返回、
空闲下来了 —— 它能去跑那个回调，`release()` 得以执行，`semaphore.acquire()` 正常返回。

#### 三层兜底

改完之后，**每一条失败路径都得有出口**：

1. **超时**：`_ask_frontend_to_choose(timeout=5.0)` 起子线程调 `evaluate_js`，
   用 `Event.wait(5)` 等它；超时就按「通知失败」处理。
2. **通知失败就补一刀**：`_on_closing` 已经返回 `False`（取消了这次关闭），
   如果通知界面又失败，用户再点 × 也还是关不掉 —— 就成了「点了没反应」：

   ```python
   def _ask_frontend_or_close() -> None:
       if _ask_frontend_to_choose():
           return
       log.info("界面接不住关闭请求，直接关闭窗口。")
       _CLOSE["pending"] = False
       _CLOSE["quitting"] = True      # 让 destroy 触发的 _on_closing 放行
       _destroy_window()
   ```

3. **`quitting` 标志**：用户选了「关闭程序」之后，之后的所有关闭事件一律放行。
   不加这个的话，`_destroy_window()` 会**再触发一次** `FormClosing` → 又进协商
   → 又拦一次，转回去又关不掉。

#### 顺带修出来的两个问题

**(a) 「关闭程序」从未让 uvicorn 收工**

原代码：

```python
_STOP = threading.Event()
...
log.info("用户选择关闭程序，准备退出。")
_STOP.set()                                  # ← 谁在读它？
```

`grep -rn "_STOP" backend/app/` 的结果：**只有它自己的定义和这一处 set，
全仓没有任何消费者。** 注释里写的「先让 uvicorn 收工」是假的 ——
uvicorn 根本没收到信号，「优雅退出」全靠 1.2 秒后的 `os._exit(0)` 硬切。

后果：如果那一刻正好在写数据库（导入刚结束、画像刚存下来），就被掐断了。
SQLite 的 WAL 模式不会因此损坏数据，但会留下没 checkpoint 的 `-wal` 文件。

**修法**：保存 `uvicorn.Server` 引用，退出时置 `should_exit` 并**轮询等它收工**：

```python
def _wait_server_stop(timeout: float) -> bool:
    t = _SERVER.get("thread")
    if t is None:
        return True
    deadline = time.time() + timeout
    while time.time() < deadline:
        if not t.is_alive():
            return True
        time.sleep(0.05)
    return False

def _quit_soon(grace: float = 4.0) -> None:
    """收尾：先让服务体面收工，再关窗口，最后兜底强退。

    顺序不能反 —— 窗口一关，主线程就从 webview.start() 返回、
    一路走到进程退出；那时 uvicorn 若还在写库，就是被硬生生掐断的。
    """
    if _wait_server_stop(grace):
        log.info("服务已收工。")
    _destroy_window()
    time.sleep(1.5)
    os._exit(0)
```

现在日志里能看到完整链路（实测输出）：

```
已通知服务收工（uvicorn should_exit）。
WingMan 已退出
Application shutdown complete.
Finished server process [12460]
服务已收工。
正在退出，放行这次关闭。
界面已关闭，等后台服务收工…
已退出。
```

**(b) `python -m app.desktop` 下窗口状态有两份**

这个是排查时**意外撞见**的，很值得记下来。

用源码模式启动后，`/api/desktop/state` 报 `native_window: false`，
但 PowerShell 明明找得到那个标题为「WingMan · 聊天僚机」的窗口。
而且 `started_at` 比日志第一行**晚了 13 秒** —— 一个模块的启动时刻，
怎么会在它自己开始工作之后？

两个线索指向同一件事：**内存里有两个 `desktop` 模块**。

- `python -m app.desktop` 会让这个文件以 `__main__` 的名字执行；
- `app.api.routes_admin` 又 `from .. import desktop`，把它**按模块名再导入一次**。

于是 `_WINDOW` / `_CLOSE` / `_SERVER` / `_STARTED_AT` 各存一份：
主流程写的是 `__main__` 那份，接口读的是 `app.desktop` 那份（永远初始值）。

症状全都**像功能坏了，而不是像状态串了**：

- 窗口开着 → 接口说「没有原生窗口」→ 界面按「浏览器模式」措辞；
- 点「后台运行」→ 后端读到一个 `None` 窗口 → 回你「已关闭」**却什么都没做**。

**修法**（文件顶部，任何可能触发 api 导入的代码之前）：

```python
if __name__ == "__main__":      # pragma: no cover - 只有直接运行时才成立
    sys.modules.setdefault("app.desktop", sys.modules[__name__])
```

`exe` 与 `python run_wingman.py` 走的是 `from app.desktop import main`，
`__name__` 本来就是 `app.desktop`，**本来就没这个问题** ——
但排查问题时很容易被它带偏，所以一并修了。

### 10.5 内存：一个 `import` 占了九成

#### 先分层测量，别猜

内存问题的直觉答案通常是「前端 DOM 太重」或「后端缓存了太多数据」。
但正确做法是先量出**基线**。用几个最小对照进程（同机、同 venv）：

| 进程 | WorkingSet | Private（提交） | 线程 |
|---|---|---|---|
| 空 Python | 4.2 MB | **0.9 MB** | 1 |
| 只 `import` 依赖（numpy 等） | 57.1 MB | **782.3 MB** | 27 |
| WingMan 服务本身（`--no-window`） | 73.7 MB | **793.5 MB** | 28 |

**结论一目了然：WingMan 自己的代码只贡献了 11 MB。780 MB 是导入依赖时提交的。**

#### 缩小到单一元凶

再单独测 `import numpy`，并且和「限制 BLAS 线程数」做对照：

| | 提交内存 | 线程 |
|---|---|---|
| 默认 | **760.6 MB** | 27 |
| `OPENBLAS_NUM_THREADS=1` | **19.4 MB** | 4 |

**760 MB 对 19 MB —— 差 39 倍，就差在一个环境变量上。**

原因是 OpenBLAS 会看机器**有多少个逻辑核**，然后开同样数量的线程，
并给每个线程预先把工作缓冲区留出来。这台机器 **24 个逻辑核** —— 于是 24 个线程。

而本项目用 numpy 只干一件事：几千条 512 维向量算**余弦相似度**。
这个规模连一次眨眼都用不到，多线程只会带来调度开销。
**那些预留的内存换来的并行度，一点都用不上。**

#### 修法

放在 `backend/app/__init__.py` 的**顶层**：

```python
for _var in (
    "OPENBLAS_NUM_THREADS",
    "OMP_NUM_THREADS",
    "MKL_NUM_THREADS",
    "NUMEXPR_NUM_THREADS",
    "VECLIB_MAXIMUM_THREADS",
):
    os.environ.setdefault(_var, "1")
del _var
```

两个刻意的选择：

- **位置**：`app/__init__.py` 是最外层，在任何子模块之前执行。
  OpenBLAS 是在 `import numpy` **那一刻**就把线程池建好的，
  之后再设环境变量**等于没设**。所以这里没有第二个可选位置。
- **`setdefault` 而不是硬赋值**：用户自己设过就听用户的，
  我们只是提供一个更省内存的默认值。

#### 效果（带窗口，实测）

| | 提交内存 | 线程 |
|---|---|---|
| 修复前 | 844.9 MB | 43 |
| 修复后 | **107.0 MB** | **20** |

### 10.6 一个坑：`GetProcessMemoryInfo` 静默返回 0

第一次写内存探针时，所有读数都是 `0.0 MB` —— **没报错，就是全 0**。

原因：`kernel32.GetCurrentProcess()` 返回的是伪句柄 `-1`。
不显式声明 `restype` 的话，ctypes 把它当 32 位 `int`，句柄被截断，
`GetProcessMemoryInfo` 于是失败并返回 0，结构体字段保持初始值。

```python
_k32 = ctypes.WinDLL("kernel32", use_last_error=True)
_k32.GetCurrentProcess.restype = wintypes.HANDLE    # ★ 这一行不能省
_k32.GetCurrentProcess.argtypes = []
_psapi.GetProcessMemoryInfo.argtypes = [wintypes.HANDLE, ctypes.POINTER(_PMC), wintypes.DWORD]
_psapi.GetProcessMemoryInfo.restype = wintypes.BOOL
```

> 这类「不报错但结果全错」的坑比崩溃更难查 —— 崩溃至少有栈，
> 它只会让你对着一个漂亮的全 0 表格怀疑自己。

### 10.7 完整内存画像（打包版实测）

| 部分 | WorkingSet |
|---|---|
| `WingMan.exe` 主进程（Python + FastAPI + 本项目代码） | 162.1 MB |
| 6 个 `msedgewebview2.exe`（Edge 渲染引擎） | 400.8 MB |
| **合计** | **约 563 MB** |

那 6 个渲染进程是 Windows 自带 WebView2 的**标准结构**
（主控 / 图形 / 网络 / 渲染 / 工具 / 崩溃上报），不是泄漏 —— 关掉程序会一起消失。

**主进程那部分已经压到位**（之前光提交内存就 845 MB）。
剩下 400 MB 是 WebView2 的固有成本：压它需要限制渲染参数，
**副作用不可控而收益不确定，这一版刻意没动**。

> 在意内存可以走浏览器模式：`WingMan.exe --browser`（或 `WINGMAN_USE_BROWSER=1`）。
> 它复用系统里已有的浏览器，不起 WebView2 进程组，主进程只剩约 74 MB。
> 代价是没有原生窗口（没有独立任务栏图标）。功能完全一样。

### 10.8 守卫与反证

#### 新增守卫

| 文件 | 项数 | 盯着什么 |
|---|---|---|
| `tests/test_memory_footprint.py` | 2（新） | 干净子进程里验证「限流早于 numpy」，并直接量提交内存 |
| `tests/test_objects_center.py` | 29 → 33 | 4 条桌面壳守卫 |

`test_memory_footprint.py` 为什么**必须用子进程**：pytest 进程自己早就把 numpy
导进来了，那时候再去断言环境变量，「限流生效了没有」根本看不出来。

四条桌面壳守卫：

- `test_the_close_hook_never_blocks_on_evaluate_js` —— 把「UI 线程里同步调
  `evaluate_js` 会死锁」的语义照搬进测试，要求关窗钩子仍然立刻返回；
- `test_desktop_close_quit_actually_tells_the_server_to_stop` —— 退出必须**真的**
  置 `should_exit`，不能只 `set()` 一个没人读的 Event；
- `test_when_the_page_cannot_be_reached_the_window_is_still_closed` —— 通知不到界面时
  必须补关窗；
- `test_state_is_shared_even_when_desktop_py_runs_as_main` —— 以 `__main__` 加载
  `desktop.py` 再 `import app.desktop`，两者必须是**同一个模块对象**。

#### 反证：6 条，全过

| 改回旧写法 | 如期失败的用例 |
|---|---|
| 删掉 BLAS 限流 | `test_the_package_caps_blas_threads_before_numpy_arrives` |
| 删掉 BLAS 限流（效果侧） | `test_importing_numpy_stays_within_a_sane_memory_budget` |
| 关窗钩子改回同步调 `evaluate_js` | `test_the_close_hook_never_blocks_on_evaluate_js` |
| 退出只 `set()` 没人读的 Event | `test_desktop_close_quit_actually_tells_the_server_to_stop` |
| 通知不到界面时不补关窗 | `test_when_the_page_cannot_be_reached_the_window_is_still_closed` |
| 去掉 `desktop.py` 顶部的自我登记 | `test_state_is_shared_even_when_desktop_py_runs_as_main` |

#### 反证本身抓出的问题

**第一次跑，「关窗死锁」那条没抓住。**

原因不是守卫太弱，而是**替换不够忠实**：只把 `_on_closing` 改回了同步调用，
却留着新版 `_ask_frontend_to_choose` 内部的线程包装 ——
那是个**现实中不存在的混合状态**（旧代码里这两处是同一套写法），自然复现不出死锁。

改成「两处必须一起改回」之后才如期失败。

> **教训：一条通过了的反证，可能只是因为你复现旧代码复现得不够忠实。**
> 这和上一轮那次（`_resolve_map` 改成了另一种坏法）是同一类问题的两个变体。

#### 重编号踩到的坑

**一次查表替换，绝不顺序 replace。** 映射里有 `0.6.0 → 0.2.0` 和 `0.2.0 → 0.1.0`，
顺序替换会让刚生成的 `0.2.0` 被后一条规则再吃一次、变成 `0.1.0`。

**这个坑真的踩了。** 脚本对第一批 20 个文件跑了**两次**（第二次是往 TARGETS 里
加发行说明时把旧列表又带上了），结果 README 的下载链接变成 `v0.1.0`、
`STATUS.md` 里 22 处 `0.6.0` 全被降级。发现方式是对比 `git diff` 里
`0.6.0 → ?` 的实际落点。修法是**回滚这 20 个文件重跑一次**。

**文件重命名也有先后。** `v0.6.0.md → v0.2.0.md` 而 `v0.2.0.md` 本身要先改走，
否则互相覆盖。执行顺序是 `0.2.0→0.1.0`、`0.2.1→0.1.1` … 最后才动 `0.6.0`。

**测试里的叙述性版本号要手工改。** `test_version.py` 的文档字符串讲的是
「代码里写 `0.1.0`、tag 打 `v0.2.0`」那次版本漂移事故 —— 重编号后两个号会撞成同一个，
机械替换会得到「0.1.0 vs v0.1.0」这种自相矛盾的句子。改成不依赖具体编号的表述。

### 11.5 隐私：真正的那个问题不在文件里

先做了全历史扫描，结论**和直觉相反**：

| 扫描项 | 结果 |
|---|---|
| 真人姓名（既有守卫） | 已在早前一轮清理过，全过 |
| 手机号 / 身份证 | 无 |
| 密钥 / 令牌 | 无（只有测试用例里的假 key） |
| 邮箱（文件内容） | 只有占位符 |
| `samples/` 两个样本 | **虚构数据**，不是隐私（「小鹿」是刻意选用的化名） |
| **提交元数据邮箱** | **42 个提交全部是一个真实邮箱** ← 唯一真问题 |

**关键认知**：姓名守卫扫的是**文件内容**，而邮箱不在任何文件里 ——
它在 `commit` 对象的 author/committer 字段里。GitHub 把每个提交的作者邮箱
明明白白印在提交页和 API 上，公开仓库里任何人都能翻。
**「文件干净」不等于「没泄漏」，这是另一条通道。**

（顺带排除了一个虚惊：扫描时命中过一串 11 位数字，看着像手机号，
追下去发现是某个 commit hash 中间的一段。）

#### 做法

1. 把本仓库的提交身份改成匿名 noreply 邮箱；
2. `git filter-branch --env-filter` 重写**全部 43 个提交**的 author 与 committer，
   同时用 `--tag-name-filter cat` 让 tag 跟着走；
3. 删除 `refs/original/*` 备份引用 + 清 reflog + `git gc --prune=now` ——
   **这一步不能省**：`git log --all` 会把 `refs/original` 里的旧提交一并扫到，
   不清理的话守卫仍然会读到旧邮箱；
4. 守卫扩展到这条通道：`test_commit_metadata_does_not_carry_a_real_email`，
   只判断「是不是匿名形态」，**不点名任何具体地址** ——
   守卫的职责是让某个字符串不出现在仓库里，它自己就不能是那个字符串。

重写前先记录了「旧 tag → 旧 commit」映射，重写后按新链顺序一一对应，
再按新编号重建 tag。

### 11.6 我自己犯的两个错（都是 `git add -A`）

1. `filter-branch` 的工作目录 `.git-rewrite/`（含全部 ref 的旧 hash 快照与
   「旧 → 新」映射表）被 `git add -A` 带进了提交并推送 —— 50 个文件。
   检查后确认**不含任何隐私**，但它是纯内部产物，不该入库。
   已从提交移除，并在 `.gitignore` 里钉死这条规则。
2. 同一次 `git add -A` 还把两个一次性临时脚本（`_archive_releases.py`、
   `_tagmap.json`）带进了提交。同样清除。

**教训**：重写历史期间工作区会出现工具自己的中间目录，
这时候 `git add -A` 是危险的；应该 `git add` 明确列出的路径，
或者提交前先看一遍 `git status`。

## 十四、工程方法与踩坑总表

### 14.1 贯穿始终的四条做法

1. **先复现，不猜。** 关窗卡死如果不测 CPU，「找耗时操作」会把人带偏几小时。
2. **静默失败最危险。** 不报错、只给错结果的问题（量纲、覆盖、状态串）要优先找出来。
3. **守卫要能被反证。** 新测试必须在**旧代码上失败过**，否则它只是一条好看的注释。
4. **文档写清「为什么」。** 决定和取舍比结论更容易被遗忘。

### 14.2 踩坑总表（按类型）

| 类型 | 具体坑 | 一句话教训 |
|---|---|---|
| **静默失败** | facts 唯一键把一对多建模成字典，「喜欢猫」被静默覆盖 | 静默覆盖比报错危险得多 |
| | `available` ≠ `ready`：库在就算「已完成」，权重没下 | 状态判断要问「能不能真的干活」 |
| | `GetProcessMemoryInfo` 静默返回 0 | 不报错但结果全错，比崩溃难查 |
| | 微信适配器少了 `iter_blocks`，从第一个提交起就崩 | 只测一条路 = 没测 |
| | `_resolve_map` 把候选表当实际列名，嗅探说 0.85 分却读不出 | 嗅探和解析必须说同一套话 |
| | `_STOP.set()` 全仓没有消费者 | 注释里的承诺要 grep 验证 |
| | `python -m app.desktop` 下有两个模块实例 | 状态串了会伪装成功能坏了 |
| **工具在骗你** | exe 里 grep 字符串判模块在不在包 | 用权威接口，并先用已知为正的样本校验探针 |
| | `txt in acc`（list）不是子串匹配 | 探针自己错了会说「修复没生效」 |
| | `blur` 能挡眼睛挡不住 OCR | 脱敏要改数据，不是改样式 |
| **验证方法** | 连到了 87xx 上遗留的旧进程 | 手工验证换端口 + 核对数据目录 |
| | 测试装置「先出声后开录」，句首丢失 | 时序错误会伪装成能力问题 |
| | 反证替换不忠实（只改一处），于是「通过」 | 通过了的反证也要被怀疑 |
| | 本地全绿但 CI 红：改了公共代码只跑部分测试 | CI 的价值是「不会忘记跑」 |
| **构建打包** | 「静态分析看不见」被推广过头（函数内 import 其实看得见） | 别把一条规则推广到它不成立的场景 |
| | `hf_xet` 白占 9 MB，功能零影响所以测试永不报警 | 体积回归只能靠量，不能靠测试 |
| | 错误话术缺「缺组件」分支，把用户指向修不好的方向 | 「合理但方向错误的建议」最可怕 |
| | onedir vs onefile：onefile 启动解压到随机目录，数据像丢了 | 打包形态的选择要以「数据在哪」为准 |
| **历史重写** | 顺序 replace 让 `0.6.0→0.2.0→0.1.0` 连环降级 | 映射替换必须一次查表 |
| | 文件重命名互相覆盖 | 先给「被占用的目标名」让路 |
| | `git add -A` 把 `.git-rewrite/` 和临时脚本带进提交 | 重写历史期间不用 `git add -A` |
| | `refs/original/*` 不清，守卫仍读到旧邮箱 | 重写后必须 gc --prune=now |
| **多进程/线程** | UI 线程里同步 `evaluate_js` 死锁（`syncContextTaskScheduler`） | semaphore.acquire 没有超时，互等必然死锁 |
| | 第二次双击开出的窗口是空壳，服务在第一个进程里 | 先问「这个动作作用到哪个进程上了」 |
| | `try` 包太宽，把成功结果和收尾失败搅在一起 | catch 会把 `renderBundle` 的成果擦掉 |
| **前端无编译器** | `loadChats` 被删了但 5 个调用点还在 | 单文件 + 零构建要自己补静态守卫 |

### 14.3 本机环境坑

| 坑 | 说明 |

| `Add-Type` 被安全策略拦下 | 用 .NET 内置成员 `Process.CloseMainWindow()` / `Responding` 等价替代 |

### 15.2 明确没做的

1. **Prompt 调优仍是最大的质量缺口**（没有变过，优先级一直第一）。
   其他所有功能都建立在「模型给出的分析够准、建议够好」这个前提上。
   默认 Mock 引擎让整条链路能跑，但建议内容是空的 ——
   **这是唯一一个「不填 API Key 就无法推进」的缺口。**
2. **WebView2 的 400 MB 刻意没动**。能压，但要改渲染参数，副作用面太大而收益不确定。
   **要压得先做一整轮界面回归。**
3. **没有给用户一个「低内存模式」开关**。`--browser` 已经能省掉整个 WebView2 进程组
   （主进程 ~74 MB），但它是个命令行参数，界面上没有入口。
4. **导出未覆盖 `engine_runs` / `activity_log`**（隐私要求只做了一半）。
5. **`delete_person` 删对象级人物设定、但不删对象级事实**（假设：事实属不可再生记忆资产）。
6. **旧提交在 GitHub 上仍有缓存视图**：重写历史会改变 hash，但 GitHub 对旧 SHA
   可能仍有缓存。彻底清除需删库重建或联系 Support，**尚未做**。
7. **`_pick` 兜底 `generic` 是一次有代价的取舍**：它能给出最能指路的失败提示，
   代价是极端情况下会少一点容错。
8. **本地 `release/` 里还有历史 zip（约 300 MB）**：在 `.gitignore` 里、不会上传，
   属于本地构建中转，删不删由你决定。
9. **关窗协商那 5 秒超时是拍的**。真实环境下 `evaluate_js` 通常在几十毫秒内返回；
   这个值只是「兜底别卡太久」的上界，没有实测依据。

## 十六、可复用经验

1. **先复现，不猜。** 关窗卡死如果不测 CPU，「找耗时操作」会把人带偏几小时。
   测出「CPU 纹丝不动」才把方向扭到「找互等」。

2. **守卫必须先在旧代码上失败过。** 不会失败的断言只是一条好看的注释。
   本项目每一条关键守卫（`loadChats`、`inferred`、真 `start()`、BLAS 限流、关窗死锁）
   都做过这个反证 —— 而反证过程中又抓出两处「替换不忠实」。

3. **静默失败 > 崩溃。** 崩溃至少有栈；静默失败只会让你对着一个漂亮的全 0 表格
   或一个缺了一半的画像怀疑自己。

4. **验证清单要按代码路径列，不能按用户功能列。**
   「语音能用」这种条目会掩盖「内部有三条路径、你只走通了一条」。

5. **单文件 + 零构建 = 没有编译器兜底。** 删除/重命名是跨文件改动，
   而测试只记得「现有断言还成立」。得自己补静态守卫（`symtable` / JS 名字定义检查）。

6. **一个 `try` 包得太宽，会把「成功的结果」和「收尾时的失败」搅在一起。**

7. **多进程 + 单服务时，先问「这个动作作用到哪个进程上了」。**
   「谁持有状态」比「谁能画出界面」重要得多。

8. **隐私有三条独立通道**：文件内容、提交元数据、截图/文档。
   守了第一条不等于守住了后两条。

9. **脱敏要改数据，不是改样式。** `blur` 挡得住眼睛、挡不住 OCR。

10. **重写历史期间不要用 `git add -A`**；重写后必须清 `refs/original` + `gc --prune=now`。

11. **映射式替换必须一次查表**，绝不顺序 replace；文件重命名要先给目标名让路。

12. **「碰巧能工作」和「保证能工作」之间要留一道显式声明**（隐藏导入、
    环境变量、动态 import）。

13. **测不了全部，就把能测的那部分固化下来**，别因为「测不全」而一条都不测
    （CI 里的编码防护就是这么来的）。

14. **错误提示里，「合理但方向错误的建议」比「没有建议」危险得多。**

15. **内存问题先分层测量，别猜。** 先量空进程基线，再逐个加依赖，
    才能发现「780 MB 是 import 交的，不是自己的代码」。
