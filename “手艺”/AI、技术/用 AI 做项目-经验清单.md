# 用一个 AI 会话做出能用的项目 — 经验清单

> 来源：WingMan（聊天僚机）项目，2026-10 从零做到 v0.2.0 发版、重编号、归档、清隐私。
> 下面每一条都是**真的踩过**才写下的，不是通用建议。

---

## 0. 这份东西怎么用

新开一个窗口做新项目时，**把这份文件整个贴给 AI**，再补充这个项目本身的信息。
它能省掉大量「AI 用最自然但最危险的写法把事情搞坏」的返工。

配套还有一个更短的版本，用来生成交接文档：[[通用交接文档生成提示词]]。

## 1. 开工前：先把边界划出来

**说清楚「什么不能碰」。** 「全权交付」式的指令会让 AI 一路做到发版——
效率很高，但它同时也会在没问你的情况下去动别的东西。开新项目时就交代：

- 只能在这个项目目录里改，不要碰我的其他目录
- 不能删文件 / 改系统配置 / 动我的知识库，除非我明确说了
- 破坏性操作（删数据、重写历史、强推）**动手前必须先问我**

**给 AI 一个「先摸清现状」的义务。** 涉及不可逆操作时，要求它先把现状列出来
（有几个版本、几个附件、多少体积），再给选项和代价。WingMan 那次删 7 个 Release、
9 个附件（约 380 MB），就是因为先清单后才敢动。

**AI 会把「有意的设计」误判成 bug。** WingMan 里 `samples/` 用了虚构化名「小鹿」，
是上一轮隐私清理时**刻意**定的，还有专门的守卫测试钉着。但 AI 第一次扫到时
差点当成隐私漏洞要清掉 —— 它没读项目历史。所以：**让 AI 先读 CHANGELOG 和测试，
再判断某样东西该不该存在。**

## 2. 排查：先复现，再动手改代码

**「总会这样」= 确定性故障，值得复现。** 用户说「点右上角叉**总会**卡住」——
「总会」说明不是偶发，能稳定复现，也就一定能找到根因。

**区分「在等」还是「在算」。** 这是判断死锁最快的一招：

| 现象 | 含义 |
|---|---|
| CPU 时间纹丝不动（数字几秒不变） | 在**等** —— 死锁 / 阻塞 |
| CPU 时间持续增长 | 在**算** —— 只是慢 |

WingMan 的关窗卡死实测是 CPU 死死钉在 2.0625s 连续 8 秒不变 → 直接判死锁，
省掉了「优化算法」这条错误路线。

**判断窗口是否「未响应」，用系统自己的判据。** Windows 上是 `IsHungAppWindow`；
PowerShell 的等价物是 `Process.Responding`；发关闭信号是 `Process.CloseMainWindow()`。
（本机 `Add-Type` 被安全策略拦，所以走 .NET 内置 API，效果一样且不用编译 C#。）

**「服务端没日志」本身就是线索。** 界面报错但后端一条记录都没有 → 请求根本没到，
别急着进业务代码翻。WingMan 的 `Failed to fetch` 最后定位到 uvicorn 默认
5 秒 keep-alive 超时，跟业务逻辑毫无关系。

**分层量测，别猜。** 「程序占 800 MB」这种结论要拆开看：空 Python / 只导依赖 /
完整服务，三组对照，才知道钱花在哪。实测结果是自己的代码只占 11 MB，
其余全是 `import numpy` 时 OpenBLAS 按核数开的线程池。

## 3. 改动：批量替换和删除是两个高危区

### 3.1 顺序替换会连锁污染

改版本号时映射是 `0.6.0→0.2.0`、`0.2.0→0.1.0`。如果写成顺序 `replace`：

```
0.6.0 → 0.2.0 → 0.1.0     ← 一个版本被连降两级
```

**必须一次性查表替换**（原值 → 新值，每处只替换一次，不递归）。
而且脚本**不能重复跑** —— WingMan 那次因为对同一批文件跑了两遍，
README 的下载链接变成了 v0.1.0、STATUS.md 有 22 处被错误降级。

### 3.2 改完必须抽查「语义」，不能只核对数字

批量替换后逐个数一遍「替换了几处」是不够的 —— 数字变了不代表句子还通顺。
那次 `WingMan-0.5.0` 被全局替换成 `0.6.0`，结果 **v0.5.0 的发行记录那一行也变了**，
历史记录被篡改。**改完全文搜一遍旧值，重点看「记录历史」的段落。**

### 3.3 删功能比加功能更容易留垃圾

WingMan 撤下通话语音时，`grep asr` 干掉 60 多处引用，测试**当时全绿**——
但复查发现 `bus.py`（只服务已删的 SSE）、预检里两个永远不会通过的检查项、
`.env.example` 里 14 个已删配置键、三处文档字符串…全都还活着。

**共同点是它们都不报错。** 测试全绿只说明「现有断言还成立」，
不等于「删干净了」——因为没人给「这东西不该再存在」写断言。

删除类改动要四层查：

1. `grep` 关键词，逐条看是不是现存功能
2. 对每个要删的模块问「**谁在调用它**」，调用方也删了才算干净
3. 跨文件的章节号 / 文件名引用，改完统一再搜一遍
4. **回头读一遍「面向人的说明文字」**（README、脚本 docstring、`.env.example`）——
   它们描述「有哪些功能」，最容易整段过期，且没有编译器管

## 4. 测试：守卫必须先在旧代码上失败过

**一条从没在旧代码上失败过的测试，不是守卫，只是好看的断言。**
每条关键守卫都要做**脚本化反证**：把修复逐条改回旧写法 → 对应用例必须失败 → 自动还原。

**反证本身也要被怀疑。** WingMan 那次有一条反证「通过」了，但其实是我
复现旧代码复现得不够忠实 —— 只改回了外层调用，却留着内层的线程包装，
那是个现实中不存在的混合状态。修法是让反证脚本支持
「**两处必须一起改回**」而不是单点回退。

**只在本地平台跑的测试，覆盖不到「导入」这件事。**
`from ctypes import wintypes` 在 Windows 上永远正常，
在 Linux 上**模块级 import 就抛异常**（`_type_ 'v' not supported`）。
表现是本地全绿、CI 全红，而报错跟功能名看起来毫无关系。
→ 一个功能可以只在 Windows 可用，但它的模块**不应该只在 Windows 上能导入**。

**单文件、无构建步骤的前端没有编译器兜底。**
改 JS 时删掉一个函数、5 个调用点没跟着改 —— 语法完全合法，测试也全绿，
但 `init()` 里那个调用点抛 `ReferenceError` 会让**后面的初始化全部不执行**。
→ 补一条静态守卫：把脚本里所有 `名字(` 抠出来，减去所有定义过的标识符。

**顺手记一个 `try` 的教训**：包得太宽的 `catch` 会把「成功的结果」和
「收尾时的失败」搅在一起 —— 用户看到「分析坏了」，其实是刷新列表那步失败，
`catch` 把刚渲染好的结果擦掉了。

**验证环境要干净。** 想验证「某个环境变量有没有生效」，不能用测试进程自己
（它早就导入过目标库了），**必须开 subprocess** 从零开始跑。

## 5. 发版：口径比数字重要

**版本号只定义一个地方，但前端那份要跟着改。**
`backend/app/__init__.py` 是单一来源，前端的 `BUILD` 常量必须同步，
用一条测试钉住「两处一致」。漂移的后果不是崩溃，而是**用户报 bug 时说不清装的是哪个包**。

**发行说明写「为什么改 / 做了什么 / 修了什么」**，不要只列 commit。

**校验和要说清能证明什么、不能证明什么。** 这是一个真实撞过的坑：
`--check` 连跑两次字节相同 → 顺手写下「重跑构建会得到同一个包」。
**但 `dist/` 是 PyInstaller 生成的，那个构建不是逐字节确定的** ——
同一份源码连构建两次，219 个文件里有 2 个不同，zip 的 SHA256 跟着变。
→ 正确口径：**能证明你下到的文件完整、中途没被换过；不能证明重跑构建结果一致。**
修完一个坑写下的总结句，要连它覆盖的范围一起验一遍。

**发版后必须实测，源码模式和打包版各跑一遍。** 别只信测试。

**归档旧版本时：留文本、不留二进制，并说明原因。**
WingMan 把 6 个旧版本收成纯文本（保留「做了什么 / 修了什么」的过程记录），
删掉全部附件 —— 理由是功能已被最新版完全覆盖，留着只会让人下一个过时的包。

## 6. 隐私：文件内容干净 ≠ 没泄漏

**这是整个项目里最反直觉的一条。**

WingMan 全历史扫下来，文件内容**完全干净**：无真人姓名、无手机号、无身份证、
无真实密钥，扫出来的「可疑项」全是无害占位符。

**但唯一的真问题不在文件里 —— 在 commit 对象的元数据里。**
42 个提交的作者/提交者邮箱是一个真实的 QQ 邮箱，GitHub 把它印在每个提交页和 API 上。
**这是一条完全独立的泄漏通道，扫文件永远扫不到。**

### 重写历史清邮箱，四步一步都不能省

```bash
# 1. 先改当前身份（只影响之后的提交）
git config user.email "<github用户名>@users.noreply.github.com"

# 2. 重写全部历史
FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch --env-filter '
export GIT_AUTHOR_NAME="..."
export GIT_AUTHOR_EMAIL="...@users.noreply.github.com"
export GIT_COMMITTER_NAME="..."
export GIT_COMMITTER_EMAIL="...@users.noreply.github.com"
' --tag-name-filter cat -- --all

# 3. ★ 删备份引用 + 清 reflog + gc —— 省掉这步，git log --all 还会扫到旧提交
git for-each-ref --format="%(refname)" refs/original/ | xargs -n1 git update-ref -d
git reflog expire --expire=now --all
git gc --prune=now

# 4. 强推（分支和 tag 都要）
git push --force origin main
git push --force origin <tag>
```

**重写历史期间 `git add -A` 是危险的。** WingMan 那次连带提交了两样东西：

- `filter-branch` 的临时目录 `.git-rewrite/`（50 个文件，含全部 ref 的旧 hash 快照）
- 两个一次性脚本和 hash 映射表

**教训：重写历史期间改用 `git add <明确路径>`，并把临时目录写进 `.gitignore`。**

**守卫要覆盖两条通道**（文件内容 + 提交元数据），而且**守卫本身不写出那个具体值**——
否则守卫文件自己就成了泄漏源。写法是**只判断「是否匿名形态」**：
邮箱必须以 `@users.noreply.github.com` 结尾（或用 `noreply` 之类规则匹配）。

**最后一条认知**：GitHub 对旧 SHA 可能仍有缓存视图，**彻底清除需要删库或联系 Support**。
强推不等于「从来不存在」。

## 7. 文档：分清「流水」和「快照」

**两类文档，过期速度完全不同：**

| 类型 | 例子 | 特点 |
|---|---|---|
| **流水** | CHANGELOG、DEVLOG、全流程报告 | 追加式，写完就不动，基本不会过期 |
| **快照** | README、STATUS、ROADMAP | 描述「当前是什么样」，**最容易过期** |

**每次改完功能/发完版，回头读一遍快照类文档。** WingMan 的 README 在归档后
还写着旧体积（31 MB）、旧包叙述（标准版/完整版）、一个指向已失效 commit 的 CI 链接。
这些都不会报错，只是安静地误导读者。

**报告要自包含**（代码内嵌、不依赖附件），方便全文搜索和长期阅读。
**归档两份**：Obsidian 知识库 + 工作区各一份，`md5sum` 核对一致。

## 8. 本机环境的几个已知坑（可直接抄）

| 坑 | 应对 |
|---|---|
| 大模型/matplotlib 画图中文变方块 | 指定中文字体（如 `Microsoft YaHei`） |
| Python 进程内存虚高 700+ MB | `import numpy` 时 OpenBLAS 按**逻辑核数**开线程占内存。在**包的最外层 `__init__.py`** 设 `OPENBLAS_NUM_THREADS=1` 等一组变量 —— 必须早于 numpy 被导入，放 `config.py` 里已经晚了 |
| PowerShell 里 `Add-Type` 被安全策略拦 | 改用 .NET 内置 API（`Process.Responding` / `CloseMainWindow()`），不编译 C# |
| 查 CI 状态没有 `gh` CLI | 走 GitHub REST API：`/repos/<owner>/<repo>/actions/runs?head_sha=<sha>`，公开仓库无需 token |
| 在 WorkBuddy 里跑 DSH / pnpm 命令失败 | 先 `unset NODE_OPTIONS`（注入的 shim 会拦删除导致锁超时） |
| 每次调接口拿不到环境变量 | WorkBuddy 的 bash 会话**不共享 shell state**，每次先 `source ~/.bashrc` |

**打包相关的坑**：
- `build_exe.py --clean` 会被批量删除护栏拦下 → 不加 `--clean`，让 PyInstaller 自己覆盖
- 「未响应」不要用任务管理器强杀 → 会跳过优雅退出、打断正在写的数据库

## 9. 一条贯穿始终的原则

**最贵的一类 bug 是「不报错、但结果不对」。**

自动采集要判断「这个候选密钥对不对」，最省事的判据是「解密结果非空」——
而它**必然恒真**：拿错密钥解出来的是 4096 字节随机数据，非空而且永远非空。
于是程序拿着一堆垃圾一路「成功」下去，把乱码当消息写进用户的记忆里。

另一处：判定「有没有认出登录账号」时用 `if "命中登录账号" in reason:`，
而未命中的候选写的是「**未**命中登录账号」—— 一个是另一个的子串，
于是「没认出我是谁」被一路当成认出来了。

**所以凡是要写判据的地方，先问一句：「它会不会恒真 / 会不会互相包含？」**
判据写错比算得慢致命得多：慢只是慢，**判据错是永远找不到正确答案，而且还在装没事。**

同理，把**机器判据**和**给人看的理由**分成两个字段 ——
别让「给人读的文案」变成代码分支的判断依据。
