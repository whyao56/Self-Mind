## 一、为什么选这个题

简历项目的门槛不是「做过」，而是**有难度、有数据、有取舍**：

1. **有难度**：不是增删改查。能说出「这里别人做不好、而我这么解决了」的一句话。
2. **有数据**：QPS、延迟、召回率至少有一个能量化。没有数字的项目在简历上等于没有。
3. **有取舍**：每个技术选型都能回答「为什么不用另一个」。

选「垂直领域 RAG 问答」的理由：入门成本极低（Python + 现成模型就能跑），
但天花板极高（切块、检索、重排、评测、拒答），且面试官对这条链路问得很细，
最容易拉开差距。**刻意避开 Agent 框架**——那个阶段写出来也讲不清。

## 三、架构

两条链路，其余代码都在为它们服务。

```
离线建库  scripts/ingest.py
  语料 → loader（md/txt/py/pdf）→ chunker（3 策略 + 标题上下文前缀）
       → embedder → 向量索引落盘
       → BM25 倒排索引落盘
                ↓
        data/index/  chunks.jsonl + vectors.npy + bm25.pkl + manifest.json

在线问答  Retriever + RAGPipeline
  问题 ─┬─ 向量通道 ─→ Top-20 ─┐
        └─ BM25 通道 ─→ Top-20 ─┴─ RRF 融合 → Top-10 → 重排 → Top-5
                                                   → prompt（带 [n] 编号）
                                                   → LLM → 答案 + 引用 + 分阶段耗时
```

核心模块职责：

- `text.py` 中英文分词（jieba，可降级到单字+二元组）、分句、分段
- `embedding.py` 向量后端抽象：`hashing`（零依赖）/ `sentence_transformers`
- `ingest/chunker.py` 三种切块策略：`fixed` / `recursive` / `semantic`
- `retrieve/bm25.py` BM25 手写实现
- `retrieve/hybrid.py` RRF 融合与加权融合
- `retrieve/reranker.py` 重排：`lexical`（零依赖）/ `cross_encoder`
- `generate/` prompt 模板、引用解析、拒答判定、多后端 LLM
- `pipeline.py` 端到端编排，**API / CLI / 评测共用同一入口**
- `eval/` 评测与消融实验

## 四、实测数据

40 条标注问题，8 篇文档、57 个切块（chunk_size=512）：

| 检索方案 | recall@1 | recall@3 | recall@5 | MRR | 平均检索耗时 |
|---|---|---|---|---|---|
| 纯向量 | 0.725 | 0.800 | 0.850 | 0.792 | 9.8 ms |
| 纯 BM25 | 0.725 | 0.825 | **0.950** | 0.803 | 0.1 ms |
| 混合（RRF） | 0.725 | **0.850** | 0.875 | 0.800 | 0.2 ms |
| 混合 + 重排 | 0.725 | 0.825 | 0.925 | 0.802 | 4.2 ms |

生成质量（离线抽取式基线）：字符级 F1 0.245、关键术语命中率 0.700、误拒率 0.025。

### 这组数字里最重要的一条发现

**纯 BM25 反而最强。** 这不是实现有问题，而是原理上注定的：

1. 默认的零依赖向量后端是「词袋 + 哈希 + IDF 加权」，与 BM25 用的是**同一批
   词项统计**。两路召回高度同源，融合自然带不来互补信息——调参也救不了。
2. 评测集的标准片段多是**专有名词型**目标（`:path`、`GZipMiddleware`、
   `use_cache=False`），这类查询恰恰是 BM25 的主场。

**结论**：想宣传「混合检索提升 XX%」，必须先把 `embedding.backend` 换成真实
语义向量再重跑。用零依赖方案的数字去讲混合检索的收益，那是假数据。

延迟上的结论是明确的：BM25 只要 0.1 ms，向量 9.8 ms，重排再加 4.2 ms。
重排的代价在「检索 + 生成」的总延迟里可以忽略，所以默认开启。

## 五、关键设计与背后的理由

| 决策 | 理由 |
|---|---|
| 融合用 RRF 而非加权求和 | 余弦相似度在 [-1,1]，BM25 分数无上界，量纲不可比；min-max 归一化又受离群值严重干扰。RRF 只看排名，量纲问题直接消失。`k=60` 取原论文默认值。 |
| 拒答阈值不基于检索分数 | RRF 融合分量级约 0.016，覆盖率型重排是 [0,1]，同一阈值换后端就失效。改用**与后端无关**的「查询词 IDF 加权覆盖率」。 |
| 评测标 `gold_snippet` 而非 `gold_chunk_ids` | chunk_id 由切块算法生成，改 `chunk_size` 就全变，评测集在消融实验里直接作废。标原文片段可跨配置复用，还能自动校验。 |
| 切块在标题段内独立执行 | 跨段会把两个主题塞进同一个块，稀释语义并让引用溯源变模糊。代价是块长分布不均匀，靠 `min_chunk_size` 控制。 |
| 把标题路径作为 chunk 前缀 | 用户问「基于类的依赖」时，标题里带这两个词的块天然更容易被召回。代价是占用 10~20 字符上下文预算。 |
| 默认用 numpy 向量库而非 Chroma | 保证 clone 下来零依赖跑通全链路和评测。语料万条内内存暴力检索是毫秒级，真正瓶颈在切块质量和向量模型。接口抽象，一行配置切 Chroma。 |
| 不用 LangChain | 项目价值就在自己实现检索链路；全封装之后说不清问题出在哪。先自己写一遍，之后再引入做对比并说明代价。 |
| 保留离线抽取式基线 `MockLLM` | 让无 API Key 环境能跑通、能出分数；同时作为生成环节的对照基线——没有基线，「提升多少」没有参照。 |
| 索引落盘写 `manifest.json` | 记录建库参数。启动时校验行序与向量化后端是否匹配，不一致就报错而非默默给错结果。评测报告的参数一律取自 manifest。 |
| API 按请求传参而非改单例属性 | 流水线是进程内单例，并发请求下改共享属性会互相污染。有测试专门守这条。 |
| 配置三级覆盖 CLI > 环境变量 > YAML | 环境变量用 `RAG__段__键`（双下划线代表层级，因为 Shell 和容器编排多不接受变量名带点）。改配置不必重建镜像。 |

## 六、过程中踩到并修掉的真实问题

按发现顺序，都是「代码能跑但结果错」的类型：

1. **循环导入**：`ingest.indexer` 用 `retrieve.bm25`，而 `retrieve/__init__`
   又导入 `retriever`（依赖 indexer）。修法：`retrieve/__init__` 用 PEP 562 的
   模块级 `__getattr__` 惰性暴露 `Retriever`。

2. **文本归一化把中文标点改成英文**：原先用 `unicodedata.normalize("NFKC")`，
   它会把中文的 `，。：（）` 一并转成半角 ASCII。改成只映射全角字母数字与表意空格的
   白名单映射表。

3. **引用路径重复**：chunk 的标题路径第一段就是文档 H1，与 `title` 字段重复，
   显示成「路径参数 > 路径参数 > 包含路径的参数」。在 `Chunk.display` 里去掉重复前缀。

4. **抽取式基线把标题行当成答案句**：切块文本带标题前缀，标题行因含关键词而
   被打高分，导致答案以标题开头。改为把标题路径作为噪声传给生成后端并过滤。

5. **评测报告参数与实测对不上**：报告从「当前配置」读切块参数，但索引可能是用
   另一组参数建的（`--index-dir` 指向别处），于是 chunk512 的实验被标成 320。
   改为一律从 manifest 读取，并以 manifest 指纹给实验命名。

6. **两个测试写错了**：一个忘了把 `embed_fn` 传给 Chunker（走了兜底路径），
   一个假设切块是全文滑窗（实际在标题段内独立执行）。修测试的同时把这个
   设计特性写进了模块文档。

7. **首次查询延迟异常**：jieba 首次分词有约 360 ms 预热开销，之后降到毫秒级。
   已记录，服务化时应在启动阶段预热。

## 八、简历怎么写 / 面试怎么讲

**简历条目模板**（数字要换成自己实测值，不要抄本文）：

> **文档知识库问答系统**｜独立开发｜Python / BM25 / 向量检索
> - 实现 BM25 与稠密向量的混合检索（RRF 融合）+ 两阶段重排，
>   自建 40 条标注评测集，Top-5 召回率从 X% 提升至 Y%
> - 设计基于查询词 IDF 加权覆盖率的拒答机制，误拒率 Z%，回答可追溯至原文小节
> - Docker Compose 一键部署，平均检索延迟 X ms；55 个单测 + CI 全绿

**面试会被追问的点，以及答案在哪**：

| 追问 | 应答要点 |
|---|---|
| RRF 里的 k 为什么取 60 | 原论文默认值；k 越大头部差距越小。有测试验证 k 变大时头部两名分差缩小 |
| 为什么不用加权求和 | 量纲不可比 + 归一化受离群值干扰 |
| 召回和重排为什么要分开 | 双塔结构无法建模词间交互；交叉编码器能但计算量随候选线性增长 |
| BM25 公式 | 手写在 `retrieve/bm25.py`，IDF 与长度归一化都有单测 |
| 怎么知道效果变好了 | 40 条标注集 + 四个指标 + 四组消融，一条命令复现 |
| 幻觉怎么控制 | 上下文编号 + 强制标注来源 + 基于覆盖率的拒答（实测误拒率 0.025） |
| 为什么不直接上 LangChain | 先自己实现理解取舍，之后再引入并说明代价 |
| 延迟瓶颈在哪 | `trace.stages_ms` 分阶段数据；BM25 0.1 ms / 向量 9.8 ms / 重排 4.2 ms |

**最能加分的一句话**：主动说「默认向量后端是零依赖哈希实现，
它与 BM25 同源所以融合收益有限，这正是我需要换成真实语义向量重跑的原因」。
承认局限并给出验证计划，比只报好消息可信得多。

## 九、复现方式

```bash
cd rag-kb
pip install -r requirements.txt

make ingest        # 建库（示例语料，秒级）
make eval          # 四组消融 + 答案质量 → 自动生成 docs/benchmark.md
make test          # 55 个测试
make lint          # ruff
make serve         # 网页界面 http://127.0.0.1:8000

make ingest-full   # 抓取完整 FastAPI 官方文档后重建（需联网）

# 做一组自己的消融实验
python scripts/ingest.py --set chunking.chunk_size=512 --out data/index/exp-512
python eval/run_eval.py --index-dir data/index/exp-512 --name chunk512
```
