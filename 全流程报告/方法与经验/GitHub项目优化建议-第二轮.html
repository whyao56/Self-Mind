3.1 安全与软件供应链（security-supply-review.md，768 行）

一句话：三个仓库的代码本身没有发现可利用漏洞，但安全工程化几乎是空白——没有依赖漏洞监控、没有漏洞上报通道、TideWatch 的 CI 权限甚至没声明、本地 HTTP 服务零鉴权。短板不在"写错了什么"，而在"没有任何机制在出错时拦住你"。

最好的一个消息：工作区扫描无明文密钥；已跟踪文件无敏感文件；Etude 的路径穿越已被正则白名单挡住；WingMan 前端每一处插值都套了 esc()（256 次）——是"靠自觉但有自觉"，不是"没意识"。

条目优先级要点
P0-S1 本地服务零鉴权🔴 P0WingMan 默认绑 127.0.0.1（正面的），但 --host 可改 0.0.0.0 且无任何警告；两个服务都无 Token、无 TrustedHost → 同机任意网页（DNS rebinding）或局域网设备可读写全部聊天数据
P0-S2 Etude 许可证冲突🔴 P0打包内含 GPL-3.0 的 edge-tts，而整仓声明 MIT。已核实：PyPI 元数据 License: GNU General Public License v3 (GPLv3)（查询日期 2026-10-13）
P1-S3 零依赖漏洞监控🟠 P1无 Dependabot / SCA / SBOM / 哈希校验。最该先做的一项
P1-S4 TideWatch CI 无 permissions:🟠 P1另两个仓库都声明了 contents: read，只有它没有
P1-S5 CVE-2024-53981 边界🟠 P1python-multipart>=0.0.9 下界覆盖受影响区间；但锁定集 ==0.0.32 是安全的，风险只在"不走锁定集"的路径。定级 P1 合理
P1-S6 .gitignore 拦不住 .env.*🟠 P1WingMan 拦 .env / .env.local 但不拦 .env.production 这类
P1-S7 无 SECURITY.md🟠 P1见 Tier 0
P1-S8 WingMan 85 处 innerHTML 无守卫🟠 P1与前端维度独立命中同一条（前端定 P0），说明两个独立视角都认为它重要
P2-S10 %TEMP% 固定文件名🟡 P2CWE-377；且 debug 日志可能落盘分析结果

Etude 许可证冲突的三个选项（需要你决策，我不替你选）：

  • A. 换掉 edge-tts —— 改用 Apache-2.0/MIT 的本地 TTS（如 Kokoro/Piper）。代价：失去微软神经音色、体积增大、需要模型下载；收益：彻底解决，且顺带解决"合成必须联网"这个隐私矛盾（你的产品定位是本地优先）
  • B. 保留但合规 —— 整个 Etude 改声明 GPL-3.0，并在发布页提供对应源码。代价：MIT → GPL 是不可逆的收紧，未来若想闭源/商业化就没路了
  • C. 隔离 —— 把 TTS 做成"用户自行安装的可选插件"，不进发布包。代价：首次使用多一步安装；收益：主仓保持 MIT
我的倾向写在明细报告里，但这是你的产品决策。唯一不能选的是"继续发 MIT + 内含 GPL 的 exe"。

3.3 发布分发与版本治理（release-engineering-review.md，822 行）

一句话：三个项目发布内容的质量很高（发行说明印 SHA256、点名包文件、写清升级会不会丢数据），但发布动作本身是"一台机器 + 一个人 + 一张手工清单"。内容越好，越说明短板不在写文档，而在过程没自动化、产物没身份、升级没通道。

条目优先级要点
P0-1 发布全手工🔴 P0三仓 .github/workflows/ 下只有 ci.yml、零发布流水线；"发布"100% 依赖本机 Windows + 开发者凭据
P0-2 两个 exe 无代码签名🔴 P0已抽验：WingMan/build/wingman.spec:141 与 Etude/build/etude.spec:157 都是 codesign_identity=None
P0-3 exe 无版本资源🔴 P0已抽验：两个 .spec 只有 name=，没有 version= → 产物对 Windows 没有机器可读身份
P1-1 WingMan 缺产物版本自证🟠 P1Etude 已有 assert_dist_version()，WingMan 没有，而它的 dist/ 策略恰好容易发错包
P1-2 Etude 打包目录无法带版本号🟠 P1用"最新 mtime"当"要发的那个"—— 这是 P1-1 一类事故的根因
P1-3 Etude 所有 Release 被标 prerelease🟠 P1/releases/latest 没有"最新正式版"可指
P1-4 版本号非单点🟠 P1已抽验：TideWatch 两处硬编码（pyproject.toml:7 + src/tidewatch/__init__.py:34）；Etude 的 README/QUICKSTART 版本无守卫。WingMan 已做到单点 + 6 条守卫测试，是三者唯一做到的
P1-6 TideWatch 无 CHANGELOG 无发行说明🟠 P1已抽验：TideWatch 目录下确无 CHANGELOG.md
P1-8 Docker 注释与实现不符🟠 P1注释自称 multi-stage，实为单 stage；镜像内用 editable 安装

本维度最好的一个消息：构建产物卫生三个仓库全部干净（git ls-files 核实无二进制/大文件入库）—— 这比多数个人项目强。

3.4 数据层可靠性与性能（data-performance-review.md，927 行）

一句话：「本地优先」意味着用户的全部资产就在一个文件里，而第一轮完全没评估过这件事的后果。本轮结论：WingMan 的那个文件没有任何备份出口，且每次导入要把它读三遍。

条目优先级要点
D-1 无任何备份 / 全量导出🔴 P0已抽验：grep -rn EXPORTS_DIR WingMan/backend 只命中 config.py:70 的定义处（定义即悬空）；搜 backup / VACUUM / iterdump 三个关键词，在 WingMan 后端零命中。对比 Etude 已有完整备份（db.py:254 backup_to() 走 VACUUM INTO、paths.py:176 backups_dir()）
D-2 导入读 3 次 + 注释与实现相反🔴 P0已抽验：read_head 的 docstring 写「避免为了判定类型把几百 MB 全读进来」，实现却是 raw = Path(path).read_bytes()[:nbytes] —— 先全读进内存再切片
D-3 substr(at,1,10) 索引失效🔴 P0已抽验：Etude/backend/app/db.py:864 是 WHERE substr(at,1,10) = ?，而索引是 idx_reviews_at ON reviews (at) —— 函数套在列上，索引彻底用不上
D-4 运行时参数只设了一半🟠 P1journal_mode=WAL 有（且 WAL 是持久设置，这点没问题），但 synchronous / cache_size / temp_store / busy_timeout 全为默认
D-5 检索全量载入向量矩阵🟠 P1且一次分析载入两遍
D-8 find_person_by_alias N×3 聚合🟠 P1为匹配一个名字把每个人的 3 条聚合查询跑一遍，采集主循环每会话 2 次
D-10 Etude 长事务持全局锁🟠 P1批量操作逐行提交 → 事务风暴
D-11 日志无轮转且落在数据目录内🟠 P1每训练包一个只增文件，会让备份体积膨胀
D-12 无任何完整性体检🟠 P1无 integrity_check、无孤儿行自检、无 VACUUM/ANALYZE
D-13 无数据保留策略🟠 P1只增不减的结构没有任何出口
D-18 Etude _JOBS 只增不减、_POOL 无 shutdown🟡 P2长驻进程资源泄漏

一个重要的口径区分（防止误解为重复第一轮）：第一轮的外键 P0 修的是增量（改 conn() 后不再产生新孤儿行）；本轮 D-12 补的是存量与可观测性（老库里已有的孤儿怎么发现、库文件是否完好、删行后空间怎么回收）。

3.5 前端工程质量（frontend-engineering-review.md，868 行）

一句话：这两个前端不是"代码写得烂"，而是"没有安全网"——WingMan 用 85 个 innerHTML 汇点 + 256 次手工 esc() 维持着一条靠自觉的安全线；两者的静态守卫都只防"写错名字"，不防"忘了转义"。

条目优先级要点
2.1 WingMan 85 个 innerHTML 零守卫🔴 P0已抽验：grep -c 'innerHTML' → WingMan 85，Etude 0。注意：第一轮建议"WingMan 照抄 Etude 的 innerHTML 守卫"实测不可行——Etude 的守卫是 grep innerHTML= 后排除 =""，套到 WingMan 上会把 85 处全部报红。WingMan 需要的是另一种机制
2.2 极淡文字对比度系统性不达标🔴 P0WingMan --dim 3.10:1（用 82 次）、Etude --fg-faint 2.50:1（用在 11.5px 小字）—— 全部低于 WCAG AA 的 4.5:1。改色板即可
2.3 两个前端都缺 aria-live🔴 P0异步加载、错误、toast 全部对屏幕阅读器静默；WingMan 90 个按钮里 0 个 aria-label
2.6 两项目都没有 CSP🟠 P1在第一轮发现"CORS 过宽 + AI 内容可能未转义"之后，CSP 是最后一道防线，而它不存在
2.8 114/140 个全局函数无边界🟠 P1顶层绑定 49 处无空值保护（$("#x").addEventListener 无 ?.）
2.9 前端零 DOM 级测试🟠 P1静态守卫挡不住"事件名大小写"这类运行期静默失效
2.10 i18n：15470 / 10776 个汉字硬编码🟡 P2建议不做（5–8 人日），只做文案集中

最重要的一条洞察（前端维度）—— 数据来源决定风险等级：WingMan 的 innerHTML 汇点风险不是均匀的，应按数据来源分档：

档数据来源风险例
A 档（最高）第三方聊天记录导入真实用户数据 + 完全不可控 → stored XSS 的天然入口。攻击者只要给你发一条特定消息，你导入后就触发导入预览 previewHTML（定义 3290、使用 3401）
B 档AI 生成内容大部分已过 esc()，但依赖每一处都记得（256 次手工调用）分析结果渲染
C 档自有静态文案基本无风险固定 UI 片段
这个分档直接决定改造顺序：不必一次处理 85 处，先把 A 档锁死（导入路径加白名单式转义或 DOM 化），投入产出比最高。 裁决说明：安全维度与前端维度对 previewHTML 的行号表述不一致（3280-3285 vs 3290/3401），主理人已读码裁决 —— 定义为 3290、使用为 3401，以 frontend-eng 为准。

两个正面的对比项（说明作者水平不低，只是没做这些零件）：

  • 两者都零 CDN、零外链字体 —— 对"离线可用"这个产品定位是正确取舍，很难得。
  • Etude 有完整的 prefers-color-scheme + 3 套 data-theme + prefers-reduced-motion（WingMan 一个都没有）。
  • WingMan 有 test_frontend_assets.py（293 行 / 8 条守卫，跑在 CI）—— 前端静态守卫比 Etude 更全面，虽然守卫错了方向。

4.1 本轮最强的一条发现：「CI 只验证最容易跑通的那条路」

两位成员从完全不同的入口独立走到同一个失效模式，并交叉核实了证据：

项目CI 实际跑的CI 没跑的（但代码里已有）
TideWatch三次安装全是 -e（editable）wheel 安装路径从来没验证过 —— 而第一轮已发现 PROJECT_ROOT = parents[2] 让 wheel 安装根本跑不起来
WingMan / EtudeMock 冒烟（模型输出永远干净）真实网络客户端代码 —— 两仓都写好了 openai_stub.py + e2e_check.py（21KB/14KB/18KB/11KB），却都没接进 CI

最硬的证据（AI 维度与发布维度交叉核实）：grep -rn "openai_stub\|e2e_check" */.github/ 的唯一命中是 Etude/.github/workflows/ci.yml:97 —— 它出现在密钥扫描的排除项里（':!scripts/openai_stub.py'）。也就是说：写进 CI 配置里唯一的一次，是为了跳过它，而不是执行它。

为什么这条最值钱：它把三个看似无关的缺口（wheel 装不上、Windows 守卫恒 skip、真实网络零覆盖）归因到同一个根因——CI 在验证"最容易跑通的那条路"，于是所有"用户实际会走的那条路"都没人验。 因此两位成员建议合并成一次 CI 改造（而不是分三次提）：新增三类 job —— 1. 发布路径（windows runner 出包 / 装 wheel） 2. 真实网络路径（起本地 stub 跑 e2e） 3. 离线降级路径 三者的共同点是零密钥、零外网、可在 PR 上跑，所以可以共用一份模板，一次评审通过。
⚠️ 流程说明（供你了解，不影响结论）：本轮有两位成员在收尾时直接交换了一次口径以避免重复（AI 维度与数据维度就 retriever.py 的内存开销归谁讲达成一致；发布维度与 AI 维度就 CI 缺口交叉核实了证据）。按团队规程，跨成员信息流本应经主理人中转；实际结果是去重更彻底、证据更硬，故予保留并在此说明。 🔧 一处执行提醒：安全维度与前端维度各自写了一个「innerHTML 守卫脚本」（check_innerhtml.py）。落地时请合并成一个，并把前端维度的「按数据来源分档」（见 §3.5 A/B/C 档）作为判据 —— 否则会出现两个脚本、两套判定、两次维护。
