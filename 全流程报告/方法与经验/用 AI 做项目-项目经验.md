## §0 一张开工检查表（打印出来用）

**开工前**

- [ ] 有歧义的地方**先问用户**，尤其是不可逆操作（删数据、重写历史、改名）
- [ ] 记下当前状态（`git rev-parse HEAD`、版本号、测试基线数），后面全都要对比
- [ ] 决定数据写在哪、配置从哪读（别等打包时才发现程序目录只读）

**每次改动**

- [ ] 新测试**先在旧代码上跑一遍，确认它失败**
- [ ] 改了公共代码 → **跑全量测试**（不是只跑相关的那几个）
- [ ] 删了/改名了一个函数 → **全文搜索所有调用点**

**提交前**

- [ ] `git status` 看一遍完整清单，**别用 `git add -A`**
- [ ] 扫文件内容里的隐私
- [ ] **扫提交元数据的邮箱**（文件干净 ≠ 没泄漏）
- [ ] 看有没有工具留下的中间目录（`.git-rewrite/`、`.venv/`、`dist/`）

**发布前**

- [ ] 构建 → 校验和连跑两次一致（证明打包那步是确定的）
- [ ] 下载页实测 HTTP 200
- [ ] 截图/文档里的界面**必须是当前版本的**

**交付后**

- [ ] 写清「这一版没做什么」和「累计没验证什么」
- [ ] 更新工作区记忆 + 归档报告

## §1 开工前先划边界

### 1.1 有歧义就问，别猜（尤其是不可逆操作）

**案例**：归档那一轮，用户说「把 0.6.0 放到 0.2.0 的位置」。
动手前确认了两件事，**两件都是不可逆的**：

- 0.2.0 要不要保留安装包？→ 保留，只是换个名字
- commit 邮箱要不要重写历史？→ 要，彻底清

如果第一条猜错（以为连包一起删），就得重新打包重发；
第二条猜错（以为只是改 config），真实邮箱会永久留在公开仓库的每个提交上。

**下次怎么做**：
- 凡涉及「删 / 覆盖 / 重命名 / 重写 / 发布」，**先列出来问**；
- 提问时给出选项和后果，不要问「你要不要怎样」（用户不知道有什么选项）。

### 1.2 先摸清现状，别按本地情况推断远端

**案例**：本地只有 2 个 tag（`v0.2.0` / `v0.2.1`），
实际远端有 7 个。**如果直接按本地情况操作，会以为「后面几个版本没发过」**，
然后「新建」一批已经存在的 tag，全乱。

第一步动作是 `git fetch --tags`，把远端 tag 全拉到本地再决策。

**下次怎么做**：动远端之前，先 `git fetch --all --tags` + 用 API 列一遍
Release/附件/tag 的真实数量，**做成一张表**（数量对得上才动手）。

### 1.3 记下基线，全程对比

**案例**：每轮报告的第一行都是这种格式：

```
> 提交 122ff93 · tag v0.6.0 · 测试 240 passed / 1 skipped
> 起点：7f69240（v0.4.0）→ 规模：29 个文件，+2691 / −152 行
```

没有基线，就说不清「这一轮到底改了什么」；
改坏了也发现不了（不知道原来多少）。

**下次怎么做**：开工第一条命令 `git rev-parse HEAD` + 跑一次全量测试，把数字记下来。

### 1.4 数据目录必须在动手前定好

**案例**：打包成 exe 后，`backend/data/` 变成可能只读的目录。
到那时才发现，就得把「数据写哪」这条链路全部改一遍。
正确做法是**在第二轮打包时就一起做掉**：冻结态下把可写数据全迁到
`%LOCALAPPDATA%\<App>`，判断集中在两个函数里（`_resource_dir()` / `_writable_root()`），
其他模块不感知「自己是不是在 exe 里」。

顺带一个容易漏的：老名字的库文件要**连 `-wal` / `-shm` / `-journal` 边车文件一起搬**，
否则用户数据看起来「丢了一半」。

**下次怎么做**：第一天就写死三条规则 ——
① 可写的进用户目录；② 只读的进包内；③ 判断只在一处做。

## §2 先复现，再改

### 2.1 直觉答案会把你带偏，先拿数据说话

**案例（最典型的一次）**：用户报「点右上角叉就卡住，显示未响应」。

直觉答案：「主线程被某个耗时操作占住了」→ 方向是「去找那个耗时操作」。
**但这个方向是错的。**

正确做法是量两个数：**窗口响不响应** + **CPU 在不在涨**。

```
发 WM_CLOSE 前   : Responding=True   CPU=2.0625s
之后 1 秒        : Responding=False  CPU=2.0625s
之后 8 秒        : Responding=False  CPU=2.0625s（纹丝不动）
```

**CPU 纹丝不动 = 死锁的指纹。** 如果是「算不过来」，CPU 会往上走。
这一条把方向从「找耗时操作」直接扭到「找互等」。

**下次怎么做**：拿到「卡 / 慢 / 没反应」类问题，先量三个数 ——
**CPU 在不在动、内存在不在涨、进程还在不在**。
CPU 不动 → 死锁/等待；CPU 满 → 算法问题；内存涨 → 泄漏。

### 2.2 复现要能脚本化，不要靠手点

**案例**：把「点 ×」这件事脚本化，用的两个 API 完全等价：

- `Process.CloseMainWindow()` 就是发 `WM_CLOSE`（等价于点 ×）；
- `Process.Responding` 读的就是 Windows 判定「未响应」用的那个状态（内部即 `IsHungAppWindow`）。

```powershell
$proc = Get-Process | Where-Object { $_.MainWindowTitle -like "*App*" } | Select-Object -First 1
[void]$proc.CloseMainWindow()
for ($i = 1; $i -le 8; $i++) {
  Start-Sleep -Seconds 1
  $p = Get-Process -Id $proc.Id -ErrorAction SilentlyContinue
  Write-Output ("第 {0}s：Responding={1} CPU={2}s" -f $i, $p.Responding, $p.CPU)
}
```

顺带一个坑：一开始想用 `Add-Type` 调 P/Invoke，**但 `Add-Type` 在本机被安全策略拦下了**。
换成上面两个 .NET 内置成员后完全等价，而且不用编译 C#。

**下次怎么做**：每个「用户报的现象」都想一条**一行命令能跑**的复现路径。
脚本化的复现 = 可重复的验证 = 修完能证明修好了。

### 2.3 测试装置的错会伪装成被测对象的错

**案例（两次）**：

1. 回环录音测试第一版写的是「先出声、后开录」，结果句首三个字没录进去
   （识别成「不要一起去看展…」），**差点误判成模型能力问题**。
   改成「先开录、等 1.5 秒再出声」才拿到干净证据。

2. 手工验证时 `curl` 到了**机器上遗留的旧进程**（端口 8787 被旧版本占着），
   看到「版本不对、数据目录也不对」，差点以为打包版是坏的。

**下次怎么做**：
- 结果不符合预期时，**先怀疑测试方法，再怀疑被测对象**；
- 手工验证**换一个没人用的端口**，并核对响应里一个**能唯一标识进程的字段**
  （数据目录 / PID / 启动时刻）。

### 2.4 定位「不确定现象」的手法：固定随机种子多跑几次

**案例**：CI 上一条断言失败，本地一直是绿的。第一反应是「Linux/Windows 差异」。
实测：用不同 `PYTHONHASHSEED`（0 / 7 / 13）连跑三次，结果完全一致 → 排除哈希随机化。
真因是**流程问题**：改完公共代码后只跑了部分测试。

**下次怎么做**：结果不稳定时，先固定随机源（哈希种子、时间、并发）跑几次，
一致 → 问题在确定的代码路径上；不一致 → 才去找随机源。

## §3 三大高危区：批量替换 / 删除改名的连锁 / 重写历史

这三件事的共同点：**改错了不会报错，只会安静地产生一堆错的东西。**

### 3.1 批量替换：映射式替换必须「一次查表」

**案例（我踩了）**：版本重编号的映射里有

```
0.6.0 → 0.2.0
0.2.0 → 0.1.0
```

顺序 replace 会让刚生成的 `0.2.0` 被后一条规则再吃一次，**变成 `0.1.0`**。

脚本还对第一批 20 个文件**跑了两次**（第二次是把旧列表又带上了），
结果 README 的下载链接变成 `v0.1.0`、`STATUS.md` 里 22 处 `0.6.0` 全被降级。

**发现方式**：`git diff` 里检查 `0.6.0 → ?` 的**实际落点**（不是看「有没有改动」）。
**修法**：回滚这 20 个文件重跑一次。

**下次怎么做**：
```python
# ✅ 正确：一次查表，绝不顺序 replace
MAP = {"0.6.0": "0.2.0", "0.2.0": "0.1.0"}
def repl(m): return MAP.get(m.group(0), m.group(0))
text = re.sub(r"\b\d+\.\d+\.\d+\b", repl, text)

# ❌ 错误：顺序 replace，会被后一条规则再吃一次
for old, new in MAP.items():
    text = text.replace(old, new)
```
并且**替换完必须抽查 diff**，不要只看「跑了没报错」。

### 3.2 文件重命名：先给「被占用的目标名」让路

**案例**：要把 `v0.6.0.md` 改成 `v0.2.0.md`，但 `v0.2.0.md` **已经存在** ——
直接改会覆盖。正确顺序是先把它改走（`0.2.0→0.1.0`、`0.2.1→0.1.1`…），
**最后才动 `0.6.0`**。

**下次怎么做**：批量重命名前先建一张「现在 → 目标」的表，
检查目标名有没有被别的东西占用，然后**按依赖顺序**执行（用临时名中转最稳）。

### 3.3 删除 / 重命名函数：跨文件调用点是最容易漏的

**案例（P0，我自己引入的）**：重构把 `loadChats` 并进了 `loadObjects`，
**漏改了 5 个调用点**。

单文件 HTML + 零构建 = **没有编译器帮你**。于是它一路来到测试面前，
而那一轮全量测试竟然是绿的。实际后果比「一个小按钮失效」严重得多：

| 调用点 | 后果 |
|---|---|
| `init()` 里那一次 | 抛 `ReferenceError` → 后面的**读设置、自检、深链接跳转全都不执行** |
| 分析成功后那一次 | 在 `try` 里 → 异常被 `catch` 接住 → **刚渲染出的结果被覆盖成一句错误提示** |

**下次怎么做**：
- 删/改名函数前，先全文搜索所有调用点（`grep -n "函数名("`）；
- **为无编译器的项目补静态守卫**：
  - Python：用 `symtable` 找「引用了但本模块没定义」的全局名（`import *` 的文件跳过）；
  - JS：抠出脚本里所有 `名字(`，减去函数声明/`var|let|const`/`for-of`/参数解构/
    关键字/浏览器内置，剩下的必须为空。
    注意要**显式排除模板串里的 CSS 函数**（`style="width:min(680px,100%)"` 会带出 `min()`）。

### 3.4 重写历史：三个必须做的收尾

**案例**：用 `git filter-branch --env-filter` 改写全部提交的 author/committer 邮箱。

三个**必须做**的收尾动作：

1. `--tag-name-filter cat` 让 tag 跟着走；
2. **删除 `refs/original/*` 备份引用 + 清 reflog + `git gc --prune=now`** ——
   **这一步不能省**：`git log --all` 会把 `refs/original` 里的旧提交一并扫到，
   不清理的话守卫仍然会读到旧邮箱；
3. 重写期间**绝对不要用 `git add -A`**。

**案例（我踩了）**：`filter-branch` 的工作目录 `.git-rewrite/`
（含全部 ref 的旧 hash 快照与「旧→新」映射表）**被 `git add -A` 带进了提交并推送**，
50 个文件。检查后确认不含隐私，但它是纯内部产物，不该入库。

**下次怎么做**：
- 重写历史前先记录「旧 tag → 旧 commit」映射；
- 重写期间只 `git add <明确列出的路径>`，提交前先看 `git status`；
- 项目里预先在 `.gitignore` 加上 `.git-rewrite/`、`.git-filter-repo/`。

## §4 隐私：有三条独立通道

**这是用户明确点名要的经验，也是整个项目里最值得记的一段。**

### 4.1 核心认知：「文件干净」≠「没泄漏」

**案例**：做全历史扫描，结论和直觉相反 ——

| 扫描项 | 结果 |
|---|---|
| 真人姓名 | 已清理过，全过 |
| 手机号 / 身份证 | 无 |
| 密钥 / 令牌 | 无 |
| 邮箱（**文件内容**） | 只有占位符 |
| **提交元数据邮箱** | **42 个提交全部是一个真实邮箱** ← 唯一真问题 |

姓名守卫扫的是**文件内容**，而邮箱**不在任何文件里** ——
它在 `commit` 对象的 author/committer 字段里。
GitHub 把每个提交的作者邮箱明明白白印在提交页和 API 上，公开仓库里任何人都能翻。

### 4.2 三条通道（一条都不能漏）

| 通道 | 内容 | 怎么守 |
|---|---|---|
| **① 文件内容** | 真人姓名、手机号、身份证、密钥 | 扫源码 + `git log -S` 查历史 |
| **② 提交元数据** | author / committer 邮箱、姓名 | 提交身份设为匿名 noreply；守卫**只判形态不点名** |
| **③ 截图与文档** | 界面上渲染的本机 wxid、QQ 号、真实路径 | 截图前**替换数据**（不是加模糊）；文档用示例值 |

> 第一轮只守了 ①，第 7 轮才发现 ②，第 8 轮才发现 ③。**每一条都是独立的。**

### 4.3 脱敏要改数据，不是改样式

**案例**：给界面截图时，采集页会渲染本机真实信息
（微信 wxid、QQ 号、`D:\文档\xwechat_files` 这类真实路径）。

第一版用 CSS `blur` 遮挡 —— **模糊挡得住眼睛、挡不住 OCR**。
而且 `innerText` 仍然能读到明文，等于没遮。

**正确做法：截图前用 JS 把文本节点替换成示例值。**

```js
// TreeWalker 遍历 NodeFilter.SHOW_TEXT，对每个文本节点做 split().join() 替换
```

```python
# 结构示意（真实值已替换为占位符 —— 讲脱敏的文档自己不能带真实值）
REDACT = [
    ("<本机微信 wxid>", "wxid_example_demo_user"),
    ("<本机 QQ 号>", "1000000000"),
    ("<本机聊天文件目录>", "D:\\AppDemo\\xwechat_files"),
    ("<用户文档目录>\\xwechat_files", "<用户目录>\\Documents\\xwechat_files"),
]
```

**反向验证法**：重新加载页面后真实值会回来
→ 证明入库的图**确实是替换态**拍的（而不是碰巧没渲染出来）。

### 4.4 一个坑：只查一个页面就下结论

**案例（我踩了）**：先查了「对象页」的 `innerText`，看到没有敏感值，
就得出结论「无敏感信息」。**但切换页面后当然读不到别的页的内容** ——
切回采集页复查才发现真实 wxid 就在那里。

**下次怎么做**：脱敏校验必须**逐页遍历**，每页都重新读一遍；
不要用「某页干净」推断「整个应用干净」。

### 4.5 顺带记两个小坑

- **不要用「命中一串数字」就判定是手机号**：扫描时命中过一串 11 位数字，
  追下去发现是某个 commit hash 中间的一段。**定位到具体位置再下结论。**
- **守卫自己不能是被禁的那个字符串**：邮箱守卫只判断「是不是匿名形态」，
  **不点名任何具体地址** —— 否则守卫文件本身就把那个邮箱写进仓库了。
  这条规矩要写死：**守卫的职责是让某个字符串不出现在仓库里，它自己就不能是那个字符串。**

### 4.6 在 git 仓库里写文档也要注意

**案例**：Obsidian 知识库本身是个 git 仓库（含 `.obsidian/` 配置）。
往里写报告时，**文档里不能出现真实邮箱、真实姓名、真实路径** ——
否则一提交就进了另一个仓库的历史。

**下次怎么做**：把「知识库/笔记目录也是 git 仓库」当成默认假设，
写文档时统一用化名和示例路径。

## §5 内存与性能

**这也是用户明确点名的。** 结论一句话：

> **内存问题先分层测量，别猜。直觉答案（前端太重 / 缓存太多）往往是错的。**

### 5.1 先量基线：一个 import 占了九成

**案例**：用户说「程序内存优化一下」。用几个最小对照进程（同机、同 venv）：

| 进程 | WorkingSet | Private（提交） | 线程 |
|---|---|---|---|
| 空 Python | 4.2 MB | **0.9 MB** | 1 |
| 只 `import` 依赖（numpy 等） | 57.1 MB | **782.3 MB** | 27 |
| 服务本身 | 73.7 MB | **793.5 MB** | 28 |

**结论一目了然：自己的代码只贡献了 11 MB。780 MB 是导入依赖时提交的。**

### 5.2 缩小到单一元凶：760 MB 对 19 MB

再单独测 `import numpy`，和「限制 BLAS 线程数」做对照：

| | 提交内存 | 线程 |
|---|---|---|
| 默认 | **760.6 MB** | 27 |
| `OPENBLAS_NUM_THREADS=1` | **19.4 MB** | 4 |

**差 39 倍，就差在一个环境变量上。**

原因：OpenBLAS 会看机器**有多少个逻辑核**，开同样数量的线程，
并给每个线程**预先把工作缓冲区留出来**。这台机器 24 个逻辑核 → 24 个线程。

而项目用 numpy 只干一件事：几千条 512 维向量算**余弦相似度** ——
**那些预留的内存换来的并行度，一点都用不上。**

### 5.3 修法的两个关键点

```python
# 必须放在最外层包的 __init__.py 顶层
for _var in (
    "OPENBLAS_NUM_THREADS", "OMP_NUM_THREADS", "MKL_NUM_THREADS",
    "NUMEXPR_NUM_THREADS", "VECLIB_MAXIMUM_THREADS",
):
    os.environ.setdefault(_var, "1")
del _var
```

**两个刻意的选择（都很容易做错）：**

1. **位置**：必须在**任何子模块之前**执行。OpenBLAS 是在 `import numpy` **那一刻**
   就把线程池建好的，**之后再设环境变量等于没设**。
   所以放在最外层的 `__init__.py` 里，并且**那里不能有别的 import**。
2. **`setdefault` 而不是硬赋值**：用户自己设过就听用户的，
   我们只是提供一个更省内存的默认值。

**效果（带窗口，实测）**：提交内存 844.9 MB → **107.0 MB**；线程 43 → 20。

### 5.4 守卫要单独起进程

**案例**：给「限流早于 numpy」写测试时，**必须用子进程** ——
pytest 进程自己早就把 numpy 导进来了，那时候再去断言环境变量，
「限流生效了没有」根本看不出来。

**下次怎么做**：凡是测「导入时的副作用」（环境变量、全局状态、模块级常量），
一律 `subprocess` 起一个干净进程。

### 5.5 压不动的部分要说清代价

**案例**：打包版实测内存画像 ——

| 部分 | WorkingSet |
|---|---|
| 主进程（Python + 框架 + 本项目代码） | 162.1 MB |
| 6 个 WebView2 渲染进程（Windows 自带） | 400.8 MB |
| 合计 | 约 563 MB |

那 6 个渲染进程是 **WebView2 的标准结构**（主控/图形/网络/渲染/工具/崩溃上报），
**不是泄漏**。能不能压？能，但要改渲染参数，**副作用面太大而收益不确定** ——
所以**刻意没动**，并在文档里写明「要压得先做一整轮界面回归」。

同时提供一个可选项：走浏览器模式可以省掉整个进程组（主进程只剩 ~74 MB），
代价是没有原生窗口。**把取舍讲清楚，让用户自己选。**

### 5.6 分层测量的一般套路

1. **空进程基线**（几 MB）；
2. **逐个加依赖**，每加一类量一次；
3. **找到跳变最大的那个**，再单独做对照实验（改一个变量，看差异）；
4. **改完再量一遍**，给出「修前 vs 修后」的数字。

## §6 守卫式测试：必须先在旧代码上失败

### 6.1 不会失败的断言，只是一条好看的注释

**案例**：这个项目把「新测试要能在旧代码上失败」定成硬标准。
做法是把修复**逐条改回旧写法**，对应用例必须失败（跑完自动还原源码）。

一次 6 条反证全过：

| 改回旧写法 | 如期失败的用例 |
|---|---|
| 删掉 BLAS 限流 | `test_the_package_caps_blas_threads_before_numpy_arrives` |
| 关窗钩子改回同步调 `evaluate_js` | `test_the_close_hook_never_blocks_on_evaluate_js` |
| 退出只 `set()` 没人读的 Event | `test_desktop_close_quit_actually_tells_the_server_to_stop` |
| 通知不到界面时不补关窗 | `test_when_the_page_cannot_be_reached_the_window_is_still_closed` |
| 去掉 `desktop.py` 顶部的自我登记 | `test_state_is_shared_even_when_desktop_py_runs_as_main` |
| 删掉适配器里缺的那行 import | `test_bundled_samples_import_through_their_own_adapter` |

### 6.2 **反证本身也要被怀疑**

**案例（两次，都很有价值）**：

**第一次**：「关窗死锁」那条反证**没抓住**。
原因不是守卫太弱，而是**替换不够忠实**：只把 `_on_closing` 改回了同步调用，
却留着新版内部函数的线程包装 —— 那是个**现实中不存在的混合状态**
（旧代码里这两处是同一套写法），自然复现不出死锁。
改成「两处必须一起改回」之后才如期失败。

**第二次**：`_resolve_map` 那条改动**改成了另一种坏法**，恰好被别的修复兜住了，
于是它「通过」了 —— 说明**反证本身也要被怀疑**。

> **教训：一条通过了的反证，可能只是因为你复现旧代码复现得不够忠实。**

**下次怎么做**：写反证脚本时，**逐行对照 `git diff` 把改动还原到旧版原样**，
不是「改成一种看起来更差的写法」。

### 6.3 守卫式测试还会帮你发现「测试根本没测到」

**案例**：「`kept` 只在模型也想改时才列出来」这条改动**本来没有任何测试盯着** ——
旧测试用的是 Mock 引擎，而 Mock 会把全部字段都填满，所以新旧写法都能过。
为此专门加了一个「**没有证据的字段就不写**」的模型桩，才把这件事钉住。

**下次怎么做**：写测试桩时，**故意让桩「什么都不做」或「只做一半」** ——
比「全都能做」的桩更容易暴露问题。

### 6.4 端到端要对着**真实产物**跑，且不碰真实数据

**案例**：HTTP 端到端检查脚本对着打包版跑，并且把 `LOCALAPPDATA`
**指向临时目录**，完全不碰真实数据。

**下次怎么做**：E2E 检查要满足三条 ——
① 打真实 HTTP（不是调函数）；② 用临时数据目录；③ 断言数量写成可见的数字（`31/31`）。

## §7 打包与发行口径

### 7.1 打包是「问题放大器」

| | 源码运行 | 打包成 exe |
|---|---|---|
| 报错 | 控制台红字 + traceback | **双击没反应** |
| 数据 | 项目目录里，随手能看 | 写哪？程序目录可能只读 |
| 改一行代码 | 保存即生效 | 重新构建 40 秒 |
| 缺依赖 | `pip install` 一行 | 要么内置，要么用户永远修不好 |

**所以打包不能只交一个壳**，必须一起做掉三件事：
① 数据挪出程序目录；② 每条错误路径都有出口（日志 / 弹窗 / `--check` 自检）；
③ 状态自查（三档：ok / warn / fail）。

### 7.2 onedir 而不是 onefile

**案例**：onefile 每次启动**解压到随机临时目录、退出即删** ——
用户第二次打开会发现「我导入的数据全没了」。
onedir 启动是秒级的，东西都看得见，排错也直观。
代价是分发一个文件夹而不是单文件，**在说明里写清楚就行**。

**下次怎么做**：选择打包形态时，第一问是「**数据在哪、会不会丢**」，不是「文件数越少越好」。

### 7.3 校验和的口径差别（必须写进发行说明）

- **打包/压缩那步是确定的**：同一份 `dist/` 连打两次 SHA 相同 →
  **印出来的校验和可以用来核对「下载」**；
- **构建那步通常不是逐字节确定的**：同一份源码连构建两次，
  221 个文件里有 2 个不同 → 自己重跑构建得到不同 SHA 是**正常的**。

**下次怎么做**：发行说明里明确写「这个校验和用来核对下载，不能用来核对构建」。

### 7.4 错误提示要「指向能修好的方向」

**案例**：模型下载失败时会调 `_explain_error()` 把底层报错翻译成人话。
它有网络超时、401、磁盘满等分支，兜底是「重试 / 换镜像」——
**但没有「缺组件」这一类**。如果真有模块没打进包，用户会看到
`ModuleNotFoundError` 被翻译成「重试 / 换镜像」，
**而镜像补不上一个没打进包的模块，这是个永远修不好的方向。**

现在补了这类判断，关键细节是**它必须排在所有网络关键词之前**
（模块名可能碰巧命中网络关键词，排在后面就会被误判成网络故障）。

> **这是这个项目反复出现的一个模式：「没有建议」不可怕，
> 「看起来合理但方向错误的建议」才可怕。**
> 前者用户会来问，后者会让用户默默流失。

### 7.5 版本号要能被现场核对

**案例**：用户报「检查更新显示 0.3.1，但界面是 0.4.0」。
**真因不是文案**，是 0.3.1 时代的**旧进程还在 8787 端口答话** ——
前端是每次从磁盘现读的（所以是新的），服务却是一个一直在跑的进程（所以是旧的）。

三层防呆：

1. **前端自带版本号常量**，与 `/api/health` 报的版本比对，不一致时页面顶部弹红色横幅；
2. **进程自述接口**：返回 `version` / `started_at` / `uptime` / `mode`（exe/源码）/ `pid` ——
   旧进程一眼可辨；
3. **HTML 加 `Cache-Control: no-store`**（只给 `text/html` 补，不覆盖已有的头）；
4. 加一条测试盯「前端常量 == 后端版本」——
   否则这道检查会变成天天误报的噪音，用户很快学会无视它，**那还不如没有**。

顺带：**改 platform 之类的字段时不要跟着改主键 id**（它是幂等键与游标的依据）。

### 7.6 别用「grep 二进制」判断模块在不在包里

**案例（我踩了，而且差点改错构建配置）**：

看到标准版里没有 `huggingface_hub` 目录，却单独躺着一个 `hf_xet`（9 MB），
推断「下载功能是坏的」，准备去 spec 里补隐藏导入。**改之前先核对了一下** ——
用 PyInstaller 自己的归档读取器列真实模块清单：

```python
from PyInstaller.archive.readers import CArchiveReader, ZlibArchiveReader
r = CArchiveReader("dist/App.exe")
open("pyz.pyz", "wb").write(r.extract("PYZ.pyz"))   # 模块归档在里层
names = sorted(ZlibArchiveReader("pyz.pyz").toc)    # 权威清单
```

结果：`huggingface_hub` 有 **147 个子模块，本来就在包里**。推断错了。

**错在一个值得记的地方**：

> 「静态分析看不见」只对「**模块名是运行时拼出来的**」成立
> （比如 `importlib.import_module(name)`）。
> **不要推广到函数内写的 `from X import Y`** —— 字节码分析照样能追到。

**同时踩的两个「工具在骗你」：**

- **不能用 `grep` 二进制里的字符串判断模块在不在包里**：
  在 exe 里 grep 到了模块名（3 次），差点当成证据 ——
  可那几次命中来自**文档字符串**（字符串会被打进去，模块不一定）。
  反过来，模块真被打进去时内容是压缩的，grep 又可能什么都搜不到。
  **两个方向都会给假结论。**
- **探测脚本自己写错了**：`txt in acc`（`acc` 是字符串**列表**）是精确成员判断，
  不是子串匹配。于是三个修复全报 `False`，看起来像「重建没生效」，实际是探针错了。

**下次怎么做**：核对「东西在不在」时 ——
① 用**权威接口**（归档读取器、`pip list`、`sys.modules`）；
② **先拿一个已知为正的样本校验你的探针**。

### 7.7 体积回归靠量，不靠测试

**案例**：`hf_xet` 白占 9 MB，**对功能零影响**，所以任何功能测试都不会报警。
这类问题只有两个入口能发现 —— **量体积**，或者**读构建配置时多问一句**。

**下次怎么做**：CI 里加一条「构建后体积超过阈值就报警」（**报警而不是失败**，避免噪声）。

### 7.8 发行归档时：说清「历史包去哪了」

**案例**：把 7 个发行版收敛成「0.1.x 只留文字、0.2.0 唯一带包」时，
发行说明里的下载表格、SHA256 清单、`Get-FileHash` 命令**都摘掉了** ——
它们指向的文件已不存在，留着只会让人点到一个失效链接。

但**保留了**「打包那步是确定的、构建不是逐字节确定的」那段说明 ——
**那是工程认知，属于流程记录，不是软件。**

**下次怎么做**：归档时区分两样东西 ——
**指向已删文件的操作指引（删）** vs **讲清道理的工程认知（留）**。

## §8 「不报错但结果不对」—— 最贵的一类 bug

### 8.1 这类问题的共同形状

**编译不报、导入不报、界面照常打开**，只有真走到那一条路时才出问题 ——
而那条路恰好没有测试。**比崩溃难查得多：崩溃至少有栈。**

项目里实际遇到的（每一个都是真实事故）：

| 问题 | 表现 | 为什么难发现 |
|---|---|---|
| facts 唯一键把一对多建模成字典 | 「喜欢猫」被「喜欢火锅」**静默覆盖** | 不报错，只是画像缺了一半 |
| `available` ≠ `ready` | 库在就算「已完成」，模型权重一个字节没下 | 界面显示绿色，录音后什么都没发生 |
| 音频量纲错（int16 当 float32） | 送进模型的波形被放大 3 万倍，输出「玩玩玩玩玩玩!」 | 不报错不警告，只是给你错结果 |
| `GetProcessMemoryInfo` 句柄被截断 | 所有内存读数都是 `0.0 MB` | 没报错，就是全 0 |
| 微信适配器少了 `iter_blocks` import | 从项目**第一个提交**起就是崩的 | 当时没有任何测试跑过那条路径 |
| 列名匹配把「候选表」当「实际列名」 | 嗅探给 0.85 高分，然后一条都没导进去 | 两个环节各说一套话 |
| `_STOP.set()` 全仓没有消费者 | 「优雅退出」是假的，全程硬切 | 注释里写着「先让服务收工」 |
| `python -m app.desktop` 下有两个模块实例 | 窗口开着，接口说「没有窗口」 | 症状像功能坏了，不像状态串了 |

### 8.2 三条对策

**① dtype 对 ≠ 量纲对。**
跨模块传数组时，接口契约要写清**值域**，并且用**数值特征做兜底校验**，
而不是只信类型标签：

```python
# 不只看 dtype，还用峰值兜底
if pcm.dtype == np.float32 and np.abs(pcm).max() > 1.5:
    pcm = pcm / 32768.0    # 按 int16 量级处理
```

**② 状态判断要问「能不能真的干活」，不是「对象有没有造出来」。**

```python
available   # 引擎对象构造得出来 —— 用于工厂选择实现类
ready       # 现在拿一段音频进来就能出字 —— 用于界面状态、自检面板
```

**这两者的差集，正是「看着配好了、用起来没反应」的全部来源。**

**③ 注释里的承诺要 grep 验证。**
「先让服务收工」这句注释下面，`_STOP.set()` **全仓没有读者** ——
`grep -rn "_STOP"` 三秒就能证明它是假的。

### 8.3 抽象实验：判断是「能力问题」还是「管线问题」

**案例**：中文识别结果乱码，第一反应是「模型太弱」。
做了一次**英文对照实验** —— 英文同样乱，才确认是管线问题而不是模型能力问题。

> **如果只测中文，很容易得出「中文就是不行」的错误结论。**

**下次怎么做**：怀疑模型/算法能力时，**换一个输入维度做对照**
（换语种、换数据源、换规格），把「能力」这个变量隔离掉。

## §9 多进程、多线程与状态归属

### 9.1 UI 线程里不能有同步的跨线程等待

**案例（最漂亮的一次根因分析）**：关窗卡死的根因是 ——

```
用户点 ×
  → Windows 发 WM_CLOSE
  → 框架在 UI 线程上回调 FormClosing
  → 我们的钩子函数                     ← 就在这个线程里
  → 想通知页面弹窗
  → evaluate_js(...)                   ← 同步阻塞
  → semaphore.acquire()                ← 死等，没有超时
```

而 `evaluate_js` 内部把完成回调**投递到 UI 线程的同步上下文**执行 ——
UI 线程此刻正卡在等 semaphore，**没有人在跑那个回调，也就永远没人 release。**

**两边互等，永不解开。**

**修法**：钩子只做「置标志 + 起后台线程 + 立刻返回」。
因为 `Invoke` 在非 UI 线程调用时会**投递**到 UI 线程执行，
而此刻 UI 线程已经空闲下来了 —— 它能去跑那个回调。

**下次怎么做**：在 UI/主线程的事件回调里，**绝不做同步的跨线程等待**。
一律「置标志 + 起线程 + 立即返回」，并给等待加超时。

### 9.2 每条失败路径都要有出口

修完死锁**不等于**修完问题。改完之后逐条检查失败路径：

1. **超时**：等待加 5 秒上界，超时按「通知失败」处理 ——
   不把用户永远留在一个不动的窗口前；
2. **通知失败就补一刀**：钩子已经返回了「取消关闭」，如果通知又失败，
   用户再点 × 也关不掉 —— 会成为「点了没反应」。所以失败时必须**主动关窗**；
3. **`quitting` 标志**：用户选了「关闭程序」之后所有关闭事件一律放行 ——
   不加这个的话，销毁窗口会**再触发一次**关窗事件 → 又进协商 → 又关不掉。

**下次怎么做**：改状态机时，把「成功 / 超时 / 失败 / 重入」四条路径都画出来，
**每条都要有出口**。

### 9.3 「谁持有状态」比「谁能画出界面」重要

**案例**：给窗口加了「后台运行」之后，问题变成「怎么把窗口找回来」。
最自然的写法是「再双击一次程序就再开一个窗口」—— **但这个窗口是个空壳**：

- 服务在**第一个**进程里，第二个进程只负责渲染窗口；
- 在新窗口里点「关闭程序」→ 请求发到老进程 → 老进程退出并销毁**它自己的**窗口 →
  新窗口变成一具对着死服务的躯壳，而**第二个进程还挂在那儿**。

**修法**：第二次双击走一个接口，由**已经在跑的那个实例**执行「显示窗口」。

> **教训：多进程 + 单服务的组合里，凡是出现「壳与本体分离」的可能，
> 都要先问一句：这个动作作用到哪个进程上了？**

### 9.4 `try` 包得太宽会把成功的结果擦掉

**案例**：分析成功后调用刷新列表的函数 —— 那个函数已经不存在了，
于是抛异常**被外层的 `catch` 接住**，把刚渲染出的分析结果**覆盖成一句错误提示**。

用户看到的是「分析坏了」，而真正的问题在刷新列表那一步；
**渲染明明成功了，`catch` 却把它的成果擦掉。**

**下次怎么做**：`try` 的范围只包「真正可能失败的那一件事」，
收尾动作（刷新、上报、清状态）**放在 `try` 外面**，
或者单独 `try` 一次并只记日志。

### 9.5 模块被加载两次：`__main__` 与模块名的分裂

**案例**：`python -m app.desktop` 会让文件以 `__main__` 的名字执行；
而另一个模块又 `from .. import desktop`，把它**按模块名再导入一次**。
于是 `_WINDOW` / `_CLOSE` / `_SERVER` 各存一份 ——
主流程写的是 `__main__` 那份，接口读的是另一份（永远初始值）。

症状全都**像功能坏了，而不是像状态串了**：窗口开着 → 接口说「没有窗口」；
点「后台运行」→ 后端读到 `None` → 回你「已关闭」**却什么都没做**。

**修法**（文件顶部，任何可能触发其他导入的代码之前）：

```python
if __name__ == "__main__":
    sys.modules.setdefault("app.desktop", sys.modules[__name__])
```

**下次怎么做**：支持 `python -m 包.模块` 入口的进程，**都要处理这个分裂**。
另外记一条排查线索：**某个模块的「启动时刻」比它自己开始工作的时刻还晚** →

## §10 文档与流水记录

### 10.1 按版本记录「起点 / 怎么做 / 踩到什么 / 怎么验证」

**案例**：`docs/DEVLOG.md` 的结构 ——
每一版四条：**起点（提交号 + 测试基线）→ 怎么做 → 踩到什么 → 怎么验证**。
末节提炼贯穿始终的做法。

**下次怎么做**：文档不要只写「现在是什么样」，要写**「为什么变成这样」**。
决定和取舍比结论更容易被遗忘。

### 10.2 现状文档要答「现在是什么样」，计划文档答「要改成什么样」

**案例**：`STATUS.md`（现状）与 `PLAN-xxx.md`（计划）分开写。
现状文档开头就写明：

> **用途**：给「全新上下文」的窗口看的一份现状底稿。目标是**读完不用再通读代码**就能动手改。
> **注意**：文件行号会随改动漂移。改动前先用函数名定位，再用行号确认。

**下次怎么做**：现状文档必备三样 ——
① 目录地图（带行号的职责说明）；② 数据模型与不变量；③ 已知缺陷与盲区。
并且提醒「**行号会漂，用函数名定位**」。

### 10.3 报告要自包含

**案例**：每份报告开头都写「本文自包含：所有关键结论都带根因与代码要点，不需要外部附件」。

**为什么**：报告是要进知识库长期检索的。半年后你只有这一个文件，
点不开当年的截图、进不了当年的仓库 —— 报告必须自己能站住。

### 10.4 诚实记账：明确写「没做什么」和「没验证什么」

**案例**：每份报告都有「遗留与未做」和「累计没有验证的东西」两节，例如：

| 没验的 | 为什么 |
|---|---|
| 云模型真实效果 | 手里没有可用的 API Key |
| 在没装 Python 的机器上运行 | 手上只有这一台 |
| macOS / Linux 桌面 | 只做了 Windows 打包 |

**为什么要写**：**免得日后误以为验过了。** 一张「累计未验证」的表，
比一堆「已完成」的勾更有价值。

### 10.5 文档里的界面描述/截图必须跟上当前版本

**案例**：README 里的界面截图拍于早期版本（7 项导航 + 语音面板），
而界面早就收敛成 4 项、语音已撤下。**旧图会误导人**。

同理，文档里的**导航项、功能列表、版本号、体积数字**都要在每轮结束时核对一遍。

**下次怎么做**：把「README 核对」加进每轮的收尾清单 ——
版本号、体积、下载链接、界面截图、文档索引，逐项过。

## §11 本机环境坑（Windows / 国内网络）

这些是**这台机器上实测踩过的**，换项目也还会遇到。

| 坑 | 现象 | 对策 |
|---|---|---|
| `Add-Type` 被安全策略拦下 | PowerShell 里编译 C# 失败 | 优先找 .NET 内置成员等价替代（如 `Process.CloseMainWindow()`） |
| `raw.githubusercontent.com` 超时 | HTTP 000 / exit 28 | 改用 GitHub API `/repos/{owner}/{repo}/contents/{path}?ref=main` 拿 blob SHA 比对 |
| 中文路径/ID 直传 URL | `Invalid HTTP request received` | 必须 URL 编码（`qq-%E5%B0%8F%E9%B9%BF-…`） |
| 测试必须在子目录跑 | 从仓库根跑单文件会跳过 `conftest.py` | `cd backend && ./.venv/Scripts/python.exe -m pytest tests/ -q` |
| 没有图像库 | `from PIL import Image` 报 `ModuleNotFoundError` | 读 PNG 尺寸：`struct.unpack('>II', fh.read(8))`（先 `fh.read(16)` 跳文件头） |
| 代理干扰本地请求 | 本地 HTTP 请求被改写成绝对地址 → 404 | 检查脚本里 `trust_env=False`；`curl` 加 `--noproxy '*'` |
| 测冻结控制台编码 | 打包后 stdout 掉回 GBK，中文乱码 | 显式 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` |
| JS 里 shell 转义 | `SyntaxError: Unexpected token` | 把 JS 写成文件再读进来执行，别塞进命令行 |
| 长命令无输出疑似卡死 | 超过 2 分钟无响应 | 先想「它是不是在下载什么东西」；能指定本地已有资源就指定 |

### 11.1 浏览器自动化的两个必记参数

```
# 必须指定系统已有浏览器，否则它会去下载一个，然后卡死
--executable-path "C:/Program Files/Google/Chrome/Application/chrome.exe"

set viewport 1440 1180     # 视口命令是 "set viewport W H"
screenshot --full <path>   # 全页截图是 --full（不是 --full-page）
```

写错 `--full-page` 会把参数当成输出路径，**生成一个名叫 `--full-page` 的文件** ——
遇到这种「怪文件」先想想是不是参数写错了。

### 11.2 端口占用是本机最常见的干扰源

**案例**：8787 端口上留着好几个早前会话的旧进程，
新起的打包版「为了单实例」直接复用旧服务并静默退出 ——
于是 `curl` 打到了旧进程，看到的数据目录和版本都不对。

**下次怎么做**：手工验证前先列一遍监听端口，
**换一个没人用的端口**，并核对响应里的数据目录/PID/启动时刻。

## §12 与 AI 协作的几条实践

### 12.1 让 AI 先读现状，再动手

**案例**：执行窗口的标准开场是 ——
「先读 `STATUS.md` 拿到现状，再读 `PLAN-xxx.md`」。
现状文档是专门为「全新上下文」写的：读完不用通读代码就能动手改。

**下次怎么做**：给新窗口的提示词里，第一条永远是**「先读 <现状文档>」**，
而不是直接描述需求。

### 12.2 两个 agent 并行做同一件事时，重点是「怎么让用户不被搞晕」

**案例**：推送时发现远程多了 9 个提交 —— 是另一个 agent 从同一基点分头做的
（源码侧零配置启动器 + 启动前自检 + 配置溯源接口）。

两边目标相同、路径不同：他要「源码装起来不费劲」，我要「连 Python 都不用装」。
冲突只有 3 个文件。最后的处理是：

- 保留对方的「快速开始（3 步）」作为 TL;DR；
- 新增**「三种跑法：怎么选」**表格，指出**唯一的分水岭**
  （「这台机器愿不愿意装 Python」）；
- 新增「排错从哪下手」，明确两个自检入口各自的命令与产物路径；
- **决定两套自检不合并**（检查项本来就不一样，强合会让两边都塞一堆跳过分支）。

> **可复用的经验：两个 agent 并行做同一件事时，价值最高的产出往往不是代码，
> 是「怎么让用户不被两条路搞晕」。**
> 合并时先问「用户面对几个入口、他知不知道该选哪个」，比先 diff 代码更有效。

### 12.3 给 AI 的约束要具体、可验证

**案例**：给执行窗口的硬约束是这种形式 ——

1. **不确定就问**：有模糊处先问用户，不要自行发明规则；
2. **守卫式测试**：新增测试要能在**旧代码上失败**；
3. **隐私红线不变**：新代码/测试/文档里不要引入真实姓名（用化名）；
4. **行号会漂**：用函数名/符号名定位；
5. **提交信息**：`type(scope): 中文描述 —— 说清为什么`，
   body 里写「改了什么 / 为什么 / 怎么验的」。

**下次怎么做**：约束写成**检查项**而不是**期望**。
「守卫要能在旧代码上失败」可以被验证；
「代码质量要好」不能被验证。

### 12.4 AI 会给出「看起来对」的结论，要验证

**案例（我自己的三次错误推断）**：

1. 推断「函数内的 import 静态分析看不见」→ 用归档读取器一查，**错了**（147 个模块都在）；
2. 推断「对象页没有敏感信息」→ 只查了一页，切回去才发现采集页有 wxid；
3. 推断「本地全绿就说明没问题」→ CI 第一次运行就抓到了漏测的 bug。

**下次怎么做**：接受「推断 → 核对 → 再动手」这个节奏。
**改动前花 5 分钟核对，能省掉几小时的返工。**

## §13 什么时候该放弃一个功能

**案例**：项目最初的需求里有「接入大模型语音通话识别」，
技术上已经跑通了（回环通道端到端能正确识别），
但 **v0.1.1 把它整体撤下了** —— 通话页只剩占位文案，后端入口一并移除。

**为什么撤**：它是三个能力里唯一一个「法规与场景都最别扭」的部分 ——
在通话中实时采集对方的声音涉及录音告知、平台条款与两方同意，
产品上无法给出干净的边界。**技术可行性不构成保留理由。**

撤下时做了三件事：

1. **后端入口真的移除**（不是藏起来），CSS 一并清理；
2. **文档里的相关表述一起核对**，不留「通话页还在」的失实描述；
3. 把原页面里有价值的内容（路线图思路）**压缩**进另一个位置 ——
   **不是原样搬运（那是另一种冗余）。**

**下次怎么做**：决定砍一个功能时 ——
① 真的删干净（别留半截）；② 全仓搜相关词条，把文档一起改；
③ 有价值的思路换个位置压缩保留；④ **把「为什么撤」写进决策记录**。

## §14 最终原则清单

把上面 13 节压成 15 条，贴在显示器旁边：

1. **不确定就问**，尤其不可逆操作 —— 给选项和后果，别问开放式问题。
2. **先复现，不猜。** 卡/慢先量 CPU、内存、进程存活 —— CPU 不动通常是死锁。
3. **基线优先。** 每次开工先记提交号 + 测试数，收工再对一次。
4. **守卫必须先在旧代码上失败过**，否则它只是一条好看的注释。
5. **反证本身也要被怀疑** —— 替换要忠实还原旧代码，不是「改得更差」。
6. **静默失败比崩溃危险。** 优先找「不报错但结果不对」的那一类。
7. **dtype 对 ≠ 量纲对；`available` ≠ `ready`。** 状态判断要问「能不能真的干活」。
8. **隐私有三条独立通道**：文件内容 / 提交元数据 / 截图文档。
   **脱敏要改数据，不是加模糊。**
9. **重写历史期间不用 `git add -A`**；完事必须清 `refs/original` + `gc --prune=now`。
10. **映射式替换一次查表**，绝不顺序 replace；重命名先给目标名让路。
11. **删/改名函数先全文搜调用点**；无编译器的项目自己补静态守卫。
12. **内存问题先分层测量**：空进程基线 → 逐个加依赖 → 找到跳变最大的 → 做对照实验。
    导入时才生效的环境变量（如 BLAS 线程数）**必须放在最外层且早于那个 import**。
13. **UI/主线程的事件回调里不做同步跨线程等待**；每条失败路径都要有出口。
14. **多进程 + 单服务时，先问「这个动作作用到哪个进程上了」。**
15. **诚实记账**：明确写清「没做什么」和「累计没验证什么」——
    一句话，**别让未来的自己误以为验过了。**
