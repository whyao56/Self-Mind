## 0. 速览：一页看懂

### 结论

故障现象看起来是「WiFi 断网」，实际是 **蓝牙音频输出通道的渲染时钟被按一半速率驱动**：

一段 **4.000 秒** 的音频，在蓝牙链路上要花 **8.1～9.1 秒** 才播完。音乐被拉长一半，播放器永远等不到音频时钟推进，于是进度条卡在 0；耳机里是被拉长一半的声音，用户判断为「没声音」。

**网络全程毫发无损**（单连接 5.5 MB/s、6 条并行合计 208 Mbps）。

### 关键数字

| 指标 | 数值 | 说明 |
|---|---|---|
| 故障期播放倍数 | **2.04 ×** | 4 s 音频实测 8158 ms |
| 修复后（未重启） | **1.12 ×** | 协议栈重置即时见效 |
| 重启后（最终） | **1.01 ×** | 4 s → 4070 ms，完全正常 |
| 蓝牙开启时下行带宽 | **208 Mbps** | 6 条并行连接，网络无恙 |
| 故障时开机时长 | **8.35 h** | 期间 Intel 无线扩展模块崩溃 6 次 |


## 1. 故障现象与技术化拆解

### 用户原始描述

> 「网络没有问题，但是像 B 站的视频点进去以后，缓冲是 0，用 QQ 音乐听歌也听不了，耳机也没有声音。点进去还是可以点进去，但视频的进度条和歌曲的进度条就一直在缓冲，**关了蓝牙就好了**。」

### 把口述翻译成技术命题

这一步是本案的转折点。「缓冲为 0」在直觉上等于「下不到数据」，但实际不是。

| 用户表述 | 技术含义 | 验证结果 |
|---|---|---|
| 「网络没有问题」 | 连通性正常 | ✅ 与实测一致 |
| 「视频点得进去」 | TCP / HTTPS / 页面渲染正常 | ✅ 流量能收发 |
| 「进度条一直缓冲」 | **播放管线收益端阻塞** | 🔴 关键：非下载问题 |
| 「耳机没有声音」 | 音频输出通道异常 | 🔴 真身：声音被拉长一半 |
| 「关了蓝牙就好」 | 故障与蓝牙链路强绑定 | ✅ 判据核心 |

### 为什么一开始会误判为网络问题

播放器必须等音频缓冲区**按实时速率被消费掉**才会推进进度条。
音频时钟慢一倍 ⇒ 缓冲区永远不减少 ⇒ 进度条停住。
这也解释了为什么「点得进去」：页面和网络请求全都没问题。

```
                 ┌──────────────────────────────────┐
   数据流  ───▶  │  下载链路（健康，5.5 MB/s 实测）  │  ← 不是这里
                 └──────────────────────────────────┘
                              │
                              ▼
                 ┌──────────────────────────────────┐
   音频流  ───▶  │  蓝牙音频渲染通道（时钟减半）      │  ← 问题在这里
                 └──────────────────────────────────┘
                              │
                              ▼
                       进度条永不推进 / 声音被拉长
```

## 4. 阶段一：假设「2.4GHz 共存抢天线」

### 思路

AX211 是蓝牙 + WiFi **二合一模块，物理共用天线**；蓝牙跳频覆盖 **2402–2480 MHz**，而 2.4G 的 1–13 信道全在 **2400–2483 MHz** 内——两者直接重叠。当前连接的工作在 **2.4 GHz 信道 3**。

### 需要的数据

1. 当前无线连接状态（SSID / 频段 / 信道 / 速率）
2. 周边无线网络（看是否有 5 GHz 可切换）
3. 网卡与蓝牙设备驱动状态
4. **能由脚本直接开关蓝牙**（否则无法做对照实验）

### 代码 1 · 蓝牙无线电开关（无需管理员）

用 WinRT `Windows.Devices.Radios.Radio` 控制蓝牙，等效于操作中心里的开关。

```powershell
# bt-radio.ps1  —— 与操作中心开关等效，无需管理员
param(
    [ValidateSet('status','on','off')]
    [string]$Action = 'status',
    [string]$OutFile = "$PSScriptRoot\bt-radio-result.txt"
)

$ErrorActionPreference = 'Continue'
$lines = @()
function L($s) { $script:lines += $s }

try {
    Add-Type -AssemblyName System.Runtime.WindowsRuntime -ErrorAction Stop

    # 关键：IAsyncOperation<T> 没有同步等待接口，必须用 AsTask 泛型方法桥接
    $asTaskGeneric = ([System.WindowsRuntimeSystemExtensions].GetMethods() | Where-Object {
        $_.Name -eq 'AsTask' -and $_.GetParameters().Count -eq 1 -and
        $_.GetParameters()[0].ParameterType.Name -eq 'IAsyncOperation`1'
    })[0]

    function Await($op, $type) {
        $t = $asTaskGeneric.MakeGenericMethod($type).Invoke($null, @($op))
        $t.Wait(-1) | Out-Null
        $t.Result
    }

    $radioType = [Windows.Devices.Radios.Radio, Windows.System.Devices, ContentType = WindowsRuntime]
    $stateType = [Windows.Devices.Radios.RadioState, Windows.System.Devices, ContentType = WindowsRuntime]
    $listType  = [System.Collections.Generic.IReadOnlyList[Windows.Devices.Radios.Radio]]

    $access = Await ($radioType::RequestAccessAsync()) ([Windows.Devices.Radios.RadioAccessStatus])
    L ("ACCESS=" + $access)

    $radios = Await ($radioType::GetRadiosAsync()) $listType
    L ("COUNT=" + $radios.Count)
    foreach ($r in $radios) { L ("  KIND=" + $r.Kind + " NAME=" + $r.Name + " STATE=" + $r.State) }

    if ($Action -ne 'status') {
        [Windows.Devices.Radios.Radio]$target = $radios |
            Where-Object { $_.Kind -eq ([Windows.Devices.Radios.RadioKind]::Bluetooth) }
        if (-not $target) { L "NO_BLUETOOTH_RADIO" }
        else {
            $want = if ($Action -eq 'on') { $stateType::On } else { $stateType::Off }
            L ("ACTION=Bluetooth->" + $want)
            try {
                # ⚠️ SetStateAsync 不能走 Await（同一条路径会失败），下发后轮询复查
                $null = $target.SetStateAsync($want)
                L "SETSTATE_DISPATCHED=ok"
            } catch { L ("SETSTATE_ERR=" + $_.Exception.Message) }

            for ($i = 1; $i -le 8; $i++) {
                Start-Sleep -Seconds 1
                $chk = Await ($radioType::GetRadiosAsync()) $listType
                $bt = $chk | Where-Object { $_.Kind -eq ([Windows.Devices.Radios.RadioKind]::Bluetooth) }
                L ("  +" + $i + "s  BT_STATE=" + $bt.State)
                if ($bt.State.ToString() -eq $want.ToString()) { break }
            }
        }
    }
}
catch {
    L ("EXCEPTION=" + $_.Exception.GetType().FullName + " :: " + $_.Exception.Message)
}

L ("DONE=" + (Get-Date).ToString("HH:mm:ss"))
$lines -join "`r`n" | Out-File -FilePath $OutFile -Encoding ascii
```

> 💡 **坑**：PowerShell 工具的 stdout 不被捕获 → 所有输出必须 `Out-File` 到文件，再用 Read 读。
> 💡 **坑**：`SetStateAsync` 的异步对象不能用与 `GetRadiosAsync` 相同的桥接路径等待，改成"下发 + 轮询复查"。

### 代码 2 · 连通性分层监测（确认共存影响有多大）

```powershell
# wifi-monitor.ps1（核心逻辑）
# 逐秒记录：网关 / 外网 / DNS / TCP443 / HTTP / WiFi 速率
$ping = New-Object System.Net.NetworkInformation.Ping

function PingMs($ip){
    try { $r = $ping.Send($ip, 600); if($r.Status -eq 'Success'){ return [int]$r.RoundtripTime } } catch {}
    return -1
}
function TcpMs($h, $p){
    $sw = [System.Diagnostics.Stopwatch]::StartNew()
    $c = New-Object System.Net.Sockets.TcpClient
    try {
        $ar = $c.BeginConnect($h, $p, $null, $null)
        if($ar.AsyncWaitHandle.WaitOne(1500)){ $c.EndConnect($ar); $sw.Stop(); return [int]$sw.ElapsedMilliseconds }
        $sw.Stop(); return -1
    } catch { $sw.Stop(); return -1 } finally { $c.Close() }
}
```

**实测结果（蓝牙在第 12 秒由脚本打开）：**

| 指标 | 蓝牙开之前 | 蓝牙开后 |
|---|---|---|
| 网关 ping | 2 ms，0 丢包 | 正常，**偶发 35 ms / 81 ms 尖峰** |
| 外网 223.5.5.5 | 19 ms，0 丢包 | 正常（尖峰 95 ms） |
| DNS / TCP443 / HTTP | 全通 | 全通，HTTP 200 |
| **Wi-Fi 接收速率** | **258 Mbps** | **掉到 103 → 115 → 155**，之后回升 |

### 阶段一结论

> **共存干扰客观存在，且已量化（速率掉 60%、延迟尖峰），但单靠「蓝牙无线电开着」不足以断网。**
> 用户遇到的是「耳机连上、在放歌」那一档——A2DP 音频流的空口占用比蓝牙待机高一个数量级。**待验证。**

同时得到的**重要副产品**（后面反复用到）：

- **5G 扫不到**：多轮扫描全程只可见 `Tenda_255BF8` 一个 2.4G 网络 → 「改连 5G」方案当前执行不了
- **蓝牙跳频覆盖 2402–2480 MHz，正好盖住 2.4G 全部 13 个信道** → 换信道也无法回避蓝牙

## 6. 阶段三：Clash Verge 代理层（今日唯一确凿变更项）

```python
import winreg
def rd(root, path, vals):
    k = winreg.OpenKey(root, path)
    for v in vals:
        try:
            d, t = winreg.QueryValueEx(k, v)
            print("  %s = %r" % (v, d))
        except FileNotFoundError:
            print("  %s = (不存在)" % v)
```

## 7. 阶段四：真实 A2DP 复现 —— 推翻共存论

### 思路

不能再靠推理。必须做**真实复现**：把音频**真的推过蓝牙链路**，同时逐秒监测网络。

关键前提：先确认**默认播放设备是否就是蓝牙端点**——如果是，那么直接播 wav 就等于真实走蓝牙。

### 代码 1 · 生成测试音频

```python
# 生成已知时长的 wav（低音量宽带信号，避免刺耳）
import wave, struct, math
for dur, name in ((4,'tone.wav'), (8,'tone8.wav'), (20,'tone20.wav')):
    sr = 44100
    buf = bytearray()
    for i in range(sr * dur):
        t = i / sr
        v = (math.sin(2*math.pi*440*t) + 0.5*math.sin(2*math.pi*880*t)) / 1.5 * 0.30
        s = int(v * 32767)
        buf += struct.pack('<hh', s, s)
    with wave.open(r'C:\path\to\%s' % name, 'wb') as w:
        w.setnchannels(2); w.setsampwidth(2); w.setframerate(sr)
        w.writeframes(bytes(buf))
    print(name, 'ok')
```

> 多频叠加（180/357/711/1443/2891 Hz）用于**空口压力测试**版本；纯音版本用于**计时**。

## 8. 阶段五：判据切换，比值法锁定真因

### 思路（本案最关键的一步）

既然网络洗清了，就**把判据从「网络通不通」换成「音频播得完播不完」**：

> **生成一段已知时长的音频，测量实际播放耗时。比值 ≈2.0 = 音频渲染时钟被减半。**

三个必须做的验证：

1. **必须确认默认渲染设备确实是蓝牙端点**，否则音频走扬声器，测出来一定"正常"（假阴性）

```powershell
    $r = @{ name = '?'; desc = ''; kind = '未知'; btname = '' }
    $p = 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\MMDevices\Audio\Render\{' + $guid + '}\Properties'

    # {a45c254e-...},2  = 端点名（耳机 / 扬声器）
```

```powershell
function W($s){ $s | Out-File -LiteralPath $log -Append -Encoding utf8 }

$ping = New-Object System.Net.NetworkInformation.Ping

function PingMs($ip){
    try { $r = $ping.Send($ip, 600); if($r.Status -eq 'Success'){ return [int]$r.RoundtripTime } } catch {}
    return -1
}
function TcpMs($h, $p){
    $sw = [System.Diagnostics.Stopwatch]::StartNew()
    $c = New-Object System.Net.Sockets.TcpClient
    try {
        $ar = $c.BeginConnect($h, $p, $null, $null)
        if($ar.AsyncWaitHandle.WaitOne(1500)){ $c.EndConnect($ar); $sw.Stop(); return [int]$sw.ElapsedMilliseconds }
        $sw.Stop(); return -1
    } catch { $sw.Stop(); return -1 } finally { $c.Close() }
}
function DnsMs($name, $server){
    $sw = [System.Diagnostics.Stopwatch]::StartNew()
    try {
        $r = Resolve-DnsName -Name $name -Server $server -DnsOnly -QuickTimeout -ErrorAction Stop
        $sw.Stop(); if($r){ return [int]$sw.ElapsedMilliseconds }
    } catch {}
    $sw.Stop(); return -1
}
function HttpCode($url, $proxy){
    try {
        if($proxy){ $r = & curl.exe -s -m 6 -x $proxy -o NUL -w "%{http_code}" $url 2>$null }
        else      { $r = & curl.exe -s -m 6 -o NUL -w "%{http_code}" $url 2>$null }
        return ([string]$r).Trim()
    } catch { return 'ERR' }
}
function WlanInfo(){
    $o = & netsh.exe wlan show interfaces 2>&1 | Out-String
    $rx = '?'; $tx = '?'

    $nowBad = ($hardRun -gt 0) -or ($softRun -gt 0)
    if(-not $nowBad -and $wasBad){ W ("*** RECOVERED at " + (Get-Date).ToString('HH:mm:ss')) }
    $wasBad = $nowBad

    Start-Sleep -Milliseconds $IntervalMs
}
W ("##### WATCH END " + (Get-Date).ToString('HH:mm:ss') + " #####")
```

## 9. 根因分析

### 出问题的环节

| 项目 | 实测值 |
|---|---|
| 默认输出端点 | `971B9AE5-BEEB-4DAD-B92E-936E5F67E3D0`（「耳机」） |
| 对应蓝牙耳机 | XISEM-Olite2（挂 `BTHENUM\{0000110B-…}` = A2DP Audio Sink） |
| 端点所属驱动栈 | 适用于蓝牙® 音频的英特尔® 智音技术（ISST），节点 `IntcBtWaveRender` / `IntcBtTopoRender` |
| 驱动包 | `oem83.inf` 版本 10.29.0.12389（2026-01-06） |
| 端点格式 | 48 kHz / 16 bit —— **正常**（已排除格式错配） |

### 机制

音频走的是 **Intel 智音技术（ISST）的蓝牙音频卸载路径**。这条路径的**运行时状态**被破坏后，渲染端按一半的速率消费音频缓冲，于是产生精确 2.00 倍的耗时。端点格式本身没问题，所以改格式、改增强、换音频文件全都无效。

```
                    正常                                    故障
        ┌───────────────────────┐              ┌───────────────────────┐
真实时间 │  1s   1s   1s   1s    │      真实时间 │   1s   1s   1s   1s    │
        └───────────────────────┘              └───────────────────────┘
音频消耗 │ ████  ████  ████  ████│      音频消耗 │ █████████  █████████  │
        └───────────────────────┘              └───────────────────────┘
             4s 音频 → 4.1s 播完                   4s 音频 → 8.1s 播完
```

### 为什么会「今天才出现」

| 证据 | 数值 |
|---|---|
| 故障发生时开机时长 | **8.35 小时**（上次启动 09-30 15:02，期间从未重启） |
| 当日 Intel 无线扩展模块崩溃 | **6 次**（`IntelIHVRouter14.dll`，22:07 / 22:12 / 22:38 / 22:39 等） |

音频通道状态损坏**必须整机重启才能重建**。长时间不重启 + Intel 组件栈反复崩溃 ⇒ 状态被破坏。

此外，**三只蓝牙耳机的 A2DP 接收端同时处于「已启动(OK)」状态**（`XISEM-Olite`、`XISEM-Olite2`、`Tonemay H5 Lite`），外加 `Rapoo BT Mouse`（BLE）——一条 2.4 GHz 天线同时维持 4 条蓝牙链路。

### 关于「蓝牙共存干扰」

共存干扰**确实客观存在，且已量化**：

| 指标 | 蓝牙关 | 蓝牙开 |
|---|---|---|
| WiFi 接收速率 | 258 Mbps | **103–155 Mbps** |
| 延迟 | 2 ms / 19 ms | **尖峰 35 ms / 81 ms** |

但连续 45 秒真实音频推送期间，网络始终零丢包、零阻塞。
**干扰是「变慢」，本案是「完全卡死」，两者不是同一个问题。**

而换信道也无法回避——**蓝牙跳频覆盖 2402–2480 MHz，正好盖住 2.4G 全部 13 个信道**。

## 10. 修复：代码与执行结果

### 修复原理

针对「ISST 蓝牙音频卸载路径的运行时状态损坏」，做四件事：

1. 清掉多余的蓝牙音频链路（减少同天线竞争）
2. 关掉耳机的**免提（HFP）**通道（避免切到 SCO 窄带模式）
3. 关掉蓝牙/音频设备的**省电**（防止链路被挂起）
4. **重启音频与蓝牙协议栈** + 重启 Intel 蓝牙/智音设备

## 14. 工程笔记：踩过的坑与方法论

### 14.1 PowerShell / Windows 工具坑

| 坑 | 现象 | 正确做法 |
|---|---|---|
| **stdout 不被捕获** | PowerShell 工具执行正常，但标准输出拿不到 | 脚本内 `Out-File` 到文件，再用 Read 读 |
| **`Write` 产出无 BOM 的 UTF-8** | PS 5.1 按 GBK 读取，中文字符**吃掉引号** → 解析报错 | 用 Python 补 UTF-8 BOM：`b'\xef\xbb\xbf' + data` |
| **`W '文本' + $var` 是陷阱**（踩过 2 次） | 命令参数模式下，`'文本'`、`'+'`、`$var` 被当成**三个独立实参**，函数只收到第一个，**变量静默丢失** | 必须写 `W ('文本' + $var)` |
| **`(Func())` 嵌套调用** | PS 5.1 解析器拒绝：`"(" 后面应为表达式` | 改成 `$t = Func; Use $t` |
| **`sc.exe` / `reg.exe` 被黑名单拦截** | `Command blocked for security` | 用 `Get-Service` / `Get-CimInstance` / Python `winreg` |
| **Git Bash 路径转换** | `wevtutil /q:...` 的参数被当成路径 | `export MSYS_NO_PATHCONV=1` |
| **提权被安全策略拦死** | `Start-Process -Verb RunAs` 被拒，加绕过沙箱参数也一样 | **别重试**，产出**自提权 `.cmd`** 交给用户双击 |
| **`.ps1` 写完必须语法预检** | 否则运行到一半才报错 | `[System.Management.Automation.Language.Parser]::ParseFile()` |
| **中文 `.reg` 导出后再读会乱码** | 配对表里的设备名显示成 `潔敮慭` | 不影响功能（MAC 是关键字段）；分析时按 MAC 反查 |

**语法预检代码：**

```powershell
$errs = $null
[void][System.Management.Automation.Language.Parser]::ParseFile(
    $p, [ref]$null, [ref]$errs)
if ($errs) { $errs | ForEach-Object { "line $($_.Extent.StartLineNumber): $($_.Message)" } }
```

### 14.2 判据选择（本案最大的方法论收获）

| ❌ 错误判据 | ✅ 正确判据 | 原因 |
|---|---|---|
| `ping` 通不通 | **持续下载速率** / **并行连接吞吐** | 单包 ICMP 丢包会造出大量伪故障（本案 5 次） |
| ping 通 = 有网 | **NCSI 探测地址** | NCSI 才是 Windows 判定"有无 Internet"的依据 |
| 带宽够 = 能播 | **播放耗时 / 音频时长比值** | 媒体播放的瓶颈常在音频输出链路，不在下载 |
| 只看默认值 | **先确认默认渲染设备是哪个** | 测音频前不确认端点，会走扬声器得到**假阴性** |

### 14.3 四条核心结论

1. **音频通道状态损坏需整机重启才能重建** —— 脚本重置协议栈只能把 2.04 压到 1.12，**必须重启**才回到 1.0
2. **2.4 GHz 无法通过换信道躲开蓝牙** —— 跳频覆盖 2402–2480 MHz，盖住全部 13 个信道
3. **遇到「开蓝牙就卡」先测播放倍数** —— 比值 ≈2.0 即确诊音频通道降速，与网络无关
4. **「今天才出现」= 优先查变更点** —— 驱动安装日志、文件时间戳、软件更新；本案虽最终证伪，但正是这条线索把排查收敛到一天内

### 14.4 完整故障判定决策树

```
「开蓝牙后视频/音乐卡住」
        │
        ├─ 先测播放倍数（4s 音频计时）
        │       │
        │       ├─ ≈2.0×  ──▶ 音频通道降速
        │       │              ├─ 跑 fix-bt-audio.ps1
        │       │              ├─ 重启电脑
        │       │              └─ 复测 verify-bt-audio.ps1
        │       │
        │       ├─ 1.1~1.3× ─▶ 轻度拖慢：观察 / 关省电 / 重置协议栈
        │       │
        │       └─ ≈1.0×    ─▶ 不是音频问题，回去查网络
        │                      └─ 用持续带宽测（别用 ping）
        │
        └─ 若「完全断网」而非「卡住」──▶ 走共存排查
                                        ├─ 扫 5GHz 是否可用
                                        ├─ 关 Bluetooth Collaboration / 省电
                                        └─ 查代理层 / 虚拟网卡跃点
```
