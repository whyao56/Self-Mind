# 内容分型优化方法论

面向 MyDigitalBrain 全库 447 篇内容笔记。

起因是这个需求：所有内容要重新回看一遍，面对不同的对象该怎么对照优化。量不小，而且记下来本身不是目的。

## 一、拆问题

需求里有两层，分开看。

一层是"不同的对象"，指的是库里不同类型的笔记：视频消化记录、操作教程、日志、读书笔记、词表、报告。如果指的是别的意思，第七节另列了两种可能。

另一层是"光记不是目的"。这句是关键，说明笔记的价值不在于存下来了，而在于能被调用。由此得出优化的方向：不按主题分（军事、健康、科技），按这篇将来怎么被调用分。

同一篇讲睡眠的内容，将来用来查，就压成结论；用来做（怎么改善睡眠环境），就写成可执行步骤。主题一样，处理方式不同。

## 二、四类调用对应四套标准

| 调用方式 | 对象 | 篇数 | 目前状态 | 优化目标 |
|---|---|---|---|---|
| 查 | `仓库区/知识/`（视频消化记录） | 300 | 我看过的内容 | 能判断、能引用 |
| 做 | `仓库区/手艺/`（教程、踩坑） | 87 | 我抄下的步骤 | 试过、知道何时失效 |
| 想 | `仓库区/日志`、`旧日志`、随笔 | 18 | 时间流水 | 可回溯的档案 |
| 练 | 书、语言、提示词、模板 | 20 | 学习材料 | 可复习的系统 |
| — | 军师台账、31 个索引 | 33 | 活的状态文件 | 只维护，不优化 |

### 1. 查 · 认知型（300 篇，`仓库区/知识/`）

目前长这样：

```
[视频原标题_哔哩哔哩_bilibili](https://...?spm_id_from=...)
刷到一个FPV无人机视角的视频。画面里，两个俄罗斯士兵偶遇一架躲在草丛里的
FPV无人机。从他们后退拉枪栓的动作来看，是想远离并击毁它……
Tags: #FPV无人机 #战争 #绝望 #人性 #瞬间
```

一段第一人称叙述，读的时候是"我在讲我看到的事"。问题在于，半年后只记得"看过一个无人机视频"，想不起当时得出什么判断，需要重新读 2000 字。300 篇累积成 60 万字。

优化动作是在末尾追加，原文不动：

- 一句结论，脱离原视频也能读懂的陈述句
- 触发场景，1 到 3 个"当我在做 X 时会用到它"
- 补漏，需要背景才读得懂的地方、明显笔误

验收标准：

- 结论是陈述句，不是"这是讲 XX 的视频"
- 触发场景具体到动作，不是"增长见识"
- 原有 BV 号、图片引用、Tags 行 0 丢失

以上面那张卡演示：

```
> 结论：真正的绝望不是喊叫，是身体先反应、表情还没来得及跟上。
> 会用上：写人物濒死的段落 / 分辨"表演性恐惧"和真实恐惧 / 分析战场影像
> 补漏：FPV 是"穿越机"第一人称视角，画面抖动大、速度快——最后那帧定格
>        是偶然拍到的，不是刻意给的特写。
```

### 2. 做 · 执行型（87 篇，`仓库区/手艺/`）

目前是分点的工具、步骤清单，带命令，例如 `npx skills add alchaincyf/huashu-design`。

问题是这类内容会过期。半年后按钮位置改了、命令参数变了、软件下架了，照着做就是白费工夫。而笔记里没有任何"我验证过没有、什么时候可能失效"的信息。

优化动作：

- 前置条件，执行前需要什么（版本、权限、账号、系统）
- 失效信号，这类操作最容易随时间消失的点
- 验证状态，试过没有、成败、日期

验收标准：

- 有明确的前置条件行，原文没写就标"原文未写"
- 标出至少一个最可能失效的地方
- 命令、代码块 0 丢失

这一类篇数少但价值高：87 篇，每失效一条就是一次真实的返工。

### 3. 想 · 内化型（18 篇）

已有成熟做法，2026-08-03 和 08-04 验证过：深度整合成可回溯的档案。

标准是补背景、消除指代依赖、跨条目关联、保留原观点与情绪；不加元叙述、不加解释性小标题、不加层级前缀。

这一类继续逐日推进，不必等新方案。

### 4. 练 · 重复型（20 篇）

对象是 `工作区/书/《苏菲的世界》`（4 篇）、`工作区/语言/道本语/词汇`（1 篇）、`仓库区/手艺/学习提示词`（8 篇）、模板等。

性质与前两类不同：它们不是要能查到，是要能记住。记忆靠重复，不靠检索。

优化动作：

- 提问化，把条目转成能自问的问题，答案就在库里
- 复习标记，frontmatter 加复习状态与下次复习日期
- 记忆锚点，词表这类给每个词绑一个画面或例句

验收标准：

- 每个条目都能问出一个问题
- 词表词条有例句或锚点
- 复习状态字段可被检索

### 5. 状态文件（33 篇）不优化

`工作区/军师/进度台账.md` 是唯一状态源，加上 31 个索引页，都是生成物或指针。优化它们等于破坏它们。索引只重跑脚本，不编辑内容。

## 三、把"回看 447 篇"变成"审 447 条"

这是解决"量不小"的办法。

不要把优化理解成再读一遍、再写一遍，那是 2.2 MB 文本。

要让模型做压缩，产出只需要审的东西：

| | 现在 | 优化后 |
|---|---|---|
| 回看一篇要读 | 约 2000 字叙述 | 约 60 字（结论 + 场景） |
| 全库回看总量 | 约 90 万字 | 约 3 万字 |
| 通读一遍 | 几十小时 | 2 到 3 小时 |

也就是说，从头回看的操作方式要变：不是打开 300 个文件逐个读，是先让模型压成 300 条，只审这 300 条。判断力花在"这条总结对不对、要不要留"上，而不是花在重读上。

这也是下面流水线设计成"模型写前半段、人审后半段"的原因。

## 四、流水线

```
① 分批    每批 10 篇（约 2.5 万字），按领域切，不跨领域混批
            ↓
② 提示词  按类型选（见《优化提示词包》），一次只跑一种类型
            ↓
③ 产出    模型只输出结构化追加块，不重写原文
            ↓
④ 校验    脚本比对：原标签种类、BV 号、图片引用，三项 0 丢失
            ↓
⑤ 追加    程序化写入笔记末尾；frontmatter 加「整理: <日期>」作幂等标记
            ↓
⑥ 抽检    每批人工看 2 篇；跑偏就停，改提示词重跑
            ↓
⑦ 提交    每批一次 git commit，坏了能回退
```

几个设计要点。

幂等：frontmatter 加 `整理: 2026-10-16`，重复跑不会重复追加，也能用搜索 `["整理":` 查出已处理和未处理的。

不删不改：所有产出都是追加块，原文永远在，写错了删掉那个块就行。

按领域分批：同领域一起处理，模型吃得到上下文，知道这几张是同一主题，总结质量更高。

先小后大：先用一个领域 9 到 12 篇跑样板，格式确认后再全量，不要一上来就 300 篇。

## 五、顺序

按性价比排：

| 序 | 做什么 | 篇数 | 理由 |
|---|---|---|---|
| 1 | 执行型（手艺 87） | 87 | 数量最少、价值最高。教程过期就是真实返工，做完立刻能用 |
| 2 | 认知型（知识 300） | 300 | 量最大，收益是复利的。排第二是因为要先用第 1 类练手、定格式 |
| 3 | 内化型（日志 18） | 18 | 已有成熟做法，保持逐日节奏 |
| 4 | 产出型（报告 37） | 37 | 抽可复用方法，量小 |
| 5 | 重复型（书、语言、提示词 20） | 20 | 要先设计复习机制，最后做 |

先做一个样板：建议挑 `仓库区/手艺/` 里某个子目录，比如「浏览器与网络」9 篇，跑完看效果、定格式，再推全量。

## 六、红线

1. 不改原文，只追加
2. 不写元叙述，不出现"这条笔记是为了…""将来我失忆了…"之类
3. 不加层级前缀，标签直接写短语，不写 `内核/xxx`
4. 每批必校验，标签种类、BV 号、图片引用 0 丢失
5. 每批必提交，一次 git commit，坏了好回退
6. 不碰状态文件，军师台账与索引页只读不写

## 七、如果"不同对象"指的是别的意思

若指"不同受众"，即同一份内容要给不同人看（自己、别人、公开），那要做的是分版而不是分型。做法是同一笔记加详版和摘要版，或者用折叠块把"给自己看的"和"能给外人看的"分开。目前库里几乎全是给自己看的，暂时用不上。

若指"不同来源"，即视频、书、文章、自己写的，这个维度已经在用了（类型标签：知识卡片、教程、报告、日记等）。它决定放哪，但不决定怎么优化。真正决定优化方式的是第二节的调用方式。
