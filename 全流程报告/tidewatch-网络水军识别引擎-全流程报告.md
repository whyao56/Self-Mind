## 2. 选题：从「做什么项目」到「识别网络水军」

### 2.1 从标杆项目提炼标准

用户给的标杆是 [`Lolitide/VirusDetector`](https://github.com/Lolitide/VirusDetector)：
浏览器扩展，用规则评分引擎检测银狐木马的钓鱼仿冒网站。零依赖 Manifest V3，
Firefox 上架版本 2.5.1，MIT 协议，52 用户。

我把它拆开，提炼出**四条可复用标准**：

1. **真实场景** —— 不解决虚构问题。银狐木马是真实存在的威胁。
2. **可解释内核** —— 结论能给依据，不是黑盒打分。所有规则公开可读。
3. **可插拔扩展** —— 加规则不需要改引擎。
4. **分级输出 + 迭代闭环** —— 给风险分级而不是「是/否」，让人能反馈。

### 2.2 为什么最终选了网络水军识别

我给了 20 个候选选题让他挑，用户圈定了「分析全网新闻、发言、弹幕、评论，
先从识别网络水军开头，到识别所有网络舆情为最终目标」。

这个选题同时满足四条标准，而且第四条的「迭代闭环」特别天然：

- **真实场景** ✅ 水军是平台和研究者真实的痛点
- **可解释内核** ✅ 「这条为什么可疑」可以逐条列出来
- **可插拔** ✅ 加一个检测维度 = 加一个信号类
- **分级 + 闭环** ✅ 三档分级 → 人工复核 → 反馈调参

而且它有一个**非常适合做开源项目**的性质：**没有标注数据是共同困难。**
真实的水军数据集几乎拿不到（涉隐私、时效性强、标注成本高）。
这意味着任何人想入场都要自己解决数据问题 —— 而如果我把「怎么在没有标注的情况下
验证算法」这件事做扎实，就是差异化价值。

### 2.3 用户选的边界

- **数据源**：公开数据集 + B站/抖音弹幕 + 评论
- **第一版边界**：三层骨架先立起来（不是先做深某一层）

第二条决定了后面的开发顺序：**先把三层都跑通、都能出结果，
再逐层加厚**。这个决定后来被证明是对的——因为只有三层都在跑，
消融实验才能告诉我「哪一层在起作用」。

## 3. 核心方法论：不靠单账号，靠协同性

### 3.1 问题的本质

最容易走错的一步，是**盯着单个账号找特征**：新注册、无头像、默认昵称、
零粉丝、只关注别人。这套特征十年前有效。现在完全无效:

> 买个养了半年的号成本极低。对手只要花点钱，就能让每个账号单独看起来都很正常。

### 3.2 换一个不变量

这个项目建立在另一个判断上：

> **对手可以伪造身份，但很难伪造「各自独立」。**

一群人要一起行动，就必然在时间、文本、关系上留下统计痕迹：

- **时间上**：同一分钟内齐刷刷开口
- **文本上**：文案从同一个模板里填出来
- **关系上**：同一批账号反复出现在同一批话题里

伪造身份只需要花钱，伪造「互不相干」需要**放弃协同本身**——那等于放弃攻击。

### 3.3 由此推出的三条硬规则

这个判断不是一个口号，它直接决定了三处实现细节：

**规则一：层权重按「规避成本」递增，不按「准确率」递增。**

```yaml
scoring:
  kind_weights:
    text: 0.9          # 换个说法就能规避
    account: 0.7       # 买个老号就能规避
    coordination: 1.3  # 要规避就得放弃协同
```

反过来配权重的话，引擎会被**对手最容易操纵的那一层**主导。

**规则二：账号层永远不单独定案。**

这一层全是弱信号（新号、无头像、默认昵称）。这些特征单独看毫无意义——
每天有大量正常用户注册。所以每个账号信号都刻意把强度压得很低，
必须多个叠加才触发：

```python
# account_signals.py —— 资料异常信号是「叠加」而不是「任一」
score = 0.0
if actor.is_default_name:  score += 0.3   # 默认昵称
if not actor.has_avatar:   score += 0.2   # 无头像
if actor.follower_ratio > threshold: score += 0.3   # 只关注别人
if (actor.rename_count or 0) >= 3: score += 0.2     # 频繁改名
if score < 0.4:            # 低于这个值不报 —— 单独一个特征不构成嫌疑
    return []
```

**规则三：协同层必须校验「跨账号」。**

这一条我一开始漏了，结果是**一个人复制粘贴连发三条同样的话被报成协同团伙**。
详见 [7.5](#7.5)。

## 5. 关键算法原理

### 5.1 AC 自动机：多模式串匹配

**为什么需要**：话术库有 55 条，正则 7 条。如果对每条发言都遍历 55 条话术
做 `in` 判断，复杂度是 `O(文本长 × 话术条数)`。加了 500 条话术就慢十倍。

**AC 自动机的价值**：把匹配复杂度变成 `O(文本长 + 命中数)`，**与模式数量无关**。

**原理三件套**：

1. **goto 表**：一棵 Trie（用嵌套 dict 实现）。
2. **fail 指针**：BFS 构建。当在节点 `p` 匹配失败时，跳到「`p` 的最长真后缀」
   对应的节点——这个后缀必须也是某个模式的前缀。
3. **output 集合**：每个节点沿 fail 链合并它所有后缀能匹配到的模式。

```python
def build(self) -> "AhoCorasick":
    """BFS 建 fail 指针，并把 output 沿 fail 链合并。"""
    queue = deque()
    for child in self._goto[0].values():
        child.fail = 0
        queue.append(child)
    while queue:
        node = queue.popleft()
        # 关键：把 fail 节点的 output 并进来。
        # 不做这一步，会漏掉「后缀也是模式」的情况 ——
        # 例如模式里有 "微信" 和 "加微信"，只匹配到后者时前者会丢。
        node.output |= self._nodes[node.fail].output
        for ch, child in node.goto.items():
            # fail 的传递：child 的 fail = child.fail 沿着字符 ch 的转移
            f = node.fail
            while f and ch not in self._nodes[f].goto:
                f = self._nodes[f].fail
            child.fail = self._nodes[f].goto.get(ch, 0)
            queue.append(child)
    return self
```

**踩的坑**：`ignore_case=True` 时要把模式和文本都先 `lower()`，
但中文不受影响、全角字母数字要先折叠——这些统一在 `normalize_text()`
和 `fold_for_match()` 里做，见 [7.1](#7.1)。

### 5.2 抗规避折叠（evasion signal 的核心）

**对手的手法**：插符号（`加·微·信`）、谐音（`加薇信`）、上全角、
夹 emoji（`加薇❤️信`）、混形近字（`微→薇/溦/威`）。

**做法**：**逐字符白名单过滤 + 同义折叠**。

```python
def fold_for_match(text: str, mapping: Mapping[str, str] | None = None) -> str:
    """激进的抗规避折叠，专供话术库匹配。

    只保留汉字和字母数字，其余一律丢弃 —— 避免「加 微 信」因为空格
    而匹配不上「加微信」。丢弃后再套一遍形近字映射表。
    """
    out: list[str] = []
    for ch in text:
        mapped = mapping.get(ch) or mapping.get(ch.lower())
        if mapped is not None:
            out.append(mapped)
        elif _CJK.match(ch):
            out.append(ch)
        elif _ASCII_WORD.match(ch.lower()):
            out.append(ch.lower())
    return "".join(out)
```

**这是有损的，绝不能用于展示。** 折叠后 `加薇❤️信` 变成 `加微信` ——
如果拿它写报告，用户会看到一句他从来没说过的话。所以：

- `Item.text` 永远是原文
- 折叠只在「匹配」这一步调用
- `text.evasion` 信号报的是**差集**（见下）

**evasion 信号的判定逻辑**：

```python
direct = rules.scan_phrases(item.text)          # 原文能匹配到的
folded = rules.scan_phrases_folded(item.text)   # 折叠后才能匹配到的
extra = folded - direct                          # 差集才是「刻意规避」的证据
```

**为什么必须用差集**：如果它把原文就能匹配到的也算进去，
那它和 `text.keyword` 就没有区别了 —— 「刻意规避」这个高精度判断会被噪声稀释。
正常用户不会把「微信」写成「薇❤️信」，这个信号是文本层里**精度最高**的一个。

### 5.3 SimHash + 汉明距离

**用途**：给海量文本算一个廉价的近似指纹，用于去重和聚类的一级过滤。

**原理**：把每个 token 哈希成 64 位，逐位投票（该位为 1 则 +1，为 0 则 -1），
最后按符号汇总成指纹。

```python
def simhash(tokens: Sequence[str], bits: int = 64) -> int:
    vector = [0] * bits
    for token in tokens:
        h = _hash64(token)
        for i in range(bits):
            vector[i] += 1 if (h >> i) & 1 else -1
    out = 0
    for i in range(bits):
        if vector[i] > 0:
            out |= 1 << i
    return out
```

相近的文本只在少数位上产生分歧，于是汉明距离成了内容相似度的廉价近似：

```python
def hash_similarity(a: int, b: int, bits: int = 64) -> float:
    return 1.0 - hamming_distance(a, b) / bits
```

### 5.4 最长公共子串（LCS）与「分母该用谁」

**为什么用子串而不是子序列**：照抄在文本上的表现是**连续片段的雷同**。
子序列会因为中文里共享常用字（的、了、是）产生大量假阳性——
任意两句正常中文的最长公共子序列都很长。

**滚动数组压空间**：

```python
def longest_common_segment(a: str, b: str) -> CommonSegment:
    """最长公共**子串**（连续），返回长度与两端起点。

    用滚动数组把空间从 O(nm) 压到 O(min(n,m))。
    短文本评论场景下时间 O(nm) 完全够用，不值得为此上后缀自动机。
    """
    if len(a) > len(b):
        a, b = b, a          # 让 a 是较短的，滚动数组大小 = len(a)
    prev = [0] * (len(a) + 1)
    best = CommonSegment(0, 0, 0)
    for j in range(1, len(b) + 1):
        cur = [0] * (len(a) + 1)
        for i in range(1, len(a) + 1):
            if a[i - 1] == b[j - 1]:
                cur[i] = prev[i - 1] + 1
                if cur[i] > best.length:
                    best = CommonSegment(cur[i], i - cur[i], j - cur[i])
        prev = cur
    return best
```

**「分母该用谁」是一个真实的 bug**，详见 [7.4](#7.4)。
结论：**必须用较长串**。用较短串会让短文本之间的误报率飙升。

### 5.5 两级过滤：性能与准确率的折中

同话题内两两比较是 `O(n²)`。一个热门视频的评论量下这个成本不可接受。

```python
for i in range(len(candidates)):
    if visited[i]:
        continue
    group = [i]
    for j in range(i + 1, len(candidates)):
        if visited[j]:
            continue
        # 一级：SimHash 汉明距离，O(1)，排除绝大多数不相关的对
        if hash_similarity(fingerprints[i], fingerprints[j]) < sim_threshold:
            continue
        # 二级：最长公共子串比例，O(nm)，只对活下来的对做精确确认
        if longest_common_substring_ratio(texts[i], texts[j]) < lcs_threshold:
            continue
        group.append(j)
```

- 只用一级 → 漏掉**局部照抄**（改了前半段、原样保留后半段），因为 SimHash 对整体分布敏感
- 只用二级 → 慢到无法接受

### 5.6 时间爆发：为什么背景速率必须取自全数据集

**原本的做法**：用该话题自身的平均密度当基准。

**症状**：一个整体就是集中投放的话题，它的平均密度早就被投放本身拉高了，
于是**永远检不出自己**，比值恒等于 1。

**修正后的做法**：

```python
# 背景速率：全数据集（所有话题）的总体到达速率，条/秒
background = len(timed_all) / max(bg_span, 1.0)
...
# 用这一段的**真实跨度**算速率，而不是名义窗口长度：
# 8 条挤在 14 秒里，说它是「8 条 / 300 秒」会把爆发稀释掉
span_sec = max((t1 - t0).total_seconds(), 1.0)
local_rate = best_count / span_sec
ratio = safe_div(local_rate, background)
```

**代价是刻意接受的**：这份数据本身必须含有可比的正常活动。如果整批数据
就是一段紧挨着的爆发（没有任何平缓的背景），信号会主动**弃权**。

> **能弃权，比能检出更重要。** 一个在信息不足时硬给结论的系统，
> 比一个说「我不知道」的系统危险得多。这条取舍有专门的回归测试守着。

### 5.7 共现图与标签传播

**构造**：账号-话题二部图 → 投影到账号一侧 → 账号-账号图。

```python
for a, b in combinations(actors, 2):
    shared = actor_topics[a] & actor_topics[b]
    if len(shared) < min_shared:          # 共同话题数下限
        continue
    # 关键：交并比约束，而不只看共同话题的绝对数量。
    # 在几个大板块都活跃的正常用户，共同话题数天然就高，只看绝对值会大量误报。
    if safe_div(len(shared), len(actor_topics[a] | actor_topics[b])) < overlap:
        continue
    adjacency[a].add(b)
    adjacency[b].add(a)
```

**标签传播找社区**（十几行实现，足够把「两两相似」聚成「一群」）：

```python
def _label_propagation(adjacency, iterations=20):
    labels = {node: node for node in adjacency}
    for _ in range(iterations):
        changed = False
        for node in sorted(adjacency):      # 按 id 排序遍历 → 结果可复现
            counts = Counter(labels[nb] for nb in adjacency[node])
            top_count = max(counts.values())
            # 平票时取字典序最小的标签，保证同一份数据两次运行结果一致
            best = min(label for label, count in counts.items() if count == top_count)
            if labels[node] != best:
                labels[node] = best
                changed = True
        if not changed:
            break
    ...
```

按 id 排序 + 平票取最小标签，都是为了**可复现**——否则同一份数据两次运行
可能给出不同的团伙划分，实验就没法对比了。

### 5.8 评分聚合公式

```
score = Σ(强度 × 档位倍率 × 信号权重 × 层权重) × scale
        + 跨层联动加分
封顶到 cap，再按 levels 切成三档
```

三个刻意的设计，每一个都对应一类常见失败：

**① 档位倍率**：同一个信号判 STRONG 比判 WEAK 贡献更多分。

```python
level_multiplier: {weak: 1.0, strong: 1.5}
```

否则「信号自己很确信」这件事传不到总分上，强证据会被平均掉。

**② 联动加分只在跨层时生效**：

```python
kinds = {h.kind.value for h in hits}
bonus = 0.0
if len(kinds) >= self.min_kinds:                    # 默认 2
    bonus = (len(kinds) - self.min_kinds + 1) * self.bonus_per_extra
```

同一层里命中十个信号**不加分**——那通常只是同一个原因的十种说法
（一条「加微信私聊」的评论会同时触发话术、正则、规避三个文本信号），
把它们当十条独立证据累加会得到虚高的分数。

**③ 保底提档 + 显式旗标**：

```python
level = self._level_for(score)
promoted = False
if level is Level.CLEAN and any(h.level is Level.STRONG for h in hits):
    # 有强信号却算成「正常」时保底提升一档。
    # 分数不变，只提档 —— 所以报告里必须把这面旗标显示出来。
    level = Level.WEAK
    promoted = True
```

`promoted` 不是内部实现细节，是 **API 的一部分**：
凡是会让使用者困惑的地方（「10.5 分 · 弱嫌疑」这种分数与档位对不上的组合），
都要在输出里解释清楚。

### 5.9 团伙 → 成员传播

协同层产出的目标是**团伙**（GROUP）。不传播的话，一个完全由水军组成的团伙
被挖出来了，成员账号在报告里却一行都看不到——**结论是对的，但不可用。**

```python
def propagate_group_members(assessments, factor):
    """把团伙的可疑度按比例传给它的成员账号。

    传播是有代价的（团伙误报会连坐成员），所以：
      - 系数默认只有 0.6，成员拿不到团伙的全部分数
      - 传播过去的信号一律标 WEAK，不直接定案
      - 只从已判为可疑的团伙往外传
    """
```

**这一条的威力有多大**：加了它之后，消融实验里「仅协同层」的
actor F1 从 `0.000/0.000/0.000` 变成 `1.000/0.725/0.841`。

## 7. 踩坑与修复（11 条）

**这一节是整个报告里最值钱的部分。**

理由：一个「跑起来不报错但结论是错的」缺陷，比崩溃难发现得多。
崩溃会自己浮出水面，错误结论会安静地写进报告里，然后被人当成事实引用。

### 7.1 全角字母数字折叠静默空转 {#7.1}

**症状**：`normalize_text("ＡＢＣ１２３")` 返回的还是 `"ＡＢＣ１２３"`。

**根因**：`str.translate()` 是拿**码点整数**去查表的，而映射表是用
**字符**当键建的：

```python
# 错的
_FULLWIDTH_ALNUM = {chr(0xFF10 + i): chr(0x30 + i) for i in range(10)}
#                ^^^^^^^^^^^^^^^ 这是字符串 "０"，不是码点 0xFF10

# 对的
_FULLWIDTH_ALNUM = {0xFF10 + i: chr(0x30 + i) for i in range(10)}
```

`str.translate` 查不到就保持原样，**不会抛异常**。同一文件里的零宽字符表
因为用了 `ord()` 反而是正常的——于是「有的折叠生效、有的不生效」，
更难怀疑到映射表本身。

> **教训**：Python 里「查不到就静默返回原值」的接口（`translate`、`dict.get`、
> 自定义的 `dig()`）是最容易藏 bug 的地方。容错设计在脏数据场景下是优点，
> 在拼写错误场景下是缺点。

### 7.2 所有信号权重静默回落到 1.0 {#7.2}

**症状**：爆发信号分数明显偏低（32.5 分），排查发现 `weight` 全是默认的 1.0。

**根因**：配置用扁平的含点键名 `signals: text.template: weight: 1.4`，
而查找用 `section("signals.text.template")`。
**点号既是配置路径的分隔符，又是信号名的一部分**——两条路径撞在一起。

**修复**：配置改成嵌套结构，`iter_signals()` 展开两层。
爆发分数从 32.5 涨到 68.2。

**守着它的测试**：`test_all_signals_exposed_via_config`
（断言「配置里声明的」与「代码里注册的」完全一致）、
`test_signal_weight_scales_contribution`

> **教训**：配置键名里的分隔符是个隐藏的语法。任何「名字里可以包含分隔符」
> 的设计都要想清楚：这个分隔符最终会不会被当成语法解析。

### 7.3 未命中任何信号的对象从结果里整个消失 {#7.3}

**症状**：CLI 显示「读取 91 条发言」，实际有 172 条。

**根因**（两个问题叠在一起）：

1. `summarize()` 的 `total` 是「判定目标数」而不是「发言数」，语义标错了
2. 更严重：**没有命中任何信号的对象压根不会出现在结果里**

第 2 点直接毁掉评测能力：「判定为正常」和「压根没跑到」被合并了，
**召回率没法算**——分母里少了一整批真水军。

**修复**：

```python
def assess(self, hits, labels=None, targets=None):
    """`targets` 是「必须出现在结果里的目标清单」。不传的话，未命中任何
    信号的条目会从结果中消失 —— 那样评测时就无法区分「判定为正常」和
    「根本没跑过」，这两件事必须能分开，否则算不出召回率。"""
```

```python
# Pipeline.run() 传入全部 item 和 actor
targets = [(TargetKind.ITEM, i.item_id) for i in data.items]
targets += [(TargetKind.ACTOR, aid) for aid in data.actors]
```

> **教训**：**「没发现异常」和「没检查」必须在数据结构上区分开。**
> 把这两件事合并的 API，一定会在评测环节反噬。

### 7.4 LCS 分母用较短串 → 正常评论被误报成抄袭 {#7.4}

**症状**：两条三十来字的**正常**评论，共用一句常见表达
（「不过在生产环境里可能还要补一些兜底」，19 字），
比例达到 `19 / 35 = 0.543`，越过 0.5 阈值被报成「互相抄袭」。

**根因**：

```python
return seg.length / min(len(a), len(b))   # 错的
```

**修复**：

```python
return seg.length / max(len(a), len(b))
```

**理由**：这个比例想衡量的是「**较长的那条里有多少比例是抄来的**」。
用较短者作分母会让短文本之间的误报率飙升，而那只说明中文表达有惯性，
不说明它们在协同。真实场景里「共享一个常用短语」太常见了。

对真正的照抄没有影响：那种情况下较长者本身也几乎全是公共段。

### 7.5 协同层未校验「跨账号」 {#7.5}

**症状**：一个人复制粘贴连发三条同样的话，被报成「协同团伙」。

**根因**：`burst` 和 `cluster` 只统计了「条数够不够」，没统计
「来自几个**不同**账号」。

**修复**：两个信号都加 `min_actors` 校验（默认 3）。

```python
actors = sorted({c.actor_id for c in cluster})
# 协同层必须校验「跨账号」。一个人连发十八条，那是刷屏，
# 属于账号层的原创度问题，不是「一群人一起行动」——
# 不校验的话，任何活跃用户都能把自己的账号刷成「爆发团伙」。
if len(actors) < min_actors:
    continue
```

> **教训**：「多条内容相似」和「多个人在协同」是两个完全不同的问题。
> 前者一个人一台机器就能做到。这是在写协同层时最容易犯的错，
> 而且症状是**误报**，比漏报更伤使用者信任。

### 7.6 账号年龄用 `datetime.now()` 计算 {#7.6}

**症状**：分析一份 2020 年的历史数据时，当年注册的水军号被算成
「注册了六年」，年龄信号**集体失效**——而且失败得非常安静，什么都不报。

**根因**：`actor.age_days()` 默认用当前时刻。分析历史数据时，
「当前时刻」是错的参照系。

**修复**：信号层改用 `data.time_span` 的上界当「现在」——
数据里的最后一秒才是这份数据的「现在」。

> **教训**：任何用到 `now()` 的地方，都要先问一句「这个 now 是谁的 now」。
> 在离线分析系统里，几乎总是数据的 now，不是运行时的 now。

### 7.7 合成数据的「正常」评论只有 20 种模板 {#7.7}

**症状**：3 个**正常**用户说了相似的话，被聚类信号判成协同团伙。

**根因**：这不是算法错，是**数据集缺陷**。生成器里正常评论是从 20 个固定
模板里抽的，抽到重复的概率不低。

**修复**：正常评论改用「开头池 × 中段池」的组合池（`pairs[:160]`），
保证任意两条不共享「开头 + 中段」组合。

**附带的第二个问题**：模板组的发帖间隔原本是 150 秒，导致它**同时**被
burst 和 cluster 抓到，两个信号混在一起没法归因。改成 900 秒后，
模板组只被 cluster 抓到——消融实验才能干净地归因。

> **教训**：**合成数据集的缺陷会被误读成算法的缺陷。**
> 看到「3 个正常用户被当成团伙」时，第一反应应该是去查数据，而不是调阈值。

### 7.8 Markdown 报告一跑就 KeyError {#7.8}

**症状**：`tidewatch scan data.jsonl --out report.md` 直接崩溃。

**根因**：`summarize()` 早就把 `total` 改名成了 `assessed`（修 7.3 时改的），
但 `render_markdown()` 里还在读 `stats['total']`。

**修复**：改成 `stats['assessed']`，顺便把 `no_signal` 也写进报告。

> **教训**：`dict` 的键是**没有静态检查**的接口。重命名字段时，
> 除了改名那处还要 grep 整个仓库。
> 这条测试真正的价值不是断言，而是**它真的把渲染跑了一遍**。

### 7.9 流水线返回的命中列表与评估结果互相矛盾 {#7.9}

**症状**：`result.assessments` 里能看到 `coordination.cluster#member`
这类传播过来的证据，但 `result.hits` 里一条都没有。

**根因**：

```python
merged = list(hits) + propagated
assessments = self.scorer.assess(merged, ...)
return Result(data, hits, assessments, ...)   # ← 返回的是传播前的 hits
```

**修复**：返回 `merged`。

> **教训**：一个对象里两个字段描述同一件事时，它们必须由**同一次计算**产生。
> 这里 `assessments` 用了合并后的数据，`hits` 用了合并前的——单看每行都对。

### 7.10 CLI 的 `--set` 只有写在子命令前面才生效 {#7.10}

**症状**：模块文档里给的示例 `tidewatch scan data.jsonl --set a.b=1`
直接报 `unrecognized arguments`。改成写在前面，**也不生效**。

**根因（两层）**：

1. argparse 默认只接受「全局选项在子命令之前」，所以文档里的写法本身就不通。
   修法是给子解析器也挂上这些选项（`parents=[common]`）。

2. 修完第一层后出现了更隐蔽的问题：`--set` 写在前面**反而失效**。
   因为 `parents=` 是共享 action **对象**的，而 `set_defaults()` 会
   **就地改写** action 的 `default`。于是给主解析器设默认值时，
   顺手把子解析器那份 `SUPPRESS` 也改成了 `[]`——
   子命令解析完拿一份空列表覆盖回去。

**修复**：每个解析器各自持有一份独立的选项定义（工厂函数），
子解析器那侧默认值用 `argparse.SUPPRESS`。

> **教训**：`parents=` 共享的是对象而不是副本，这是个反直觉的点。
> 而且「两个位置都测」不是冗余——只测一个位置的话，第 2 层根因根本不会暴露。

### 7.11 协同层的 actor 级 F1 是 0 {#7.11}

**症状**：消融实验里「仅协同层」的 actor F1 是 `0.000 / 0.000 / 0.000`。

**根因**：这是**设计缺口**，不是 bug。协同层产出的目标是团伙（GROUP），
不产出账号（ACTOR）。于是「抓到了团伙」这件事在账号级指标上完全体现不出来。

**修复**：加 `propagate_group_members()`，在流水线里传播后重新评分。
actor F1 从 `0.000/0.000/0.000` 变成 `1.000/0.725/0.841`。

> **教训**：**指标为 0 不一定是算法不行，也可能是定位错了。**
> 在调参之前，先确认指标衡量的东西和信号产出的东西是不是同一个层级。

## 8. 实测数据与结论

### 8.1 实验设置

| 项目 | 值 |
|---|---|
| 配置指纹 | `330f370aea9c` |
| 数据 | `data/eval/synthetic_labeled.jsonl` |
| 规模 | 193 条发言 / 160 个账号 / 10 个话题 |
| 来源 | `scripts/gen_sample.py` 合成 |
| 注入模式 | normal 120 / template 8 / burst 15 / gang 24 / shill 5 / repeat 18 / flood 3 |
| 标注 | 水军发言 73 条、水军账号 40 个 |
| 判定口径 | 弱嫌疑及以上算可疑 |
| 启用信号 | 10 / 10 |

### 8.2 消融实验主表

| 实验 | 启用信号 | item P/R/F1 | actor P/R/F1 | 挖出团伙 | 耗时 |
|---|---|---|---|---|---|
| **全量** | 10 | 1.000 / 0.096 / 0.175 | **1.000 / 1.000 / 1.000** | 3 | 497 ms |
| 仅文本层 | 4 | 1.000 / 0.096 / 0.175 | 0.000 / 0.000 / 0.000 | 0 | 24 ms |
| 仅账号层 | 3 | — | 1.000 / 1.000 / 1.000 | **0** | 4 ms |
| 仅协同层 | 3 | — | 1.000 / 0.725 / 0.841 | **3** | 41 ms |
| 文本+账号 | 7 | 1.000 / 0.096 / 0.175 | 1.000 / 1.000 / 1.000 | 0 | 26 ms |
| 文本+协同 | 7 | 1.000 / 0.096 / 0.175 | 1.000 / 0.725 / 0.841 | 3 | 64 ms |
| 账号+协同 | 6 | — | 1.000 / 1.000 / 1.000 | 3 | 44 ms |

### 8.3 团伙检测纯度（全量）

| 信号 | 抓到的成员数 | 其中真水军 | 纯度 |
|---|---|---|---|
| `coordination.cluster` | 8 | 8 | 100% |
| `coordination.cooccur` | 6 | 6 | 100% |
| `coordination.burst` | 15 | 15 | 100% |

### 8.4 三条核心结论

**结论一：三层不是冗余，每一层都在干别人干不了的活。**

- 「仅账号层」的 actor F1 = 1.000，与全量**相同**，但团伙数是 **0**
- 「仅协同层」的团伙数是 3，与全量**相同**，但 actor 召回只有 **0.725**

「发现团伙」和「把账号判准」是两种不同的能力，各自有独立的层承载。
去掉任何一层，都有东西做不了。

**结论二：团伙纯度 100%。** 报出来的 3 个团伙，成员全是注入的水军账号，
正常用户一条都没被牵连。

**结论三：item 级召回 0.096 是刻意留的口子，不是缺陷。**

协同层的证据（「这 15 条在 154 秒内来自 15 个账号」）天然长在团伙上。
要把它归到每一条具体发言，需要再设计一层「团伙 → 成员 → **条目**」的传播。
目前只做了「团伙 → 成员」一级。**这正是迭代清单的第 1 项。**

### 8.5 性能

| 信号 | 耗时 | 复杂度 |
|---|---|---|
| `coordination.cluster` | ~420 ms | O(n²) 同话题两两比较 ←**唯一热点** |
| `text.template` | 12 ms | O(n × 词数) |
| `text.repetition` | 5 ms | O(n × 文本长) |
| `text.evasion` | 4 ms | O(n × 文本长) |
| 其余 6 个信号合计 | < 5 ms | |
| 评分 + 传播 + 重评 | 2 ms | O(命中数) |

### 8.6 关于这些数字，必须一起说明的边界

> ⚠️ **合成数据只用来验证算法原理（信号方向对不对、三层是否互补），
> 不能用来宣称真实场景下的准确率。**

理由是诚实且具体的：这份数据是我自己注入的，注入模式天然贴合我写的信号。
在这种数据上刷到 99% 没有任何信息量。

真实场景的评测需要公开数据集或自己的标注数据。
`eval/run_eval.py` 的 `load_labelled()` 只依赖「目标 id → 是否水军」
**一个映射**，换成自己的标注即可：

```python
def load_labelled(path):
    """标注只需要两样：目标 id 和「它是不是水军」。
    任何数据集只要能提供这个映射，就能套进这套评测 —— 这是它不绑定
    特定数据集的关键。"""
```

### CI 里两个刻意的设计

**① jieba 有/无 两条矩阵。** jieba 是可选依赖，不装时 `tokenize` 会降级为
字符 bigram。只测「装了 jieba」那一条，等于**把降级路径的承诺放在嘴上**。

**② 冒烟断言只卡在「功能还在」的最低线。**

```python
assert signals >= 8, f"启用的信号数异常偏少: {signals}"
assert item_f1 > 0, "item F1 退化为 0"
assert actor_f1 > 0, "actor F1 退化为 0"
```

卡得太死会让正常的调参变成红叉，那反而会**逼着后人把 CI 删掉**。

### 关于 `data/raw/` 的处理

`data/raw/` 被 `.gitignore` 和 `.dockerignore` 双重排除，原因是抓取下来的
评论/弹幕可能含个人信息，绝不能被打进镜像分发出去。但保留
`data/sample/` 和 `data/eval/` 进版本库——review 时要能看到数据长什么样。

<a id="10"></a>
## 10. 已知限制与待验证假设

### 10.1 已实现的限制（写进 README 的部分）

1. **item 级召回低（0.096）**。协同层的证据长在团伙上，还没传播到具体条目。
2. **合成数据不能作为性能背书**。它只证明原理成立。
3. **爆发检测依赖可比的背景速率**。数据里没有平缓的正常活动时，信号主动弃权。
4. **`_MAX_PER_TOPIC = 400` 是性能保护**。单话题超过 400 条只取前 400 条。
5. **共现图是 O(n²)**。账号数上万时会明显变慢，需要先按活跃度剪枝。
6. **标签传播只跑 20 轮**。超大图上可能不收敛。
7. **没有跨语言支持**。分词、折叠表、停用词都是中文的。

### 10.2 未验证的假设（诚实标注）

| # | 假设 | 为什么仍需验证 | 怎么验证 |
|---|---|---|---|
| H1 | 三层互补性在真实数据上成立 | 合成数据的注入模式天然贴合我写的信号；真实协同可能是长周期、低频、跨话题的 | 接一个有标注的公开数据集重跑 |
| H2 | SimHash 阈值 0.72 合适 | 经验值，无理论依据 | 构造已知相似度的文本对，画阈值-召回曲线 |
| H3 | 打乱语序的洗稿能挡住 | 挡不住。LCS 是子串，SimHash 对语序不敏感但**没测过** | 造「同义词替换 + 语序打乱」样本测漏检率 |
| H4 | 共现图交并比阈值 0.5 合适 | 经验值。对于只在单一话题活动的团伙这层完全失效 | 按**信号**粒度（而非层级粒度）做消融 |
| H5 | 单机 Python 的天花板在哪 | 193 条 497ms，1 万/10 万条**没测过**；`_MAX_PER_TOPIC=400` 是拍下来的 | 测规模-耗时曲线 |

> 把未验证的假设写出来，不是自我否定。它同时也是给别人的路标：
> 「你可以从这里继续做」。而且它挡住了最糟糕的一种质疑——
> 别人发现假设不成立时，不会觉得你在撒谎。

## 11. 迭代路线

### 12.3 面试官大概率会追问的问题

**Q：你为什么不用大模型？现在做内容风控不是都上 LLM 吗？**

> 三个理由。第一，这个项目的定位是**可解释的规则引擎**，我用它做基准线——
> 任何模型方案都必须先解释清楚它比规则强在哪、强多少，而这个基准线现在不存在。
> 第二，水军规避关键词的手法（谐音、插符号、形近字）用规则+折叠表能挡，
> 而且成本是零、可解释、可微调；换成 LLM 就变成了不可解释的黑盒+按量付费。
> 第三，**协同行为这个维度 LLM 做不了**——判断「这 15 条在 154 秒内来自
> 15 个账号」需要看整批数据的关系结构，不是逐条文本理解能解决的。
> LLM 更适合做「语义洗稿检测」这一块，那是我的迭代清单里的一项。

**Q：你的准确率是多少？**

> 合成数据上账号级 F1 是 1.000，**但我不认为这个数字有意义**，所以我在
> README 里主动写了它的边界。这份数据是我自己注入的，注入模式贴合我写的
> 信号，在这种数据上报 99% 没有信息量。
> 我认为**有意义的结论是消融实验揭示的**：三层互补，
> 账号层单独能判准账号但一个团伙都发现不了，协同层单独能挖出全部团伙
> 但账号召回只有 0.725。这个结论是可检验的，而且它不依赖于数据的绝对难度。
> 真实准确率需要公开数据集来测，`eval/run_eval.py` 只依赖
> 「目标 id → 是否水军」一个映射，换成任何标注都能跑。

**Q：最难的地方在哪？**

> 不是算法。AC 自动机、SimHash、标签传播都是教科书内容，我甚至刻意
> 用最简单的实现（标签传播只有十几行）。
> 最难的是**「跑起来不报错但结论是错的」这一类缺陷**。
> 我记录了 11 条，其中 6 条属于静默失败——不崩溃、不抛异常，
> 只是悄悄给出错误结论。举个例子：`str.translate` 查不到就返回原值，
> 所以我的全角折半角映射表因为键用了字符而不是码点，一直静默空转。
> 另一个更严重：聚合器只遍历它见过的目标，导致**没有命中任何信号的条目
> 从结果里整个消失**——这一条直接让召回率算不出来，因为分母里
> 少了一整批真水军。
> 所以我在项目里做的最有价值的一件事可能不是信号，是**那批回归测试**。

**Q：如果给你一个真实的平台数据，你会怎么改？**

> 三步。第一，先跑一遍现有配置，**看误报**——正常用户被误伤是最先要解决的
> 问题，因为规则的代价是不对称的：漏一个水军平台损失不大，
> 误伤一个正常用户是公关事件。第二，读一遍误报样本，把领域话术补进
> `rules/phrases.yaml`，同时看哪些信号在高频误报，用 `--set` 把它关掉或者降权。
> 第三，才是考虑加新维度——那时候我会有真实数据告诉我缺什么。
> 现在这个阶段最不该做的就是凭想象加信号。

**Q：这个项目有什么是你觉得做得不够好的？**

> 两点。第一，**item 级召回只有 0.096**，因为协同层的证据长在团伙上，
> 我还没做「团伙 → 成员 → 条目」的二级传播。这个我很清楚，也写在了 README 里。
> 第二，**评测的粒度太粗**。现在的消融只区分「哪一层」，说不出
> 「层内哪个信号在起作用」——这意味着十信号里可能有两个从来没贡献过
> 任何东西，而我不知道。按信号粒度做消融是我迭代清单的第 2 项。

### 12.4 为什么这个项目适合放简历

对照用户给的四条标准：

| 标准 | 在简历/面试里的价值 |
|---|---|
| **可以实际应用** | 面试官能立刻理解场景，不需要你解释背景 |
| **别人可以微调** | 证明你想过「可维护性」和「给别人用」，不只是「能跑通」 |
| **原理清晰** | 每一条都能往下追问三层：算法、为什么选它、代价是什么 |
| **方便迭代** | 你有明确的 roadmap 和已知缺陷清单，说明这是活的项目 |

而且它有一个**很难得的特点**：**核心难点不在算法，在工程判断。**
AC 自动机、SimHash 都是现成的，真正值钱的是「知道该检测什么」
（协同而不是单账号）和「知道哪里会安静地出错」（11 条踩坑里的 6 条静默失败）。
这两样东西恰恰是面试里最能体现水平的部分。
